Start here

Audience: new Umicom contributors and anyone learning to use a terminal or Git for the first time. You need no programming experience.

How to study: follow each command carefully; read its result before progressing. Work in your own $HOME\UmicomLearning practice folder. Do not execute destructive commands in Umicom Framework or Umicom OS.

Our core distinction: Windows Terminal hosts a shell; PowerShell 7 (pwsh) is the shell; Git records versions locally; GitHub hosts repositories online; GitHub CLI (gh) connects you to GitHub.

This offline handbook includes Chapters 264–283, the beginner onboarding capstone, and optional Framework integration lessons at the end. Full C23 source, tests, instructor notes, video scripts and change manifest are in the accompanying Update 37 ZIP.

Chapter 264 — Open a terminal and choose the correct PowerShell

Bits to Banking · Absolute Beginner Course · Unit 1: Starting confidently
Time: 20–30 minutes · Requirements: a Windows 11 or Windows 10 computer; no developer account required.

Why start here?

Before we use GitHub, build Umicom Framework or learn C23, we need a reliable place to type instructions. This place is called a command-line shell. You type a command and press Enter. The computer runs it and displays a result or a useful error. A command is not something mysterious: opening a folder, listing files and asking for the computer’s name are ordinary examples.

The word terminal usually means the window that displays the shell. Windows Terminal is an application that can host several shells in tabs. PowerShell is one of those shells. Command Prompt (CMD) is another. On Linux, a terminal window commonly hosts Bash or another shell. A window and the programme running inside it are different things.

The Windows search screenshot

The screenshot above shows why new users can be confused. Windows PowerShell is the older Windows edition, normally version 5.1. PowerShell 7 is the newer cross-platform edition and starts with pwsh. Windows PowerShell ISE is an older editor for Windows PowerShell scripts; it is not the PowerShell 7 terminal we use in this course. Windows PowerShell (x86) is a 32-bit variant and is not appropriate for our default development setup. Developer PowerShell for VS 2022 preconfigures Visual Studio compiler tools; we do not need it for the initial lessons. A result labelled PowerShell may be the newer application, but always check the version rather than guessing from the icon.

Practice: open a shell from the Start menu

  1. Save any unsaved work in other programmes.
  2. Click the Start button, or press the Windows key on your keyboard.
  3. Type PowerShell into the search box. Do not type a command yet.
  4. If you have an entry called PowerShell 7 or PowerShell under Apps, select it. If you only see Windows PowerShell, open that for now; Chapter 265 shows how to install PowerShell 7.
  5. A window opens with a line ending in > (the prompt). That line is where the next command goes. Type the following without copying the word PS or any example prompt text:
Get-Location

Press Enter. You should see a path, for example C:\Users\Student. Yours will be different. A path tells you where you are in the folder system; it is not your GitHub identity.

Now check your shell version:

$PSVersionTable.PSVersion

If the major number is 7, you are using PowerShell 7. If it is 5, you are probably using Windows PowerShell 5.1. Both can run the basic commands in this chapter; for the remaining Windows lessons we prefer PowerShell 7.

Start PowerShell 7 explicitly

If PowerShell 7 is already installed, type this inside your current PowerShell window:

pwsh

A new PowerShell session starts. Run $PSVersionTable.PSVersion again to confirm version 7. If you see an error saying pwsh was not found, do not panic or start changing the PATH. The next chapter explains how to install it correctly. Use exit to leave the inner PowerShell session and return to the previous one.

Command Prompt, DOS and PowerShell: a useful comparison

cmd.exe (Command Prompt) looks familiar to people who used DOS. Both accept textual instructions, but modern CMD runs on Windows, not on MS-DOS. PowerShell also accepts commands, but returns structured objects for many operations and has different quoting and pipeline rules. For example, Get-Process returns process objects with names, IDs and memory properties; it is not merely a block of display text. Knowing CMD is helpful, but do not assume every DOS command works identically in PowerShell.

On Linux, open the application normally named Terminal, Konsole or GNOME Terminal. Type pwd and press Enter to show the current directory. Chapter 271 introduces Linux alongside the equivalent Windows operations.

Practice and review

Run Get-Location twice. Did your location change? Explain why not. Run $PSVersionTable.PSVersion and record whether you have version 5 or 7. Point at the screenshot and identify the terminal window, shell, older ISE and 32-bit shell concepts. Finally, close the window using its close button; it will not uninstall anything.

If something differs from the example: report the exact command and the error text. Do not run unknown administrative commands merely to make the display match another person’s computer.

Chapter 265 — Install PowerShell 7, Git, GitHub CLI and a text editor

Bits to Banking · Absolute Beginner Course · Unit 1
Time: 25–45 minutes plus downloads · Requirements: Windows with an internet connection; installation permissions may be required.

What each tool does

PowerShell 7 is the command-line shell in which we type instructions. Git records changes to local project files and lets you compare earlier versions. GitHub is a website that hosts Git repositories for sharing and collaboration. GitHub CLI (gh) is a command-line tool for your GitHub account: signing in, creating a repository and opening a browser page. Visual Studio Code is a text editor for source files; it is optional and does not replace Git. CMake, Ninja and GCC are build tools we will install later when needed.

A command beginning with winget asks Windows Package Manager to install software. A command beginning with git uses Git. The spaces and the two adjacent hyphens in --version are important. git - -version is not the same command as git --version.

Step 1 — Check the Windows package manager

Open PowerShell as in Chapter 264. Type:

winget --version

You should see a version identifier such as v1.x. The exact number changes as Winget is updated. If Windows says it cannot find winget, first check App Installer through Microsoft Store / your organisation’s IT support, or follow Microsoft’s official guide: https://learn.microsoft.com/windows/package-manager/winget/ . Do not download installers from unofficial advertising pages.

Step 2 — Install PowerShell 7

If you are currently in Windows PowerShell 5.1, you can use it to run this installation command:

winget install --id Microsoft.PowerShell --exact --source winget

Accept the installer prompts only after reviewing what is being installed. Modern releases can use MSIX; older installations may use MSI. This command does not remove Windows PowerShell 5.1. Close the old window, open PowerShell 7 from Start, and verify:

$PSVersionTable.PSVersion
pwsh --version

Microsoft’s official instructions: https://learn.microsoft.com/powershell/scripting/install/install-powershell-on-windows . If installation is restricted by your organisation, ask the administrator before proceeding.

Step 3 — Install Git and GitHub CLI

Enter one line, wait for it to finish, and only then enter the next:

git --version

If Git is missing, install it:

winget install --id Git.Git --exact --source winget

Check GitHub CLI:

gh --version

If it is missing:

winget install --id GitHub.cli --exact --source winget

Newly installed commands sometimes require a new terminal so Windows can refresh its PATH. Close and reopen PowerShell 7, then retry both version checks. Do not guess installation folders or edit system PATH as a first response.

Step 4 — Install an editor (recommended)

You can use Notepad if you prefer, but Visual Studio Code makes it easier to see project files and compare changes:

winget install --id Microsoft.VisualStudioCode --exact --source winget

Verify that its code launcher is available:

code --version

If the editor is installed but code is not found, open it from the Start menu; the command-line launcher may need to be added by the installer or a new session.

Step 5 — Find the command locations

Get-Command pwsh, git, gh | Select-Object Name, Source

Get-Command locates commands available to the current shell. Select-Object displays only the properties we asked for. Each row should show a name and a file location. The list can vary according to how software was installed, and an unavailable command may produce an error rather than a row.

Stop and verify

Record four facts in a text note: your PowerShell major version, Git version, GitHub CLI version and whether VS Code opens. Do not share authentication tokens or private configuration files in a classroom message. Installing Git does not create a GitHub account, sign you in, or create a repository; those are separate steps in Chapter 272.

Common problems: If Winget cannot find a package, check spelling and your network connection. If access is denied, review installation permissions. If the programme works from Start but not PowerShell, reopen PowerShell and try again. Avoid copying random installation scripts from the internet.

Chapter 266 — Find, create, read and organise files safely

Bits to Banking · Absolute Beginner Course · Unit 1
Time: 30–40 minutes · Requirements: PowerShell 7. Safety: all write operations stay in a new practice folder.

A folder is a location, not a Git repository

A drive is a storage location such as C:. A folder (directory) groups files and folders. A path describes a location such as C:\Users\Student\UmicomLearning\notes-practice. Get-Location tells you where PowerShell is currently working. Creating a folder does not automatically put it under Git version control; that happens only after git init in Chapter 273.

We will work below $HOME (your own account’s home directory) so you do not need administrator permissions or risk modifying a real Umicom checkout. In the examples, PowerShell resolves $HOME to your computer’s actual user directory. Do not copy another learner’s username into your commands.

Guided exercise: your first safe workspace

1. Ask where you are:

Get-Location

2. Make a dedicated folder for course work:

New-Item -ItemType Directory -Path "$HOME\UmicomLearning" -Force

You may also type mkdir "$HOME\UmicomLearning". mkdir is a convenient alias in PowerShell. We will use the full command when teaching specific options.

3. Enter the folder:

Set-Location "$HOME\UmicomLearning"

4. Check:

pwd

pwd is a short alias for Get-Location. The displayed path should end in UmicomLearning. If it does not, stop and correct the directory before writing files.

5. Create a practice project folder and enter it:

New-Item -ItemType Directory -Path ".\notes-practice" -Force
Set-Location ".\notes-practice"

6. Create a small Markdown document:

Set-Content -LiteralPath ".\README.md" -Value "# My first Umicom Notes project" -Encoding utf8

A .md file is a plain-text document written in Markdown, the format used for our learning pages. PowerShell has created a text file here; it has not created a PowerShell script.

7. List and read the new file:

Get-ChildItem
Get-Content -LiteralPath ".\README.md"

You should see README.md listed, followed by its heading when you run Get-Content.

8. Add another sentence:

Add-Content -LiteralPath ".\README.md" -Value "This is a safe local practice repository."
Get-Content -LiteralPath ".\README.md"

9. Open the document in an editor:

notepad ".\README.md"

You may use code ".\README.md" if VS Code is installed. Close the editor after saving; the file is still in the same folder.

Understand copying, moving and previewing deletion

Use a practice copy before testing rename or deletion operations:

Copy-Item -LiteralPath ".\README.md" -Destination ".\README-copy.md"
Get-ChildItem

To rename the copy:

Rename-Item -LiteralPath ".\README-copy.md" -NewName "README-backup.md"

Before removing anything, learn -WhatIf, which explains the action without doing it:

Remove-Item -LiteralPath ".\README-backup.md" -WhatIf

The file should still exist. Verify with Get-ChildItem. We deliberately do not run a real deletion in this first course. On a real source tree, an accidental recursive deletion could destroy uncommitted work that Git cannot restore.

Small terminal features that save time

You can often press Tab while typing a folder or command name to complete it. The Up Arrow recalls a recent command; always read it before pressing Enter again, especially if it modified files. Clear-Host clears the visible screen without deleting your files. Get-Help Get-ChildItem -Examples shows examples of a built-in command. If you start an unintended long-running command, Ctrl+C often requests interruption, but it cannot undo a command that has already changed the filesystem.

Get-Help Get-ChildItem -Examples
Clear-Host

The examples are for learning; you should not copy a help example that deletes or overwrites real project files without understanding it.

Relative and absolute paths

./README.md and .\README.md refer to the file in the current directory; .. means the parent directory. C:\umicom\Umicom-Bits2Banking is an absolute path. When a lesson says Set-Location, follow it before entering subsequent relative paths. The same command can operate on a completely different file if your current directory is wrong.

Check your understanding

Explain what pwd, Get-ChildItem, Set-Location, Get-Content and -WhatIf do. Why did we put the practice project under $HOME rather than altering the existing Umicom Framework directory? Write down one way to check your directory before using git add -A in the future.

Chapter 267 — Inspect Windows, the processor, memory and storage

Bits to Banking · Absolute Beginner Course · Unit 2: System administration
Time: 30 minutes · Requirements: a Windows computer and PowerShell. All commands are read-only.

What is system administration?

A system administrator keeps computers usable, secure, updated and recoverable. Before installing a compiler or investigating a failed build, a good administrator gathers evidence about the machine. The operating system is the software that manages programmes, memory, disks, accounts and devices. The CPU executes instructions; RAM holds temporary working data; storage retains files after power is removed.

We will use built-in Windows commands that report information without changing settings. You do not need to understand every reported property yet. Start by recognising the hardware categories and whether your machine has enough free space to complete a build.

Step 1 — Identify Windows and its architecture

Get-ComputerInfo | Select-Object WindowsProductName, OsVersion, OsArchitecture

Get-ComputerInfo collects details; Select-Object reduces the output to three columns. Look for 64-bit or x64, which matters when choosing a compiler. This query may take several seconds. Your Windows edition and version will differ from the instructor’s.

A shorter check is:

[System.Environment]::OSVersion.Version

The first command is preferable when you want the Windows edition and architecture together.

Step 2 — Read the processor and core count

Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors

Win32_Processor is a Windows management class. Cores are CPU execution resources. Logical processors are scheduling units visible to Windows; a processor may present more logical processors than physical cores. The name and numbers are not a benchmark and do not automatically prove that one machine is faster than another.

Step 3 — Check installed RAM

[math]::Round((Get-CimInstance Win32_ComputerSystem).TotalPhysicalMemory / 1GB, 2)

The result is a number in units that PowerShell labels with the 1GB binary constant (1,073,741,824 bytes). It is useful for planning how many builds or browser tabs you can run at once. Installed RAM is different from free RAM: Windows uses some memory for itself and running programmes.

Step 4 — View drives and free space

Get-PSDrive -PSProvider FileSystem

This displays accessible filesystem drives and the reported free and used capacity where available. Do not confuse the drive letter with the amount of free space. A low-space drive may cause CMake to fail while producing many temporary .obj files.

For an easy-to-read summary of fixed local disks, try:

Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
    Select-Object DeviceID, VolumeName, Size, FreeSpace

The second command produces byte counts; Windows settings can show friendlier units. A shared or network drive may be reported differently, so confirm its availability before choosing it as a build directory.

Step 5 — Locate programmes the shell can run

Get-Command pwsh, git, gh, cmake, ninja -ErrorAction SilentlyContinue |
    Select-Object Name, Source

A missing row means the command was not found in the current command search path; it does not prove that the software has never been installed. Reopen PowerShell after installation. Later, the course shows exact GCC paths for MSYS2 UCRT64.

Practice record

Create a private notes page with your Windows edition, CPU name, RAM, free space on your work drive and which tools are available. Do not post machine serial numbers, account IDs or security configuration in a public issue. The class can compare broad CPU architecture and build capacity without collecting unnecessary personal information.

Review: Why is free disk space relevant to CMake? What is the difference between RAM and storage? Why might Get-Command git produce no result just after installing Git? Why should every diagnostic begin with a read-only check?

Chapter 268 — Users, administrators, permissions and responsible changes

Bits to Banking · Absolute Beginner Course · Unit 2
Time: 25–35 minutes. All mandatory exercises are read-only.

One computer can have more than one authority level

A user account identifies the person or service acting on the computer. A permission controls which resources that account can read or change. An administrator can perform some system-wide changes that a standard user cannot. On Linux, a command prefixed with sudo can run with elevated privileges if the account is authorised. That extra authority is not required for browsing documentation, editing files in your home directory, creating a practice Git repository or running most learning tests.

Treat administrator privileges as a controlled exception, not a shortcut for fixing errors. A compiler build that unexpectedly requires administrator access may simply be writing to the wrong folder. First correct the workspace location; do not disable security controls.

Identify the current account

In PowerShell:

whoami

The output will normally contain a computer or domain name and a user name. That is not your GitHub account and does not need to match your Git author name. You can learn more about the current process’s Windows access token using:

whoami /groups

This produces a long list of Windows groups; some groups may be disabled for the current process. Do not assume membership means all privileges are currently enabled.

Inspect permissions on your practice folder

Get-Acl "$HOME\UmicomLearning" | Select-Object Path, Owner

An ACL (access-control list) records permissions associated with a resource. We are displaying the owner rather than modifying any ACL. Windows can inherit permissions from parent directories; changing them without understanding inheritance can block legitimate access.

Why we avoid “Run as Administrator” for ordinary lessons

The screenshot in Chapter 264 shows a Run as Administrator option. It starts a shell with higher privileges after approval. Do not use it for Git commits or normal C23 builds. Elevated shells are more dangerous because a mistaken path can affect the whole computer. Some installations may legitimately prompt for elevation; follow the signed installer and your organisation’s policy, then return to an ordinary PowerShell session.

Think about Git access separately

Git can record local commits without connecting to GitHub. GitHub authentication allows the CLI to act on an online account. A repository permission determines whether an account may push to a particular remote repository. Signing into GitHub does not grant permission to push into every Umicom Foundation repository.

In future chapters, avoid putting passwords, API keys, access tokens or personal identifiers in Markdown files. A .gitignore file may keep a local file out of new commits, but once a secret has already been committed, ignoring the file does not remove it from history.

Safe operating routine

Before changing any system or repository setting: identify the current folder; state what should change; inspect the current state; make a small change; verify the result; record how to reverse it. On financial and operating-system projects, additionally identify who owns the mutable state and what audit evidence will be retained.

Practice: Explain the difference between a Windows user, local administrator, Git commit author and GitHub account. Check your current account and folder owner. No permissions need to be changed.

Chapter 269 — Inspect processes, services and Windows event logs

Bits to Banking · Absolute Beginner Course · Unit 2
Time: 25–40 minutes · Mode: read-only observation.

A programme and a process are not the same thing

A programme is executable code stored on disk. A process is a running instance with its own identifier (PID) and resources. Opening two windows of an application can create two processes or one process with multiple windows, depending on the application. A service is software supervised by the operating system for ongoing work; not every process is a service.

When Umicom Studio appears not to open, first distinguish “the executable did not start” from “the process started then exited” and “the process runs but the window is hidden”. A successful compile proves none of these runtime states.

Step 1 — List running processes

Get-Process | Select-Object -First 10 Name, Id, CPU

The results are a snapshot; processes start and stop constantly. CPU is often accumulated processor time, not a live percentage. To examine one familiar application, replace the name if necessary:

Get-Process -Name explorer -ErrorAction SilentlyContinue |
    Select-Object Name, Id, WorkingSet64

-ErrorAction SilentlyContinue hides a simple “not found” error when Explorer is not running, but do not use it to suppress a real failed build or test.

Step 2 — List services

Get-Service | Select-Object -First 12 Name, Status, DisplayName

A service can be Running, Stopped or in a transitional state. A stopped service is not always an error; some run only when required. Do not start or stop unfamiliar services in a classroom exercise. For a named service you are responsible for, consult its approved administration guide before changing it.

Step 3 — View a few recent events

Get-WinEvent -LogName System -MaxEvents 5 |
    Select-Object TimeCreated, Id, LevelDisplayName, ProviderName

Windows records events from many providers. A warning in Event Viewer does not necessarily explain an unrelated Umicom crash. Compare the timestamp, application name and exact event message before drawing conclusions. Some logs require permissions; in that case, do not bypass your organisation’s access policy.

Step 4 — Relate to Umicom builds

A CMake configure step prepares the build plan. Ninja compiles and links binaries. CTest launches registered test programmes. Windows then starts the completed executable. If a programme never appears, inspect the earliest failing stage: compiler output, link error, missing executable or runtime crash. Keep exact error text and paths; they are the evidence a developer needs.

Practice: List ten processes, ten services and five recent system events. Name one difference between a warning, a process exit and a build error. Record what each command can prove and what it cannot prove.

Chapter 270 — Networks, DNS, HTTPS and safe connection checks

Bits to Banking · Absolute Beginner Course · Unit 2
Time: 30 minutes. All examples send ordinary diagnostic queries; use networks you are authorised to access.

Why GitHub depends on networking

When you run git commit, Git stores a new local revision; the internet is not required. When you run git push, Git contacts a remote server, usually over HTTPS or SSH, and asks it to accept commits. When you run gh auth login, you authorise the GitHub CLI to act on an account. These actions depend on network availability, credentials and repository permissions, but they are still three different operations.

An IP address identifies a network endpoint. DNS maps human-readable names such as github.com to addresses. A port identifies a service on a host; HTTPS commonly uses TCP port 443. HTTPS protects data in transit using TLS. None of these prove that your GitHub account has permission to push to a particular repository.

Step 1 — Inspect local network settings

Get-NetIPConfiguration | Select-Object InterfaceAlias, IPv4Address, IPv4DefaultGateway

The output depends on your adapters, including VPNs and Wi-Fi. Avoid sharing complete local network details publicly when they are not needed.

Step 2 — Ask DNS for an address

Resolve-DnsName github.com

You may see several records, including IPv4 and IPv6 addresses. The particular addresses can change. A DNS response means the name resolved; it does not prove that GitHub authentication works.

Step 3 — Test the HTTPS port

Test-NetConnection github.com -Port 443

The field TcpTestSucceeded indicates whether the TCP connection was established. A failure may mean loss of internet access, a proxy, a firewall or temporary service unavailability. It does not necessarily mean GitHub is down, and a success does not prove that git push will be authorised.

Step 4 — Distinguish local and remote failures

If git --version works but git push fails, check the remote and authentication:

git remote -v
gh auth status

Run these inside your intended Git repository. A message saying “not a git repository” is not a network error; it means you are in the wrong folder or have not run git init.

Concept-to-evidence table

Question Appropriate first observation
Is Git installed? git --version
Is GitHub’s hostname resolving? Resolve-DnsName github.com
Can I connect to HTTPS? Test-NetConnection github.com -Port 443
Is GitHub CLI authenticated? gh auth status
Which remote repository does Git use? git remote -v
May I push to that repository? Repository permissions and actual push result

Practice: Explain why successful DNS, TCP, authentication and repository permission are separate facts. Do not change proxy, firewall or credential settings during this initial exercise.

Chapter 271 — Launch a Linux terminal and understand the same ideas

Bits to Banking · Absolute Beginner Course · Unit 2
Time: 30–45 minutes · Applies to: common desktop Linux distributions. Installation commands differ by distribution.

Same purpose, different shell

On Windows our principal shell is PowerShell 7. On Linux a common choice is Bash, displayed in a terminal such as GNOME Terminal or Konsole. You still type commands and press Enter. The important concepts remain the same: current directory, files, processes, permissions, storage and networking. The syntax is not identical: Get-Location is a PowerShell command; pwd is a standard Unix-style command. Git, CMake and Ninja use largely similar command names on both operating systems.

Step 1 — Open the terminal

Open your desktop’s Applications menu, search for Terminal, then start it. Many distributions also support Ctrl+Alt+T, but do not assume that shortcut works everywhere. You should see a prompt, commonly containing a username and current directory.

pwd

This prints your current working directory, typically /home/student. On Linux, forward slashes / separate path segments. Unlike Windows, a path generally does not start with a drive letter.

Step 2 — Work in a safe course folder

mkdir -p "$HOME/UmicomLearning/notes-practice"
cd "$HOME/UmicomLearning/notes-practice"
pwd
ls -la

mkdir -p creates the requested folder and missing parents. cd changes directory. ls -la shows detailed entries including dot-prefixed hidden files. Paths are generally case-sensitive: README.md and readme.md may be different files.

Create the same simple text document as the Windows course:

printf '%s\n' '# My first Umicom Notes project' > README.md
cat README.md

Warning: > redirects output and overwrites the named file. We use it only inside a disposable new practice folder. Do not run this command against a real source file that may contain important content. Prefer a text editor for ongoing changes.

Step 3 — Ask about the operating system and hardware

uname -a
lscpu
df -h
free -h

uname reports kernel information. lscpu describes processor architecture and CPU topology. df -h reports filesystem capacity. free -h reports memory. Exact options and results depend on the distribution and installed tools. For an account name, run whoami; for identity and groups, run id.

Step 4 — Check essential development commands

git --version
cmake --version
ninja --version
gcc --version

If a command is missing, use your distribution’s official package manager instructions rather than pasting an unfamiliar curl | bash command from a website. On Debian- or Ubuntu-based systems, packages such as git, cmake, ninja-build and build-essential are often provided through APT; Fedora and other distributions use different tools. Installation needs the appropriate account permissions and update policy.

Chapter 272 — Configure Git and sign in to GitHub

Bits to Banking · Absolute Beginner Course · Unit 3: Version control
Time: 25–40 minutes · Requirements: Git and GitHub CLI installed; a GitHub account you control.

Three identities you must not confuse

Your computer login gives you access to Windows or Linux. Your Git author identity is the display name and email stored alongside new Git commits. Your GitHub account is your online account with permissions to hosted repositories. These can have different names. Git commit author information is not itself proof that the person was authenticated to GitHub; authentication is a separate step.

Before this lesson, sign up at the official GitHub website if you do not already have an account: https://github.com/signup . Confirm your email according to GitHub’s instructions. Choose a strong, unique password and enable multi-factor authentication. Never send a password, authentication token or recovery code to an instructor.

Step 1 — Check that Git and GitHub CLI work

Open PowerShell 7, then type each command on its own line:

git --version
gh --version

Both should print version information. If either says it cannot find the command, revisit Chapter 265; authentication cannot repair an installation problem.

Step 2 — Configure the name recorded in future commits

git config --global user.name (Read-Host "Your display name")

After pressing Enter, PowerShell asks for a name. Type the name you want on your commits and press Enter. Do not type your name into the source code or the parentheses; Read-Host collects the answer for this one command. This operation changes Git’s global configuration for your account; it does not register a GitHub username.

Next configure an email associated with your GitHub account, or your GitHub-provided private no-reply email if you prefer privacy:

git config --global user.email (Read-Host "Your verified Git commit email")

Do this once, not three times. Repeating the same command is unnecessary. Be aware that commits can make the configured email visible in repository history; use an appropriate privacy setting and never use somebody else’s address without authorisation.

Step 3 — Confirm what Git stored

git config --global --get user.name
git config --global --get user.email

You should see the values you entered. If they are wrong, rerun only the relevant git config command. Global configuration is usually stored in a configuration file in your home folder; you should not need to edit it manually.

Step 4 — Sign into GitHub CLI

First ask whether you are already authenticated:

gh auth status

If it reports you are not signed in, start the guided login:

gh auth login

Choose GitHub.com when asked for the host. Follow the prompts, normally selecting HTTPS for Git operations and Login with a web browser. GitHub CLI may display a short one-time device code and open a browser where you confirm it. Use the official GitHub login page, not a link supplied by an unknown person. After finishing, return to PowerShell and run gh auth status again. This command checks which account gh can currently use; it does not prove your permission to every repository.

Step 5 — Understand what was not done

You have not created a local Git repository, made a commit, or uploaded any files. You have installed tools, given future commits an author label and authorised a CLI to communicate with GitHub. That separation helps diagnose later errors.

Security note: GitHub CLI normally stores credentials through the available operating-system credential store, but storage behaviour depends on the environment. Do not display or share saved tokens. Review the official manual if your account is managed: https://cli.github.com/manual/gh_auth_login .

Practice: Explain the differences between Git identity, GitHub authentication and repository write permission. Record the output of git --version, and state whether gh auth status succeeds, without posting any secret values.

Chapter 273 — Create a local Git repository and make two commits

Bits to Banking · Absolute Beginner Course · Unit 3
Time: 35–50 minutes · Mode: local, no internet needed. The exercise uses your own practice folder only.

What is version control?

Imagine editing the Umicom Notes guide each day. Without version control you might copy it into files called README-final.md, README-final-2.md and README-final-really.md, then lose track of which one is correct. Git records changes as commits with identifiers, authors and messages. You can inspect the history and compare versions without making a copy of the entire project each time.

A repository is a folder that Git tracks. A working tree is the set of files you are editing. The staging area records exactly which changes you intend to put in the next commit. A commit creates a history entry from those staged changes. A branch, such as main, names a line of history.

Step 1 — Go to your practice Notes project

Set-Location "$HOME\UmicomLearning\notes-practice"
Get-Location
Get-ChildItem

If the folder is missing, return to Chapter 266 and create it. You should see README.md. Do not run these steps in C:\umicom\Umicom-Applications, framework, umicomOS or any real shared project.

Step 2 — Start local version control

git init -b main

git init creates a hidden .git directory holding local history and configuration. -b main makes the initial branch main. This is an ordinary local operation. It does not create a repository on GitHub.

git status

Git should report that you are on main and that README.md is not yet tracked. The exact message may differ if you previously practised here.

Step 3 — See which file would enter history

git add README.md
git diff --cached
git diff --cached --check

git add copies the current file content into the staging area. git diff --cached displays the proposed commit changes; --check reports certain whitespace problems. Confirm that the staged file contains only the text you expect.

Now commit:

git commit -m "docs: add Notes project introduction"

The message describes what changed, not whether the author is pleased with it. The exact commit identifier is not important; every learner will get a different one.

Step 4 — Edit and commit again

Add-Content -LiteralPath ".\README.md" -Value "The Notes project will later be built in C23."
git diff
git status

git diff now shows the unstaged edit. When you are ready, stage everything in this practice repository:

git add -A
git diff --cached --check
git diff --cached --stat
git commit -m "docs: describe the future C23 Notes lab"

git add -A includes file additions, edits and deletions throughout the current repository. It is convenient only after inspecting git status and verifying you are in the intended repository. The command does not create a commit by itself.

Step 5 — Read your local history

git log --oneline -5
git status
git branch --show-current

You should see two commits and the branch main. If Git says “nothing to commit, working tree clean”, that is expected. It means the files on disk match your latest local commit; it does not mean anything has been uploaded online.

Exercise: observe the three locations

Change one word in README.md using Notepad, then run git diff. Stage it and compare git diff with git diff --cached. What changed? Did the commit history grow merely because you staged it? Finish with an explanatory commit. Do not use reset --hard, clean -fd, force push, or deletion commands while learning.

Common issue: “Author identity unknown” means the name or email is not configured. Return to Chapter 272. “Not a git repository” means you are outside your intended folder; use Get-Location.

Chapter 274 — Publish your first repository to GitHub with gh

Bits to Banking · Absolute Beginner Course · Unit 3
Time: 25–40 minutes · Requirements: a local notes-practice repository with at least one commit, GitHub CLI authentication and internet access.

Git and GitHub do different jobs

Git has already saved your Notes history locally. GitHub is a hosting service where you can place a copy of that history. A remote is a named address for another repository, often called origin. Push sends your local commits to the remote. Fetch downloads information about remote history without automatically changing your working files. The repository can remain private while you practise.

Step 1 — Check the local project

Set-Location "$HOME\UmicomLearning\notes-practice"
Get-Location
git status
git branch --show-current
git log --oneline -3

Before continuing, make sure the branch is main, there is at least one commit, and you are not in a real Umicom shared repository. If git status shows uncommitted work, review and commit it first or leave it uncommitted intentionally; the command below only publishes commits.

Step 2 — Check authentication

gh auth status

If not authenticated, run gh auth login and follow Chapter 272. A GitHub account may be permitted to create private repositories even if it cannot write to an organisation-owned repository.

Step 3 — Create the remote and push the current commits

gh repo create notes-practice --private --source . --remote origin --push

Read this command from left to right: gh repo create requests a new online repository; notes-practice names it; --private limits its visibility; --source . means this local directory; --remote origin adds an address called origin; and --push uploads the existing commits. It does not change the project’s C23 code.

Before pressing Enter: confirm again that you are inside notes-practice. If the repository already exists online or origin is already configured, stop and inspect instead of running the create operation repeatedly.

Step 4 — Confirm what was published

git remote -v
git status
gh repo view --web

git remote -v shows the remote address. gh repo view --web opens the repository in your browser. You should find your README.md and recent commits. If the browser shows a private repository, that is expected. Do not change it to public merely to make the class exercise work.

Step 5 — Make another safe change and upload it

Add-Content -LiteralPath ".\README.md" -Value "Version control preserves our editing history."
git status
git diff
git add -A
git diff --cached --check
git diff --cached --stat
git commit -m "docs: explain why Git history matters"
git push origin main

Only the last command sends the new commit to GitHub. If it reports “Everything up-to-date”, there may be no unpublished commit; verify with git log. If it reports “non-fast-forward”, do not force push. The remote may contain newer commits; inspect git fetch origin and git log --oneline --left-right HEAD...origin/main before deciding what to do.

Security and common failures

Never commit .env credential files, passwords, private keys or access tokens. Private repositories are still subject to account access, backups and permissions. If gh asks you to authorise a browser login again, verify it is the official GitHub flow. If the repository is owned by an organisation, its policies may restrict creation or pushing.

Practice: Explain what origin is, why --push sends only committed content and what --private changes. Compare your local git log -3 to the History/Commits view in the browser.

Work on a copy, not someone else’s live folder

When you clone a repository, Git downloads its history into a new local folder. You can read code and lessons without editing the online original. Chapter 276 — Install the C23 compiler, CMake and Ninja on Windows

Bits to Banking · Absolute Beginner Course · Unit 4: Building real software
Time: 35–70 minutes depending on downloads · Requirements: Windows x64, internet access, installation permissions as required.

Three tools, three responsibilities

A compiler translates C source into object code. GCC is one compiler we use for C23. A build configuration tool, CMake, reads CMakeLists.txt and prepares build instructions. Ninja executes those build instructions efficiently. A compiler is not a text editor; an editor is where we write code, and the compiler is what checks and translates it.

We use MSYS2 UCRT64 on Windows because it provides a consistent native GCC toolchain and its dependencies. UCRT64 means that the resulting Windows programmes use Microsoft’s Universal C Runtime. Do not confuse an MSYS2 UCRT64 shell with the PowerShell 7 shell; we may install tools in one environment and invoke them from the other.

Step 1 — Check existing installations

Open PowerShell 7:

cmake --version
ninja --version

If either command is not found, that is not a code error; we need to install the tool. Check whether MSYS2 exists at the common default path:

Test-Path "C:\msys64\ucrt64\bin\gcc.exe"

True means that exact file exists; False means it does not. The file can be installed elsewhere, so this test is not a universal MSYS2 detector.

Step 2 — Install MSYS2

Open the official site https://www.msys2.org/ and use its documented Windows installer. The common installation folder is C:\msys64, which we use in later examples. If your institution manages software installation, follow its policies.

After installation, open MSYS2 UCRT64 from the Start menu (not the generic MSYS shell). It uses an environment appropriate for building native Windows applications. If the package database prompts you to update, follow the official MSYS2 update instructions, closing and reopening the UCRT64 terminal when told to.

Inside the MSYS2 UCRT64 terminal, run:

pacman -Syu

Follow prompts; close and reopen the required MSYS2 terminal if the update tool requests it, and repeat updating as the official MSYS2 documentation requires. Then install GCC, CMake and Ninja packages for UCRT64:

pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja

pacman is an MSYS2 package manager, not a normal PowerShell command. Do not enter these commands in the wrong shell.

Step 3 — Return to PowerShell and check the actual executables

Close the MSYS2 terminal after installation. Open PowerShell 7 and run:

& "C:\msys64\ucrt64\bin\gcc.exe" --version
& "C:\msys64\ucrt64\bin\cmake.exe" --version
& "C:\msys64\ucrt64\bin\ninja.exe" --version

The & is PowerShell’s call operator; it runs the quoted executable path. Simply writing "C:\msys64\ucrt64\bin\gcc.exe" displays a string instead of executing the programme. The versions may differ from your teacher’s versions.

For the current PowerShell window only, place UCRT64 tools at the front of the command search path:

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

This is an interactive environment setting, not a .ps1 implementation script. It lasts for that PowerShell process and children, not permanently for the whole computer. Now gcc --version, cmake --version and ninja --version should resolve to the UCRT64 versions. Get-Command gcc,cmake,ninja | Select-Object Name,Source confirms which executables were selected.

C23 language support

Older compilers may recognise an earlier C language standard but not ISO C23. Our native laboratory requests C23 through CMake. If configure says the compiler does not support the required standard, check gcc --version, verify that the UCRT64 compiler was selected, and update through the supported MSYS2 package manager rather than changing source requirements to an older dialect.

Practice: Explain which tool compiles, which configures and which executes the build plan. Record the actual paths and versions without guessing them. No code changes are needed yet.

Chapter 277 — Build and test a real C23 Umicom Notes programme

Bits to Banking · Absolute Beginner Course · Unit 4
Time: 45–65 minutes · Source: labs/native/contributor-notes. This is a professional but intentionally small teaching laboratory.

Start with a useful application, not a meaningless greeting

Our first compiled example is a simple Umicom Notes component. It can add, read and update short notes held in memory. It helps a new contributor understand source files, header contracts, libraries, executables and tests. It does not save notes to disk and does not replace the production document services in Umicom Framework. A banking or financial programme would additionally require durable storage, authorisation, audit, error recovery and domain controls.

Step 1 — Open the correct repository and check tools

This chapter assumes you have already downloaded and review-merged Update 37 into your Bits2Banking repository as described in the batch’s root-level build guide.

Set-Location "C:\umicom\Umicom-Bits2Banking"
Get-Location
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
gcc --version
cmake --version
ninja --version

Do not run the configure command from an arbitrary folder and then assume its relative paths will work. If you are using a personal clone elsewhere, change the Set-Location path to the exact location of that clone.

Step 2 — Read the four core files

Open labs/native/contributor-notes/notes.h. A header publishes function declarations and types. notes.c defines the functions. main.c is the runnable example. test_notes.c contains independent checks. CMakeLists.txt describes how the compiled parts fit together.

Read the public function declaration:

BtbNotesResult BtbNotesAdd(BtbNoteStore *store,
                           const char *text, uint32_t *outId);

This function receives a caller-owned Notes store, copies a text value into it, and provides the new identifier through an output pointer. The result tells the caller whether the operation succeeded. An invalid or full request must not silently change the existing Notes data.

Step 3 — Configure the build

Copy this command into PowerShell as one complete command (the backticks continue a line):

cmake -S ".\labs\native\contributor-notes" `
    -B ".\output\learning-build\contributor-notes" `
    -G Ninja `
    -DCMAKE_C_COMPILER="C:\msys64\ucrt64\bin\gcc.exe" `
    -DBUILD_TESTING=ON

-S points to source, -B to the generated build directory. -G Ninja selects the generator. -DCMAKE_C_COMPILER chooses the actual compiler. -DBUILD_TESTING=ON registers the tests. The build directory is separate from the source so we do not scatter object files through the lessons.

Step 4 — Compile and test

cmake --build ".\output\learning-build\contributor-notes" --parallel 2

The compiler converts the C23 files into object files. The linker makes a library and two programmes: a demonstration and a test runner. A successful build does not guarantee correct behaviour, so run CTest:

ctest --test-dir ".\output\learning-build\contributor-notes" --output-on-failure

Expected: 8/8 tests passing, including add, update, too-long input, capacity, missing record, invalid argument, copied ownership and the demo. This count is for the default standalone lab; an optional Framework SDK example can add another test if enabled.

Step 5 — Run the programme

& ".\output\learning-build\contributor-notes\btb-contributor-notes-demo.exe"

It should print two contributor Notes. The changed text of the first note demonstrates an edit. When the programme exits the notes disappear, because they were never written to permanent storage.

Step 6 — Safe code exploration

Make a reviewed copy of the source if necessary. Edit only the first note text in main.c, leaving function signatures unchanged. Rebuild; notice which C file was recompiled. Rerun CTest and the programme. Compare with Git using git diff -- labs/native/contributor-notes/main.c, and do not accidentally stage changes to unrelated files. If you want to return to the delivered version, use your editor’s undo or Beyond Compare review rather than forcing a reset.

Review: What is the difference between a .h file and a .c file? Which stage creates the .exe? Why does an output pointer need a validity check? What does 8/8 passing establish, and what does it not establish about saving bank records?

Chapter 278 — Read errors, identify the failing stage and preserve your work

Bits to Banking · Absolute Beginner Course · Unit 4
Time: 30–45 minutes. Focus on observation and evidence before changing anything.

A useful error is not a personal failure

A failed command is information. It tells you which step was attempted and what went wrong. The quickest reliable approach is not to paste a collection of repair commands; it is to identify the first failed stage, preserve the current state and change one thing at a time.

For a native Umicom learning project, there are four important stages: configure → compile/link → test → run. An error in one stage can prevent later stages from starting. If Ninja reports “file not found”, the earlier CMake configuration or source path may be wrong. If CTest says “Not Run”, that is not a test pass; the requested executable may not have been built.

Checkpoint A — The wrong folder

If PowerShell shows Cannot find path or Git says not a git repository, first check:

Get-Location
Get-ChildItem

Only then run Set-Location to the correct repository. Never rely solely on the text of an example prompt copied from a website: it may reflect a different computer.

Checkpoint B — A command is missing

If gcc, cmake, ninja, git or gh is not recognised:

Get-Command git, gh, cmake, ninja, gcc -ErrorAction SilentlyContinue |
    Select-Object Name, Source

For the UCRT64 compiler specifically:

Test-Path "C:\msys64\ucrt64\bin\gcc.exe"

Do not guess PATH changes before verifying the installation. Use the documented installation method and reopen the shell.

Checkpoint C — A compiler or linker error

For compiler output, read the first real error, including the filename, line, column and message. A later wall of dependent errors may be caused by the first missing declaration. A warning does not always stop compilation, but should be reviewed rather than ignored. A linker error such as an undefined reference usually means a declared function was not found in a linked object or library; it is not automatically a missing header.

Umicom Framework already provides shared diagnostic parsing through umi_build_parse_diagnostic_line and related APIs. Our classroom exercise does not introduce another production compiler parser.

Checkpoint D — A test failed or did not run

ctest --test-dir ".\output\learning-build\contributor-notes" -N
ctest --test-dir ".\output\learning-build\contributor-notes" --output-on-failure

-N lists registered tests without running them. It is useful before deciding whether the tests were configured and built. A Not Run result is incomplete evidence; reconfigure/build before attempting to interpret it as a functional failure. An actual assertion failure indicates a programme ran but did not meet its expected contract.

Checkpoint E — Git refuses a push or submodule update

Run read-only inspections first:

git status
git branch --show-current
git log -1 --oneline
git remote -v

Inside a parent Umicom OS repository, framework is a submodule, possibly checked out at a detached HEAD. Its working tree may contain modified or untracked files. Preserve those files before synchronising a submodule. Read the earlier Chapters 184–195, 260 and the Framework-owned submodule policy before changing a real repository.

Prohibited shortcuts for novice troubleshooting: git reset --hard, git clean -fd, unreviewed git stash pop, git push --force, repository mirroring with deletion and unverified installer scripts. These can destroy uncommitted or valuable work.

How to ask for useful help

Supply the exact command, full error text, operating system, relevant tool versions, current folder, and whether there are uncommitted changes. Do not share private account tokens or security credentials. One focused error report is better than a summary saying “it doesn’t work”.

Practice: In your Notes lab, distinguish a configuration error, a compilation error, a CTest failure and a Git remote permission error. Explain what evidence you would collect for each without performing a destructive repair.

Evidence to retain: the configure result, build outcome and test count; record failures accurately rather than editing the report to show green results.

Part D — Safety and communication (20 points)

  1. Explain why normal learning commands should not require Run as Administrator.
  2. Distinguish the system login, Git author and GitHub account.
  3. Explain what an upstream Git repository is and why you cannot push to every repository you can clone.
  4. Explain the danger of git add -A when run in the wrong folder.
  5. Describe the safe first response to a detached HEAD or a submodule conflict.

Success standard: 80/100 with no safety-critical misunderstanding, or a reviewed resubmission of the affected section. Instructors should value accurate failure reporting over a falsely claimed successful build.

Chapter 280 — Use Umicom Framework’s native repository verification

Bits to Banking · Optional Advanced Unit · Git and Framework integration
Time: 35–50 minutes · Prerequisite: Chapters 272–279 and a real Umicom checkout that you are authorised to inspect.

Why we do not invent another Git automation script

Umicom Framework already contains native repository and version-control capabilities. Its built umicom command includes repository verification and controlled gitlink locking. A separate PowerShell script that parses Git output, stages submodules or constructs Git commands would duplicate this reusable implementation and introduce an additional maintenance risk. PowerShell remains useful for typing individual build and Git commands interactively; it does not own Umicom repository functionality.

Important distinction: repo verify previews actions; repo lock can stage a gitlink, changing the parent’s Git index. Neither command fetches remote commits, commits a repository, pushes to GitHub or proves that any GUI or OS boot works.

Step 1 — Know the actual repository layout

An Umicom Applications checkout may have framework/ as a submodule. Umicom OS also has a framework/ submodule pointing to the same canonical Framework repository, but each parent records its own tested revision. The Kernel is independent and does not use a Framework submodule in the same way. Do not copy Framework source files between the two checkouts to synchronise them.

Step 2 — Inspect, without changing anything

Open PowerShell, then:

Set-Location "C:\umicom\Umicom-Applications"
Get-Location
git status
git branch --show-current
git submodule status framework
git -C ".\framework" status --short
git -C ".\framework" rev-parse HEAD

If any output suggests local modifications, an unknown branch or unpublished changes, stop. Preserve the source and ask for a review before switching revisions. The parent Git history and submodule history are not the same.

Step 3 — Run Framework-owned read-only verification

If your Framework native CLI has already been built, locate it at your actual build path. For the established Applications build preset, a common path is:

$umicom = "C:\umicom\Umicom-Applications\build\windows-ucrt64-all-debug\bin\umicom.exe"
Test-Path $umicom

Continue only if the result is True and the binary is the reviewed tool from your own build:

& $umicom repo verify .

This operation reports the intended gitlink state without staging it. Read every warning. If the executable is missing, build the native Framework tool through your approved CMake preset rather than downloading an unknown replacement.

Step 4 — Understand the write boundary (do not execute in this exercise)

The corresponding staged operation is:

# For an authorised, reviewed integration AFTER full build and tests only:
# & $umicom repo lock .

The leading # makes these lines comments so they will not change your repository when pasted. Actual release work requires separate evidence that the intended Framework commit has been built and tested with the parent application. Review git diff --cached --submodule=log before committing. The project owner decides when to stage and publish the updated pointer.

Read Git’s recorded pointer

git ls-files --stage framework

A submodule entry uses mode 160000 and stores a commit identifier. That identifier is not a copy of Framework source. It is a reference to a commit in a separate repository. Checking out a newer Framework commit inside the child does not automatically update and publish the parent pointer.

Review: Why is the native repo verify preferable to a new script? What does repo lock change? What must pass before a parent gitlink is published? What does mode 160000 mean?

Chapter 281 — Call the existing Framework build planner from C23

Bits to Banking · Optional Advanced Unit · Native architecture
Time: 40–60 minutes · Prerequisite: working C23 toolchain and understanding of public interfaces.

Framework capability first

Before adding application code, search Umicom Framework for a suitable public contract. For deciding which applications and tests may be affected by changed files, Framework already provides UmiBuildAutomation in include/umicom/build/automation.h. It understands scopes, changed paths, shared providers and consumers, and action categories including configure, build, test and documentation. Our educational repository must reuse this component rather than copy its implementation.

The optional labs/native/contributor-notes/framework_planner_example.c contains a real consumer of the public Framework API. It does not implement Git, a compiler parser or a competing planner.

A controlled fictional example

Imagine a changed public Framework header. We register a Framework scope as a shared provider, and a Notes application scope as a consumer. We then provide a fictional changed path and ask Framework to produce its plan. The model should select the direct Framework scope and the inherited Notes consumer.

UmiBuildAutomation *planner = NULL;
UmiBuildAutomationChange changedFile;

if (umi_build_automation_create(&planner) != UMI_STATUS_OK) {
    /* Report unavailable planning resources to the caller. */
}
/* Scope registration and cleanup are shown in framework_planner_example.c. */
umi_build_automation_change_init(&changedFile,
    "framework/include/umicom/build/automation.h", 0);

The complete source handles failures, registers scopes, evaluates the changes and destroys the Framework-owned coordinator. Read the actual file for the complete programme before compiling it. Its input paths are fictional training values, not an observed Git working tree. A selected test is a plan, not a passed test.

Build it only with a compatible installed SDK

The standard beginner Notes build does not require Framework. To enable the optional example, you must have an installed Framework CMake package exporting Umicom::build. Replace the placeholder below with an installation prefix that actually exists on your computer:

Set-Location "C:\umicom\Umicom-Bits2Banking"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S ".\labs\native\contributor-notes" `
    -B ".\output\learning-build\contributor-notes-framework" `
    -G Ninja `
    -DCMAKE_C_COMPILER="C:\msys64\ucrt64\bin\gcc.exe" `
    -DBUILD_TESTING=ON `
    -DBTB_ENABLE_FRAMEWORK_PLANNER_EXAMPLE=ON `
    -DCMAKE_PREFIX_PATH="C:\ACTUAL\FRAMEWORK\INSTALL\PREFIX"

Do not run this with the placeholder unchanged. The course package does not claim the SDK is installed or that the optional target was tested on your machine. When configuration succeeds, run cmake --build and ctest --test-dir against that separate build directory.

Architectural discussion

Framework’s public ABI is the boundary. The Notes application only prepares typed inputs and reads the returned plan; it does not access internal src/build/automation.c state. Studio, Trader, TMS and OS have separate verification obligations. If your install exports different targets or an incompatible API, record the mismatch and consult the matching Framework revision rather than copying its source into the learning lab.

Review: What is an API consumer? Why is a selected test not a passed test? Why does an optional installed SDK target protect the standalone beginner build?

Chapter 282 — Select native tests and record what actually ran

Bits to Banking · Optional Advanced Unit · Build and test engineering
Time: 30–45 minutes · Requirements: configured contributor-notes CMake build.

Not every test is relevant to every source change

A contributor who edits a Markdown learning page needs content and link checks. Someone who changes notes.c must rebuild and run Notes tests. A change in a shared Framework header may require dependent application tests and packaging checks. Umicom Framework already provides the production build-automation planning service. CTest is one of the tools that actually executes registered tests.

We first learn how to run a targeted set of tests without confusing “selected” with “passed”.

Step 1 — Confirm configuration

Set-Location "C:\umicom\Umicom-Bits2Banking"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

If the contributor-notes build directory is not configured, follow Chapter 277 before continuing.

Step 2 — List the registered tests without executing them

ctest --test-dir ".\output\learning-build\contributor-notes" -N

The result should list eight tests for the default standalone build. The -N option does not run these programmes, so do not write “8 passed” beside this output. It only proves the test registrations were visible to CTest.

Step 3 — Run one named test

ctest --test-dir ".\output\learning-build\contributor-notes" `
    -R "contributor_notes.capacity" --output-on-failure

-R chooses tests whose test name matches a regular expression. capacity checks what happens when our bounded note array has no free slot. It must reject the ninth note while preserving the eight existing notes. A regular-expression selection that matches zero tests must not be described as a successful regression.

Step 4 — Run the full group

ctest --test-dir ".\output\learning-build\contributor-notes" `
    --no-tests=error --output-on-failure

--no-tests=error turns a zero-selected-tests situation into an error, protecting us from accidentally claiming green results when nothing ran. --output-on-failure shows details for failed test programmes. Read the final test summary and compare the number of tests registered with the number executed.

Step 5 — Record the evidence

A useful test record contains: source commit or reviewed working-tree state, operating system, compiler, CMake preset/build directory, actual command, selected tests, passed, failed, skipped and not run counts. A test that could not launch is “Not Run”; it is not “Passed”. If an optional Framework SDK integration was disabled, label it not exercised rather than adding it to the passing total.

Regression selection and safety

A quick focused test is a helpful feedback step, not always the complete acceptance gate. For example, a change to Umicom Framework’s stable C ABI can affect Studio, Trader, OS user-space and installers even if the Notes tests pass. Do not mark a complete platform build green solely because the smallest example passes.

Practice: List the eight tests without executing them. Run the capacity case, then run all eight. Write a one-paragraph evidence summary identifying which result came from a real execution and which was just discovery.

Chapter 283 — Capstone: review, test and publish a learning change

Bits to Banking · Optional Advanced Unit · Versioned delivery
Time: 45–90 minutes · Prerequisite: completion of Chapters 264–279 and authorisation to push to your intended repository.

Goal

Combine the habits from the course into a safe end-to-end delivery. Your change could be a corrected explanation in a Markdown lesson or a reviewed improvement to the C23 Notes demonstration. It must be small enough that another contributor can understand what changed and why. The aim is not to make a large number of commits; it is to produce one reproducible, reviewable update.

Step 1 — Identify the owner and repository

Use your practice repository for this capstone unless an Umicom maintainer has explicitly authorised an official Bits2Banking change. Check the current folder and branch:

Get-Location
git status
git branch --show-current
git remote -v

Confirm which repository you intend to modify. If you are in a parent repository with submodules, examine their status separately rather than assuming git status covers all child edits.

Step 2 — Describe the change in one sentence

For example: “Clarify the difference between Windows Terminal and PowerShell 7”, or “Improve the Notes demonstration’s displayed instruction”. Decide which user will benefit and how you will verify the behaviour. Use an editor to make a targeted change; preserve headers, authorship, comments, existing features and educational context.

Step 3 — Build/test the relevant source

For a Markdown-only change, inspect the links, heading, commands and rendered preview in the existing approved publishing system. For a C23 Notes change, run the Chapter 277 configure, build and CTest commands, and record the actual number of passing tests. If a larger Framework-owned component is affected, follow its own build and testing requirements; do not substitute the Notes lab for Framework acceptance.

Step 4 — Review staging before commit

git status
git diff
git add -A
git diff --cached --check
git diff --cached --stat
git diff --cached

Pause: If any unrelated path, unreviewed deletion or suspicious secret appears, do not commit. Stage only the intended changes after correcting the problem. git add -A is broad and therefore requires careful review.

Step 5 — Commit and push (authorised main only)

git commit -m "docs(learning): clarify the first contributor workflow"
git push origin main
git status

These commands follow the Umicom owner-maintained direct-to-main policy. External contributors who cannot push to the organisation repository should submit a fork-based pull request instead. A remote push may be rejected if the remote advanced independently; do not force push. Fetch and compare histories first.

Step 6 — Confirm publication separately

A successful git push establishes only that GitHub accepted the commits. It does not establish that the learning site deployed successfully or that a final executable works on Windows and Linux. Publication must be checked independently using the repository’s approved CI and site build process. If you cannot observe the final site, report publication as not verified.

End-of-course evidence package

Retain the change description, reviewed diff, Git commit ID, tool versions, build/test results, relevant screenshots or logs and remaining open checks. For a practical Umicom contribution, clearly distinguish: source is committed, tests passed locally, CI passed, and site or binary deployed. These are separate milestones.

Final reflection: What would go wrong if a developer assumed git push also compiled and tested code? Which fact changes when an OS parent gitlink is updated? Why is preserving old functionality especially important when the project is used to teach new contributors?
