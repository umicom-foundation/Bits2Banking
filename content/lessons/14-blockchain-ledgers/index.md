# Introduction to Blockchain and Distributed Ledgers

[Lesson library](../index.md) · [Learning sequence](../../start/learning-sequence.md) · [Browser course](../../courses/blockchain-ledgers/index.html)

Start with files, records and validation. A ledger is a record of transactions. A distributed ledger has cooperating copies on different computers. Learn the record and its checks before studying how those computers agree. The programming exercises also require C foundations.

- [Learning path Canonical Markdown NextWhat you will learnExplain build a merkle tree from transaction digests with explicit assumptions, an independently checkable worked example and the limits of the evidence. Concept and mechanismAn ordered group of transactions can be represented by a single root digest. Hash each transaction into a leaf node, combine neighbouring nodes into parents, and repeat until one digest remains. Real blockchains specify their own precise byte encodings; the Umicom learning algorithm uses domain-separated SHA-256 on already-hashed record digests. A Merkle root is an authenticated-data-structure commitment only when obtained from a trusted block/header/anchor. Worked exampleFor transactions A,B,C,D, compute four leaf-domain hashes, then parents P0=H(nodeDomain||LA||LB), P1=H(nodeDomain||LC||LD), and bind the top with count four. Concept and mechanismA Byzantine participant may send contradictory statements to different peers rather than merely crash. Classical BFT protocols address such behaviour with authenticated messages, quorum intersection and view-change rules. An often-studied model uses 3f+1 replicas and 2f+1 commit votes for f Byzantine faults. Real protocols differ, and the number alone is not a complete algorithm. Worked exampleWith f=1 the classical configuration has 4 replicas and a 3-vote quorum. Two size-three groups overlap in at least two replicas, so at least one overlapping member is honest if no more than one is faulty.
