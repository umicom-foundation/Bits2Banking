# Understand the analysis and simulation build graph

## What you will learn

A build graph describes which outputs depend on which inputs. This project uses CMake to describe the graph and Ninja to execute the required commands. GHDL analyses and runs VHDL.

## Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

~~~text
git --version
cmake --version
ninja --version
ghdl --version
~~~

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

~~~text
git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu
~~~

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

~~~text
cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation
~~~

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

~~~powershell
cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"
~~~

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.


## Follow the dependency chain

~~~text
learning_cpu.vhd + tb_learning_cpu.vhd + GHDL executable
                         |
                         v
                  analysis.stamp
                         |
                         v
                   cpu_analysis
                         |
                         v
                  simulation test
~~~

The stamp is a small file written only after successful analysis and elaboration. Analysis checks VHDL source and records design units in the work library. Elaboration connects the selected top-level design.

## Inspect the command

Open CMakeLists.txt. The custom command lists both VHDL files and the GHDL executable under DEPENDS. Changing a listed input makes the analysis output out of date. VERBATIM asks CMake to preserve command arguments correctly, including paths containing spaces.

LANGUAGES NONE tells CMake that this project does not use its built-in C or C++ compiler rules. GHDL is located with find_program.

## Observe incremental work

1. Build the project twice without changing source.
2. The second build should have no analysis work to perform.
3. Change an explanatory comment in your practice VHDL file.
4. Build again.
5. Analysis is expected to run because the source timestamp changed.

This dependency graph does not decide whether an edit changes semantics. It conservatively analyses changed source. Separate tests are still run by CTest when you request them.

## Run the waveform target

~~~text
cmake --build --preset simulation --target simulate
~~~

This target depends on cpu_analysis and runs the testbench with a waveform output. It is an explicit action and runs each time requested. Its output is in build/simulation/ghdl-work/cpu.ghw.

## Check your understanding

Why must the stamp be written last? If analysis fails but a fresh stamp is left behind, the next build could incorrectly consider the failed step current.
