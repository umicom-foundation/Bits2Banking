# Choose expected results independently

## What you will learn

An oracle is the rule used to decide whether a result is correct. If a test calculates its answer by repeating the same faulty logic as the implementation, both can agree while being wrong. You will derive CPU expectations from the instruction table.

## Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

~~~text
git --version
cmake --version
ninja --version
ghdl --version
~~~

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

~~~text
git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu
~~~

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

~~~text
cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation
~~~

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

~~~powershell
cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"
~~~

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.


## Prepare expectations on paper

For each instruction write the accumulator and address before and after the edge. Apply the published instruction meaning rather than copying the case statement.

| Step | Instruction | Expected accumulator | Expected address |
| --- | --- | --- | --- |
| Reset | reset high | 0 | 0 |
| Load | x"13" | 3 | 1 |
| Pause | x"2F", enable low | 3 | 1 |
| Subtract | x"31", enable high | 2 | 2 |
| Branch | x"58" | 2 | 3 |

The pause row is especially useful because a naive "one input means one instruction" test would advance the expected address incorrectly.

## Read an assertion

~~~vhdl
assert accumulator = 3 and address = 1
  report "pause changed state" severity failure;
~~~

assert evaluates a condition. If it is false, report provides an explanation and severity identifies the seriousness. The simulation command uses --assert-level=error so an error or failure stops the run with an unsuccessful result.

## Test the test

1. Make a separate practice copy.
2. Change one expected value from 3 to 4.
3. Run the simulation.
4. Confirm that the run fails at that assertion.
5. Restore the correct expectation.
6. Run again.

This deliberate mistake checks whether the assertion is actually reached and whether the runner reports failure. It does not prove that every other assertion is correct.

## Improve messages

Several supplied assertions have concise default diagnostics. Add a report string describing the specific instruction and invariant. Avoid inserting values that your test did not actually observe.

## Check your understanding

Why keep the original instruction table when reviewing a test? It is the contract against which both implementation and expected values are compared. Agreement between two pieces of code is weaker evidence if both were copied from the same logic.
