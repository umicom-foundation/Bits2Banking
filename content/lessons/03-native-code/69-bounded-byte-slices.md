# 69. Read bytes safely: a fictional ledger message

A financial application receives data from files, database drivers and network connections. Such data arrives as **bytes**. It may contain invalid characters, missing fields or a zero byte in the middle of a message. A parser must not assume that every input is a valid, terminated C string.

We will build a small reader for a fictional account change. The example is intentionally much smaller than a banking message standard, but the validation techniques apply to larger systems.

## 1. Define the format

One complete message consists of an unsigned account number, a colon, a required plus or minus sign, and a decimal amount measured in pence:

```text
1001:+2500
```

This means training account `1001` has a positive change of 2,500 pence. No real account is opened, no payment is sent, and no transaction is posted.

The message length is supplied separately. We do not call `strlen()` on the received bytes.

## 2. Define the result

Open [`ledger_line.h`](https://github.com/umicom-foundation/Bits2Banking/blob/main/labs/native/bounded-ledger-line/ledger_line.h):

```c
typedef struct BtbLedgerRow {
    uint32_t accountId;
    int64_t changePence;
} BtbLedgerRow;
```

The account identifier has a fixed width. The signed amount can represent credits or debits in **exact minor currency units**. We do not use a floating-point value to represent pence.

The parser returns a status and writes a result only when the entire message has been validated.

## 3. Check every digit

For each account digit, the parser calculates whether multiplying the current value by 10 and adding the next digit would overflow `uint32_t`:

```c
if (account > (UINT32_MAX - digit) / 10U)
    return BTB_LEDGER_RANGE;
account = account * 10U + digit;
```

The subtraction is safe because `digit` is known to be between 0 and 9. The expression tests the operation **before** performing it.

A signed 64-bit amount needs special care. Its negative range includes `INT64_MIN`, whose absolute magnitude is one larger than `INT64_MAX`. The code accumulates the digits in an unsigned 64-bit value, uses a different limit for negative values, and only converts after checking the complete magnitude.

## 4. Reject incomplete input

The parser refuses:

```text
1001:2500             missing sign
1001:+               missing digits
1001:+12extra         extra characters
4294967296:+1        account identifier exceeds uint32_t
```

It also rejects a zero byte inside the input, because the exact grammar contains only ASCII digits, a colon and a sign. The parser never treats that zero as permission to ignore the remaining bytes.

In `ledger_line.c`, find the final statement `*outRow = result;`. Until that statement, all changes happen in temporary local variables. Rejected input therefore leaves the previously stored record untouched.

## 5. Build and test

From `C:\umicom\Umicom-Bits2Banking`:

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S ".\labs\native\bounded-ledger-line" -B ".\output\learning-build\bounded-ledger-line" -G Ninja -DCMAKE_C_COMPILER="C:\msys64\ucrt64\bin\gcc.exe"
cmake --build ".\output\learning-build\bounded-ledger-line" --parallel 2
ctest --test-dir ".\output\learning-build\bounded-ledger-line" --output-on-failure
```

The project registers three tests: valid and invalid messages, a demonstration programme, and 20,000 deterministic generated byte sequences. The generated-input test is a useful *fuzzing exercise*, although it is not a replacement for coverage-guided fuzzing or a complete protocol review.

## 6. Extend the reader carefully

Add a rule that rejects an account identifier of zero. Make the change in `ledger_line.c`, add one failing test to `test_ledger_line.c`, and rebuild. Be clear whether zero is prohibited by the **application's business rules** or by the **wire format**; those two concerns do not always belong in the same layer.

The real Umicom Framework contains a shared web stack: [`include/umicom/web/`](https://github.com/umicom-foundation/umicom-framework/tree/main/include/umicom/web). It owns HTTP parsing and networking contracts. Our small fictional ledger reader is an exercise, not a competing production implementation.
