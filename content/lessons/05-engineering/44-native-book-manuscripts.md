# 44. Assemble a book from Markdown using C23

A book is more than a collection of unrelated files. Its chapters must appear in a deliberate order, its metadata must remain associated with the correct edition, and its published output should be traceable to the original manuscript.

Bits to Banking keeps the original manuscript for *Islam: Blueprint for Life* under `dropzone/documents/islam_blueprint_for_life/`. That folder contains a `volume.yml` file and the individual Markdown chapters. The web edition is prepared from those originals; we should not edit the published copies and then silently overwrite the source.

In this lesson, you will use a native C23 program to **list available book volumes** and **assemble one reviewable Markdown manuscript**. You will then inspect the code that performs the work.

## 1. Read the book manifest

Open:

```text
dropzone/documents/islam_blueprint_for_life/volume.yml
```

The beginning of the file contains the book title and other descriptive fields. The ordered list under `chapters:` identifies the files that make up the book. A simplified extract looks like this:

```yaml
title: "Bits to Banking — Volume 1: Islam: Blueprint for Life"
slug: islam_blueprint_for_life
chapters:
  - introduction_to_islam.md
  - history_of_money.md
  - decline_of_sound_money.md
  - modern_banking_and_finance.md
```

The real manifest contains the complete list of ten chapters. The order is significant: a book assembler must follow the manifest, not the alphabetical order returned by the filesystem.

A *manifest* is a document that describes an artefact to be built. A *source manuscript* is the original editable material. An *output artefact* is a result produced from those sources.

## 2. List the available books

In PowerShell, use the Umicom Education executable built from Framework:

```powershell
Set-Location "C:\umicom\Umicom-Applications"

$Education = ".\build\umicom-education\bin\umicom-education.exe"
$Books = "C:\umicom\Umicom-Bits2Banking"

& $Education book list --repo $Books
```

You should see the `islam_blueprint_for_life` volume, its title and its chapter count. The program reads folders under `dropzone/documents/` that contain `volume.yml`, validates the chapter entries and checks that their files exist.

This operation is **read-only**. It does not copy or modify a chapter.

## 3. Assemble the first book

Run:

```powershell
& $Education book assemble --repo $Books --volume islam_blueprint_for_life
```

The native publisher reads the chapters in manifest order and writes a combined Markdown source to:

```text
C:\umicom\Umicom-Bits2Banking\output\native-books\islam_blueprint_for_life.md
```

Open that file in a text editor. You should find the title first and then each original chapter in the manifest sequence, separated by visible Markdown rules. UTF-8 text, Arabic passages, headings and code blocks are copied as source text. If a source chapter starts with a UTF-8 byte-order mark, the assembler omits that mark so it does not appear in the middle of the combined document.

This output is an **intermediate manuscript**, not the final PDF or DOCX edition. Relative chapter-to-chapter links from the separate source files may need conversion before final publication. The existing BookForge and converter processes remain responsible for published book editions.

## 4. Repeat the assembly safely

Run the same command a second time. If the generated bytes are unchanged, the program reports that the manuscript is unchanged.

Now suppose a chapter has been edited. The output no longer matches the source. By default the program **preserves the existing assembled file**, rather than silently replacing it:

```text
DIFFERENT (preserved)
```

After reviewing the source and assembled versions, you may explicitly regenerate the native output:

```powershell
& $Education book assemble --repo $Books --volume islam_blueprint_for_life --refresh
```

`--refresh` is not a Git commit and does not modify the chapter originals. It only replaces the selected generated manuscript after a complete new result has been prepared.

## 5. Follow the C source

Open these Framework files in Umicom Studio IDE or your editor:

```text
framework/include/umicom/education/site.h
framework/src/education/book.c
framework/tools/umicom-education/main.c
framework/tests/education/test_book.c
```

The public header declares the operations. The CLI interprets `book list` or `book assemble`, validates arguments and delegates the work to the Framework library.

The book library has several jobs. It discovers manifest folders, checks the volume identifier, parses the supported manifest fields, verifies chapter filenames, reads the original files, constructs the output and compares the result with any existing file.

Notice how these responsibilities differ. Parsing a manifest must not publish a book. A successful copy must not decide that the manuscript is approved for release. Keeping the responsibilities separate makes failures easier to investigate and permits other applications to reuse the same services.

## 6. Why the filenames are validated

Consider a damaged manifest that contains:

```yaml
chapters:
  - ../private-notes.md
```

`..` moves up one directory in a filesystem path. A tool must not let manuscript metadata read arbitrary files outside the selected book. The current C23 assembler accepts only simple `.md` filenames with letters, numbers, hyphens, underscores and dots, and refuses names beginning with a dot. It also rejects missing and repeated chapters.

This restricted format is intentional. **It is not a complete YAML implementation.** A future general manifest reader would need a tested YAML parser, schema validation, appropriate limits and a separately reviewed path policy.

## 7. Understand the write process

The assembled output is not written directly over the previous edition. The library first generates a complete temporary file beside the intended output. If reading any chapter fails, it discards that incomplete temporary output and leaves the earlier manuscript untouched.

Only after a successful assembly does it compare the two versions. If they are identical, no replacement is necessary. If they differ, explicit refresh permission is required. Publishing then replaces the previous generated file using the host operating system's file-replacement operation.

This is a small example of a useful software engineering principle: **prepare a complete result before publishing it**.

## 8. Test the implementation

From the Applications repository:

```powershell
Set-Location "C:\umicom\Umicom-Applications"

cmake --build ".\build\umicom-education" --parallel 2

ctest --test-dir ".\build\umicom-education" --output-on-failure
```

The `framework.education.book` test creates a disposable two-chapter book. It checks the chapter order, removes only a leading UTF-8 BOM from the generated compilation, refuses to overwrite a differing output, accepts an explicit refresh and rejects both missing chapters and traversal attempts.

These tests do not alter the published Islam chapters. They operate in a separate build-tree fixture.
