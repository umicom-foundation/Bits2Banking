# Lesson 17 — Generate Text with Our Own Native Transformer

**Bits to Banking · Build Your Own LLM from Scratch**  
**Author:** Sammy Hegab · **Organisation:** Umicom Foundation  
**Implementation:** Umicom Framework, C23

## What you will learn

Until now, our experiments have focused on *training* a transformer. We have
learned how text becomes tokens, how the decoder calculates logits, why
backpropagation updates weights and how checkpoints record those weights.

This lesson introduces **inference**: applying an already-trained model to
predict the next token without changing its weights. We will generate several
tokens in succession, inspect how a prompt changes the model's context, compare
greedy and probabilistic sampling, and reload the exact same model from disk.

The example is small enough to examine mathematically and to test with complete
C23 source. It is not designed to write production-quality C code.

## 1. From one prediction to a sequence

Suppose we enter the source-code prompt:

```c
int account
```

The byte tokenizer maps each byte to an integer token ID. The model receives a
bounded sequence of token IDs and produces a row of **logits** (unnormalised
scores) for every input position. Only the final row represents the next-token
prediction after our current prompt.

The first predicted token is appended to the context. We then ask the decoder
for another prediction. Repeating this procedure is called **autoregressive
generation**. The model's new output becomes part of its next input.

Our experimental decoder supports a fixed context size. When the prompt is
shorter than the context, the Framework left-pads with the beginning-of-sequence
token. When the prompt becomes longer, older tokens fall off the left of the
window. A token cannot attend to tokens that have not yet been generated.

## 2. Greedy prediction versus sampling

If the final logits for three permitted tokens are `2`, `1` and `0`, greedy
selection always picks the first token. It is completely deterministic and does
not use the random-number generator.

For probabilistic sampling, we calculate:

```text
P(token i) = exp(logit[i] / temperature) / sum(exp(logit[j] / temperature))
```

Here `z` is a token's logit and `T` is a positive temperature. At `T=1`, our
example gives probabilities near `0.6652`, `0.2447` and `0.0900`.

**Top-K** sampling considers only the K largest logits before applying this
formula. With `K=2`, the third token is removed; the probabilities become
approximately `0.7311` and `0.2689`.

Smaller positive temperatures favour the most likely token. Larger temperatures
produce flatter distributions. A random seed selects a reproducible sequence of
draws; it does not make the distribution deterministic for every possible seed.

### Numeric safety

Naively evaluating `exp(very_large_logit)` can overflow. Umicom Framework first
subtracts the maximum selected logit, computes exponentials and then
normalises. The output is checked for finite values; invalid temperatures,
`NaN` logits, oversized K and insufficient output buffers are rejected.

Equal logits are ordered by increasing token ID, giving a well-defined tie rule
across supported platforms. The sampling PRNG is seeded locally, not stored in
mutable global state.

## 3. A reusable C23 Framework service

The public header is:

```text
Umicom-Applications/framework/include/umicom/ai/training/generation.h
```

The implementation lives at:

```text
Umicom-Applications/framework/src/ai/training/generation.c
```

There are three reusable operations:

- `UmiAiTrainingSampleLogits` chooses a token from checked logits.
- `UmiAiTrainingDecoderGenerate` produces an explicitly bounded token array
  using the Framework decoder's existing logits operation.
- `UmiAiTrainingDecoderGenerateBytes` accepts raw UTF-8 or binary prompt bytes
  and returns exact output bytes through the canonical reversible tokenizer.

The application owns the input and output memory and must destroy the loaded
model after use. All three operations provide failure-atomic output contracts.
A complete result is published only after every requested token is produced.

The current model has a 260-ID vocabulary: IDs 0–3 are reserved, and the
remaining 256 IDs represent every possible byte value. The sampler excludes
reserved IDs from generated output. It does not automatically stop on EOS;
the present training corpus has not established a meaningful EOS convention.

**Important:** Generated bytes are not necessarily valid UTF-8. The native CLI
prints escaped bytes rather than treating arbitrary model output as terminal
control sequences or a NUL-terminated string.

## 4. Build and test the source

Open PowerShell, using our canonical checkout location:

```powershell
Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

cmake -S ".\framework\learning\native-llm" `
    -B ".\build\windows-ucrt64-native-llm-debug" `
    -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON

cmake --build ".\build\windows-ucrt64-native-llm-debug" --parallel 2

ctest --test-dir ".\build\windows-ucrt64-native-llm-debug" `
    --output-on-failure --no-tests=error
```

The focused tests verify permitted token ranges, ties, seeded reproducibility,
numeric safety, rolling context, byte roundtrips and checkpoint equivalence.

## 5. Create a trained checkpoint and generate text

Use the existing native experiment tool to create a **new** checkpoint. Choose
a different path if the file already exists: the checkpoint API does not
silently overwrite training evidence.

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-experiment.exe" `
    ".\framework\learning\native-llm\fixtures\experiment.conf" `
    "C:\umicom\_local\lesson-decoder.umi"
```

Now generate 24 bytes with greedy inference:

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-generate.exe" `
    "C:\umicom\_local\lesson-decoder.umi" "int account" 24 1 1.0 42
```

Repeat using `top_k=8` and `temperature=0.8`:

```powershell
& ".\build\windows-ucrt64-native-llm-debug\umicom-native-llm-generate.exe" `
    "C:\umicom\_local\lesson-decoder.umi" "int account" 24 8 0.8 42
```

The final argument is the sampling seed. Compare identical and different seeds
while keeping the checkpoint and generation settings fixed. Do not expect valid
C syntax after such a limited training run.

## 6. Understand what the tests prove

We can establish that the decoder performs a forward pass, samples from the
specified probability distribution, retains generated tokens in its rolling
context and reloads trained weights without changing predictions.

We cannot conclude that the system understands C23, Umicom Framework or
Calypso. That will require larger licensed datasets, genuine held-out source
files, quality-controlled benchmarks and more model capacity. Falling
training loss is not sufficient evidence.

Similarly, exact results from a fixed seed verify reproducible sampling only
for the specified implementation and arithmetic environment. Model weights
remain unchanged throughout generation, and no generated text is executed.

## 7. Review questions and practical exercises

1. Why does the next prediction depend on previously generated tokens?
2. Which row of a decoder's logits is used to predict the next token?
3. Explain the difference between `top_k=1` and `top_k=8`.
4. Why subtract the maximum logit before computing exponentials?
5. Why must generated output be returned as bytes with an explicit length?
6. What happens when the prompt exceeds the model's context length?
7. Run the experiment twice with the same seed and compare the output. Then
   change only the seed and explain the different result.
8. Inspect `src/ai/training/generation.c` and identify where the Framework
   refuses to publish incomplete output after a rejected request.
