# Lesson 63 — Qualify KV-Cached Nucleus Generation in Native C23

**Bits to Banking · Umicom Foundation**  
**Author:** Sammy Hegab  
**Implementation authority:** Umicom Framework C23

## Learning objectives

Explain when a key/value (KV) cache is mathematically reusable, why beginning-of-sequence padding matters, and how an existing Framework decoder is combined with nucleus sampling without building another neural network.

## 1. Correctness precedes optimisation

A transformer decoder produces the next-token scores from a sequence of tokens. A **key/value cache** retains intermediate attention projections so the decoder may avoid repeating calculations. It is a memory/performance technique, not a new language model and not a new training process.

The existing Framework components have distinct responsibilities:

- `UmiAiTrainingDecoder` owns the model and its trained parameters.
- `UmiAiTrainingKvCache` owns a cache snapshot of a decoder's inference state.
- `UmiAiTrainingSampleLogitsNucleus` applies the existing top-K/top-p sampling policy.
- `UmiAiTrainingDecoderGenerateCachedNucleus` composes those Framework facilities for a bounded, seeded generation request.

The cached route must preserve the behaviour of `UmiAiTrainingDecoderGenerateNucleus` before anyone claims it is an improvement. It must not silently alter the model, positions, sampling policy or checkpoint format.

## 2. Why beginning-of-sequence padding matters

Consider an **eight-token** decoder context and a prompt containing only three tokens: `[A, B, C]`. The canonical generator evaluates an eight-token input:

```text
[BOS, BOS, BOS, BOS, BOS, A, B, C]
```

Here `BOS` denotes a beginning-of-sequence padding token. The prompt symbols are schematic: an actual implementation uses integer token IDs.

If a new cache prefilled only `[A, B, C]`, A, B and C would receive different *learned absolute position embeddings*. Even correct attention arithmetic could therefore produce different logits. Compatibility requires the same full, left-padded context.

When a ninth token enters a full eight-token rolling window, the oldest token falls out. Every retained token shifts to a new absolute index. A cache built from the previous positions is then stale; the Framework rebuilds the window's key/value rows instead of reusing mathematically invalid projections.

## 3. Read the existing Framework interface

The public header `umicom/ai/training/generation_cache.h` declares:

```c
UmiStatus UmiAiTrainingDecoderGenerateCachedNucleus(
    UmiAiTrainingDecoder *model,
    const size_t *promptTokenIds, size_t promptTokenCount,
    const UmiAiTrainingNucleusOptions *policy,
    size_t newTokenCount, uint64_t seed,
    size_t *outTokenIds, size_t capacity, size_t *outCount,
    UmiAiTrainingGenerationCacheStats *outStats);
```

This is a **Framework API excerpt for study**, not a second implementation. Callers provide the decoder, prompt, policy, seed, output buffer and capacity. The decoder remains caller-owned and must not be used concurrently. The cache exists inside the generation call; it is not a persistent application-wide cache.

The associated byte adapter `UmiAiTrainingDecoderGenerateCachedBytesNucleus` returns raw bytes and an explicit count. Generated bytes can include NUL (`0x00`) or invalid UTF-8; they must not be treated as automatically terminated C strings.

## 4. Measure the work actually performed

For a full **eight-token** initial prefill followed by **19** complete rolling-window rebuilds, the computed-row count is

**Calculation:** `8 + 19×8 = 160 computed token rows.`

The statistics record `computedRows`, `windowRebuilds` and `retainedTokens`. They describe the amount of cache computation, **not** milliseconds, memory bandwidth or output quality. If learned absolute positions force full rebuilds, a cache does not automatically make the measured generation faster.

An optimisation claim requires separate wall-clock measurements with identical model, prompt, compiler, CPU, sampling settings and repeatable trials.

## 5. Exercises

1. Write the eight-token, left-padded context for a one-token prompt `[X]`.
2. With an eight-token context and 12 requested output tokens, how many computed rows are recorded if the first prefill is followed by 11 full-window rebuilds?
3. Explain precisely why retaining keys after a position shift can change next-token probabilities.
4. Why is a lower `computedRows` value not proof of a proportional decrease in elapsed time?

<details>
<summary>Worked answers</summary>

1. `[BOS, BOS, BOS, BOS, BOS, BOS, BOS, X]`.
2. `8+11×8=96` rows, with **11** rebuilds under the stated assumption.
3. Learned position embeddings are inputs to the projections. Changing the position changes the hidden representation and therefore may change computed keys and values.
4. Other costs—memory copies, allocation, cache locality, sampling, coordination and fixed overhead—also contribute to elapsed time.

</details>

## 6. Evidence and boundaries

The Framework source and its regression tests, not this manuscript, establish what the implementation currently does. Inspect the real header and generated statistics when evaluating a change. Keep generation and training separate: generating tokens must not update decoder weights.
