## A practical learning problem

Suppose we are training the tiny Umicom decoder to predict the next byte in
illustrative C23 source for accounts and notes. The goal is to preserve
repeatable training behaviour, not to create a genuine autonomous banking
assistant from a few source files. Our reviewed training partition contains
`train/account.c` and `train/notes.c`; the evaluation partition contains
`eval/payment.c`. Entire files remain in their selected partitions, so an
evaluation example cannot accidentally become a training window.

Training a language model consists of more than calling a mathematical update
function. The training supervisor must choose the correct source window,
calculate the learning rate for the absolute step, retain the optimiser's
history, record held-out measurements and cope with interruption.

## Model weights versus optimiser state

AdamW updates each weight using an estimate of the gradient's average and of
its squared magnitude. For a scalar gradient `g` at step `t`:

```text
m_t = beta1 * m_(t-1) + (1-beta1) * g_t
v_t = beta2 * v_(t-1) + (1-beta2) * g_t^2
m_hat = m_t / (1-beta1^t)
v_hat = v_t / (1-beta2^t)
w_t = w_(t-1) - learning_rate *
      (m_hat / (sqrt(v_hat) + epsilon) + weight_decay * w_(t-1))
```

The calculation depends on **all earlier gradient history** through `m_t`,
`v_t` and `t`. Saving only the weight vector `w_t` is insufficient to repeat
the same next update after restarting. The Framework's combined checkpoint
therefore stores the unchanged native decoder checkpoint alongside the AdamW
moment vectors and completed optimiser-step count.

## A schedule belongs to the whole training run

Assume we approve eight total steps with a cosine schedule, two warmup steps,
a peak learning rate of 0.018 and a minimum of 0.002. We train steps 1–3,
save both model and AdamW state, then resume at step 4. Correct continuation
still evaluates the **original eight-step schedule** at steps 4–8. Replacing
that schedule with a new five-step schedule after restarting would change the
learning rates and therefore the trained parameters.

The Framework runner makes these choices explicit:

```c
UmiAiTrainingExperimentConfig config;
UmiAiTrainingAdamWConfig optimizerOptions;
UmiAiTrainingLearningRateSchedule schedule;

/* After loading an approved plan, use its peak learning rate. */
schedule.kind = UMI_AI_TRAINING_SCHEDULE_COSINE;
schedule.peakLearningRate = config.learningRate;
schedule.minimumLearningRate = 0.002F;
schedule.warmupSteps = 2U;
schedule.totalSteps = 8U;

/* No manual tokeniser, optimiser or checkpoint implementation in the app. */
UmiStatus status = UmiAiTrainingExperimentAdamWValidate(
    &config, &optimizerOptions, &schedule);
```

This example is illustrative: initialise `config` and `optimizerOptions` with
the existing Framework defaults or approved plan before calling the validator.

## Our real native implementation

The new API is in
`framework/include/umicom/ai/training/experiment_adamw.h` and its
implementation in
`framework/src/ai/training/experiment_adamw.c`.

The native service delegates to the existing Framework modules:

1. `UmiAiTrainingDatasetBatch` selects deterministic, whole-file partitioned
   token windows using the approved seed and **absolute** step number.
2. `UmiAiTrainingLearningRateForStep` calculates the learning rate without
   looking at wall-clock time.
3. `UmiAiTrainingDecoderTrainAdamWStep` executes the established forward,
   backward and transactional optimiser update.
4. `UmiAiTrainingExperimentEvaluate` calculates the same sampled held-out
   cross-entropy and perplexity used by the SGD trainer.
5. `UmiAiTrainingAdamWCheckpointEncode` and `Decode` clone a complete model
   and optimiser pair before a resumed run.

The two returned handles are owned by the caller. Destroy the AdamW optimiser
**before** the decoder because the optimiser borrows its parameter handles.
An interrupted or rejected run does not publish either handle.

## How to reproduce the experiment

In PowerShell, after merging the approved source files and completing a clean
build, run:

```powershell
Set-Location 'C:\umicom\Umicom-Applications'
ctest --test-dir '.\build\windows-ucrt64-native-llm-debug' `
  -R '^framework\.ai\.training\.adamw_experiment_(resume|contract|cancel|demo)$' `
  --output-on-failure
```

The resume regression compares two entire checkpoint byte streams:
one generated by an uninterrupted AdamW run, and one by an intermediate run
followed by a checkpoint clone and exact continuation. This checks both model
weights and optimiser moments, not merely a similar loss value.

An executable teaching example is
`framework/learning/native-llm/train_adamw_experiment.c`. Its source file is
not a script; it is a small C23 consumer of the Framework public interfaces.
By default it does not create checkpoints. If you explicitly request a new
checkpoint, the Framework refuses to overwrite an existing path.

## Security evidence is a separate question

The user's McAfee quarantine report lists three `ti!` detection identifiers
associated with two builds of the native training executable and an Umicom
Studio lifecycle test. CTest displayed `Process not started / BAD_COMMAND` for
the training executable. These facts show that Windows security software
intervened; they do **not** show a numerical training failure or establish
whether the suspicious binaries are safe. An identifier alone is not a
confirmed malware family classification.

Do not turn antivirus off, rename blocked programs to evade scanning, or mark
the entire build tree as trusted. Instead, preserve the quarantine information,
check the exact SHA-256 and signing status where obtainable, verify your build
inputs and request the security vendor's verdict. The engineering guide
`framework/learning/native-llm/WINDOWS_TEST_SECURITY.md` and the package's
`SECURITY_INCIDENT_REVIEW.md` provide read-only PowerShell commands and the
submission procedure.

## Limitations and next engineering questions

AdamW training here still operates on one bounded native batch per optimiser
step. SGD effective-batch accumulation is a distinct, existing capability; we
do not silently represent that as AdamW accumulation. The combined checkpoint
contains model and moment state, but not a signed training plan or a
cryptographic source-data fingerprint. If the reviewed source files or the
original schedule change, the claimed exact-resume experiment changes too.
