# Lesson 157 — Stream model bytes as complete UTF-8 characters

**Bits to Banking · Umicom Foundation**  
**Author:** Sammy Hegab · **Implementation language:** C23

## Learning objectives

Understand the encoding and ownership invariant, follow a concrete example, identify the reusable Framework service and explain a safe failure outcome.

## 1. The engineering problem

A byte-token language model emits one raw byte at a time. One printed character, however, may need two, three or four UTF-8 bytes. If an application displays each byte immediately as a character, it can show corrupted text or introduce replacement symbols that were not in the model output.

The native Framework therefore provides `UmiUtf8StreamAppend`. It owns no model: it accepts one byte and emits a **complete UTF-8 scalar sequence** only when enough valid bytes have arrived. The generated bytes themselves remain under the existing Framework tokenizer and stacked inference interfaces.

Consider the euro symbol `€`, encoded in UTF-8 as hexadecimal bytes `E2 82 AC`. The first call accepts `E2` and reports zero completed output bytes. The second accepts `82` and also reports zero. The third accepts `AC` and publishes all three bytes in order. The caller must use the reported length rather than `strlen` because streaming data is not a NUL-terminated C string.

## 2. Use the existing Framework boundaries

```c
#include "umicom/base/utf8_stream.h"
UmiUtf8Stream utf8 = {0};
uint8_t completed[4] = {0};
size_t completedBytes = 0U;
UmiUtf8StreamReset(&utf8);
/* A real caller obtains one byte from the Framework inference session. */
UmiStatus status = UmiUtf8StreamAppend(
    &utf8, (uint8_t)0xe2U, completed, sizeof(completed), &completedBytes);
/* status == UMI_STATUS_OK; completedBytes == 0. */
```

The application does not reinterpret partial UTF-8 as text. The Framework rejects overlong byte sequences, UTF-16 surrogate encodings and code points above U+10FFFF. Invalid input leaves the stream and output unchanged. It does not invent replacement characters.

## Practice

**Question:** Why is it incorrect to display `E2` as an independent UTF-8 character?

<details><summary>Reveal the worked answer</summary>

It is only the start byte of a three-byte code-point encoding; valid display requires the continuation bytes `82 AC` too.

</details>
