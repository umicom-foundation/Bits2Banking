Publishing lessons for Umicom Studio

A learning pack is a folder containing lessons and a manifest. A manifest is a list of the files the reader may open. Each entry includes a title, a stable identifier and a SHA-256 checksum: a value calculated from the exact file bytes. If the file changes, its checksum changes. This detects a mismatched edition; a checksum alone does not identify or authenticate its publisher.

The native catalogue, admission checks, reader, history and optional local checkpoints belong to Umicom Framework. This small Python tool prepares course metadata for that reader. It does not compile a project, run lesson examples, install software or grant project trust.

Review the course

  1. Keep related pages in one ordinary folder, without symbolic links or junctions. Those are filesystem shortcuts to another location and are refused by the publisher.
  2. Write clear titles, prerequisites, examples, an exercise and a worked answer. Use fictional accounts and transactions.
  3. Open collection.json. Its resources list is explicit: the publisher does not scan and include every file in a directory.
  4. Add each intended HTML page with a stable id, title, topic, kind and relative path. Use lesson for lessons and guide for overviews.
  5. Use local links between declared pages. A link such as ../index.html means the index one folder above. It may stay inside the selected pack; it must never escape the pack root.
  6. Check the Framework version supported by the reader. Set a reviewed inclusive minimum and maximum compatibility range. Do not enlarge it simply to bypass an error.

Publish the reviewed bytes

Open PowerShell. Replace the checkout path if yours differs. These commands need an installed Python interpreter. Run the write command only after reviewing the content.

Set-Location "C:\umicom\Umicom-Bits2Banking"
python tools/prepare_studio_learning_pack.py content/courses/framework-and-finance --write
python tools/prepare_studio_learning_pack.py content/courses/framework-and-finance --check

The first command writes learning-pack.json through a temporary file in the same folder. The second compares without writing. A matching pack reports Learning pack matches the declared file bytes. A missing resource, unsafe path, duplicate identity, unsupported metadata or stale manifest produces an error. Correct the input and repeat; do not remove the native checks.

Increase the collection revision for a new published edition. Keep existing resource IDs when their meaning stays the same so a learner can recognise the lesson. Changing the bytes requires publishing new checksums even when only prose changes.

Preserve bytes between computers

Windows and Unix tools sometimes write different line endings. That changes the checksum even when the text looks identical. The repository's .gitattributes keeps this collection at LF line endings. Apply an equivalent explicit policy to another pack before publishing it, and run --check on the delivered checkout. Do not hash one copy and distribute another.

Check the content and reader

  1. Open the course index in a browser. Follow every course and lesson link, and check illustrations and worked answers.
  2. Use the project's test environment to run python -m pytest tests/test_studio_learning_pack.py. This exercises the publisher's refusal and replacement rules and checks this collection's declared links. It is separate from native UI qualification.
  3. In Studio, open Guided Learning → Open local learning catalogue. Select the pack folder and choose Load learning pack.
  4. Open the index, move into a course, follow a lesson, return to the course and use Back/Forward. Check anchor links, long content and keyboard navigation.
  5. If using checkpoints, select a database file in a writable folder you choose. Record and inspect a checkpoint; then close and reopen the catalogue and load the pack again.

The native reader shows supported structured content, not arbitrary browser behaviour. CSS styling and interactive scripts are not a native lesson contract. Give every visual explanation a useful text description. Never treat loading a page as passing an exercise.

Limits and recovery

  • A pack contains at most 256 resources. This publisher limits each resource to 1 MiB and the manifest to 256 KiB. Split a larger library into focused packs.
  • Identifiers, titles, paths and version fields have native limits. Read an error as a request to correct the metadata, rather than truncate it silently.
  • If a file is missing or replacement fails, an existing manifest is retained. Recheck the filesystem and permissions before retrying.
  • The native course button selects a known pack identity. Other packs can still be loaded and searched through the catalogue; they do not require hard-coded drive letters in Studio.
  • Publishing the manifest does not prove a Studio build, UI workflow or learning example works. Keep executed results separate from authored checks.
