Creating a New Umicom Application

A beginner’s guide to making folders, creating GitHub repositories, sharing the Umicom Framework, and adding a new application module—followed by a practical design for automatic discovery so future contributors no longer edit CMake by hand.

Part A · Lesson 01

What are we making?

We will use a fictional but realistic Umicom Notes application as an example. The commands are teaching examples: only run them if you actually want to create repositories with these names.

Umicom Notes is a future note-taking product. It could start as a desktop application and later add other frontends. We are teaching repository setup, not building the Notes application itself.

Standalone product

umicom-notes is the main project. It contains documentation and has framework and application submodules.

Reusable application module

umicom-notes-module is the module repository. Both the standalone product and the Umicom Applications suite use it.

Expected folder structure:

C:\umicom\ │ ├── umicom-notes\ Main standalone Git repository │ ├── framework\ Git submodule → umicom-framework │ ├── application\ Git submodule → umicom-notes-module │ ├── docs\ │ ├── README.md │ └── .gitmodules │ ├── umicom-notes-module\ Initial local module checkout (optional afterwards) │ └── Umicom-Applications\ Existing parent Git repository ├── framework\ Existing Framework submodule └── applications\ ├── studio\ ├── trader\ ├── bank\ └── notes\ Another checkout of umicom-notes-module
Three folder names, two new repositories

framework, application and applications/notes are local folder names. The Git submodule URL identifies the actual GitHub repository. Multiple parents can reference the same module repository, each pinned to a particular commit.

What if a command fails?

Stop at the failed command, read its message and check the current directory with pwd. cd does not create folders; mkdir does. A command such as note license is not a PowerShell text editor; use notepad LICENSE.

Part A · Lesson 03

Create the application module repository

Create the module first. The two parent projects will link to it later.

6

Create the module directory

The name umicom-notes-module will also be our GitHub repository name.

PowerShell — type this command
cd C:\umicom
PowerShell — type this command
mkdir umicom-notes-module
PowerShell — type this command
cd umicom-notes-module
PowerShell — type this command
pwd

What to expect: You should be in C:\umicom\umicom-notes-module.

7

Create basic project directories

A real native application normally separates public headers, C23 source code, tests and documentation.

PowerShell — type this command
mkdir include
PowerShell — type this command
mkdir src
PowerShell — type this command
mkdir tests
PowerShell — type this command
mkdir docs
PowerShell — type this command
dir

What to expect: The four directories exist locally. Empty directories are not committed to Git by themselves.

8

Create a README and licence file

In Notepad, type a description of the proposed app and save the file. For the licence, use the organisation’s approved licence text.

PowerShell — type this command
notepad README.md
PowerShell — type this command
notepad LICENSE

What to expect: Include Copyright (c) 2026 Umicom Foundation in the licence notice. The copyright notice alone is not a complete MIT licence.

Important: this is a repository exercise, not a buildable module

A working application module also needs CMakeLists.txt, application.umicom.yaml and valid C23 implementation files. Do not create empty placeholders and assume the application will compile. For a real project, use the approved Framework generator/template; Lesson 08 explains the native generator already available.

9

Start tracking the module with Git

git init creates the local repository. The -b main option selects the initial branch name.

PowerShell — type this command
git init -b main
PowerShell — type this command
git status

What to expect: Git should report that you are on branch main.

10

Stage and commit the first files

Staging selects what the next commit will contain. Committing records the current revision.

PowerShell — type this command
git add -A
PowerShell — type this command
git diff --cached --check
PowerShell — type this command
git commit -m "docs(notes): start Umicom Notes module"

What to expect: The output should include a newly created commit identifier.

11

Create the GitHub module repository

This example uses the existing Umicom GitHub account. It requires permission to create repositories there.

PowerShell — type this command
gh repo create umicom-foundation/umicom-notes-module --public --source . --remote origin --push

What to expect: GitHub creates the remote and pushes the local main branch.

Public versus private

Use --public only for material intended to be published. Do not commit passwords, access tokens, private keys or private customer or patient information. A private repository would use --private.

Create the standalone parent project

This parent project reuses Umicom Framework and the same Notes module, without copying their source files.

12

13

Add a README and licence

The parent project needs its own history.

15

Do not make the framework directory yourself. Git must create and register it.

PowerShell — type this command

What to expect: Git creates the folder and records its URL in .gitmodules.

16

Link the Notes module

This uses the module repository you created in Lesson 03.

PowerShell — type this command
git submodule add -b main https://github.com/umicom-foundation/umicom-notes-module.git application

What to expect: The standalone application now has an application submodule.

17

See your work

List the files and submodule commit references.

PowerShell — type this command
dir
PowerShell — type this command
git submodule status
PowerShell — type this command
git status

What to expect: You should see framework, application and .gitmodules.

18

Commit and publish the parent

Save the parent’s README and the two pinned submodule references.

PowerShell — type this command
git add -A
PowerShell — type this command
git diff --cached --check
PowerShell — type this command
git commit -m "feat(notes): compose standalone Framework application"
PowerShell — type this command
gh repo create umicom-foundation/umicom-notes --public --source . --remote origin --push

What to expect: You now have two independent GitHub repositories linked through Git submodules.

What makes it standalone?

The parent can eventually have its own CMakeLists.txt, presets, resources and packaging settings. A Framework-first standalone build configures Framework once, then adds the application module. Adding two submodules alone is not yet a complete build configuration.

Illustration — standalone parent CMake responsibilities
# Educational CMake outline for the standalone parent — not a full preset.
cmake_minimum_required(VERSION 3.24)
project(UmicomNotes LANGUAGES C)
set(CMAKE_C_STANDARD 23)
include(CTest)
add_subdirectory(framework)
add_subdirectory(application)

The actual starter must also honour the established Framework build options, available targets, platform toolchain, resource and installer policies. Use the existing Umicom native scaffolder for real files rather than relying on this illustration alone.

Add the same module to Umicom Applications

The suite will have a second checkout of the module, pinned independently from the standalone product.

19

Open your existing suite repository

This folder should already exist from the normal Umicom development setup.

PowerShell — type this command
cd C:\umicom\Umicom-Applications
PowerShell — type this command
git status --short

What to expect: Read any changes already present. Do not overwrite or commit unrelated work.

20

Register the Git submodule

Again, Git creates the target folder; do not run mkdir applications\notes beforehand.

PowerShell — type this command
git submodule add -b main https://github.com/umicom-foundation/umicom-notes-module.git applications/notes

What to expect: Git adds an applications/notes entry to .gitmodules.

21

Inspect the new module

The files now come from the same Notes module repository.

PowerShell — type this command
git submodule status applications/notes
PowerShell — type this command
dir applications\notes

What to expect: You should see the module’s checked-in files.

Current Umicom limitation

As of this guide, Git registration and CMake build registration are separate steps. Git successfully adds the module, but the suite still uses a hard-coded list of extended CMake applications. The next three additions are required today; Part B proposes removing this manual step.

22

Open the existing suite CMake file

Only modify this file once when registering a genuinely new module. Never replace the complete file with a short example.

PowerShell — type this command
notepad C:\umicom\Umicom-Applications\cmake\UmicomExtendedApplicationModules.cmake

Current manual addition A — build option

CMake — place beside existing application options
option(UMICOM_APPLICATIONS_BUILD_NOTES
       "Build the Umicom Notes application module"
       OFF)

Current manual addition B — all-modules build

CMake — place inside the existing if(UMICOM_APPLICATIONS_BUILD_ALL_MODULES) block
set(UMICOM_APPLICATIONS_BUILD_NOTES ON CACHE BOOL
    "Build Umicom Notes" FORCE)

Current manual addition C — register subdirectory

CMake — place inside the existing umicom_add_extended_application_modules() function
umicom_add_optional_application(
    UMICOM_APPLICATIONS_BUILD_NOTES
    "applications/notes"
    "Umicom Notes"
    "Notes")

Save the file. The separate Umicom::Framework target is already configured by the suite root; applications should not construct Framework again.

23

Commit only the new suite registration

The module must already be pushed to GitHub before the suite records its commit.

PowerShell — type this command
git add .gitmodules cmake/UmicomExtendedApplicationModules.cmake applications/notes
PowerShell — type this command
git diff --cached --check
PowerShell — type this command
git diff --cached --stat
PowerShell — type this command
git commit -m "feat(applications): register Notes module"
PowerShell — type this command
git push origin main

What to expect: The suite now pins the new module at the version that was checked out when you committed.

Part A · Lesson 06

Build and test a real module

This lesson applies after the module has valid C23 source, a working CMakeLists.txt, a manifest and tests created using an approved Umicom Framework template.

24

Configure the headless build

Use the suite’s existing Windows preset, and enable the new module.

PowerShell — type this command
cd C:\umicom\Umicom-Applications
PowerShell — type this command
cmake --preset windows-ucrt64-headless-debug -DUMICOM_APPLICATIONS_BUILD_NOTES=ON

What to expect: CMake prepares the build files. If no valid module CMake definition exists, configuration should stop with an error.

25

Build the module

The example target name must agree with the module’s actual CMakeLists.txt.

PowerShell — type this command
cmake --build --preset windows-ucrt64-headless-debug --target umicom-notes-console --parallel 2

What to expect: A valid build creates the executable. Do not assume the target exists until the module declares it.

26

Run the module tests

Only registered tests with matching names are selected.

PowerShell — type this command
ctest --test-dir .\build\windows-ucrt64-headless-debug -R "^notes\." --no-tests=error --output-on-failure

What to expect: If CTest reports no matching tests, the module needs correctly registered test targets.

27

Run the application

Start the actual executable only after the build succeeds.

PowerShell — type this command
.\build\windows-ucrt64-headless-debug\bin\umicom-notes-console.exe

What to expect: A working console would start and exit normally. This command is an example, not a claim that a Notes executable currently exists.

GTK4 comes after the portable core

Once the portable build passes, enable the suite’s GTK4 preset and build the manifest-declared native executable. Reuse the Framework GUI adapter; do not create product-owned copies of generic windows or widgets.

Part A · Lesson 07

How to work on the project tomorrow

Git submodules save exact revisions. They do not automatically follow new remote commits in their parent repositories.

1. Change and test shared Framework code (if needed)
↓
2. Commit and push Framework
↓
3. Change and test Notes module
↓
4. Commit and push Notes module
↓
5. Update and commit each parent’s submodule references

Example: Suppose you changed a C23 file inside the suite’s applications/notes submodule.

PowerShell — type this command
cd C:\umicom\Umicom-Applications\applications\notes
git status --short
git add -A
git diff --cached --check
git commit -m "feat(notes): improve Notes functionality"
git push origin main

Then return to the suite and update its pinned revision:

PowerShell — type this command
cd C:\umicom\Umicom-Applications
git add applications/notes
git diff --cached --check
git commit -m "chore(applications): update Notes module"
git push origin main

The standalone parent has a separate checkout. When you want it to use the newly pushed Notes version, update its submodule explicitly:

PowerShell — type this command
cd C:\umicom\umicom-notes
git submodule update --init --remote application
git add application
git diff --cached --check
git commit -m "chore(notes): update application module"
git push origin main
Check your working tree first

The --remote update may move the local submodule to a different commit. Run it only when the submodule has no work you want to preserve. Git’s parent commit will record the exact new revision. For a fresh checkout, use git clone --recurse-submodules URL, or run git submodule update --init --recursive after cloning.

Part B · Lesson 09

How automatic module discovery should work

Yes—developers can avoid editing UmicomExtendedApplicationModules.cmake. We should automate registration at CMake configure time while retaining explicit Git trust and reproducible versions.

The current suite already discovers manifest files for some downstream activities, such as build-target catalogues and native workstation composition. However, adding a new optional application to the actual build is still a hard-coded operation in cmake/UmicomExtendedApplicationModules.cmake. This is the missing link.

Developer adds a Git submodule under applications/
↓
CMake scans registered module directories and their manifests
↓
Validate submodule registration, identity, paths and required Framework interfaces
↓
Create an optional build switch and call existing umicom_add_optional_application(...)
↓
Existing product, installer, tests and shared GTK4 flows see the module

Today Manual

1. Add Git submodule.
2. Edit option(...).
3. Edit all-modules setting.
4. Add umicom_add_optional_application(...).
5. Configure and build.

After improvement Proposed

1. Add Git submodule.
2. Confirm its manifest and trust.
3. Run CMake.
4. CMake registers, configures and builds the approved module automatically when enabled.

Proposed source of truth: the checked-in Git submodule plus its application.umicom.yaml manifest. A generated build catalogue is an output, not an additional hand-maintained list.

Example of the information we already have

Educational YAML excerpt — not a complete manifest
schema: umicom.application.v1
application:
  id: org.umicom.notes
  name: Umicom Notes
  short_name: Notes
  native_executable: umicom-notes
  console_executable: umicom-notes-console
frontends:
  - console
  - gtk
installation:
  component: Notes

A valid real manifest also declares the supported schema fields for application version, Framework compatibility, entry/profile, source layout and ownership boundaries. The C23 Framework manifest parser should remain the authoritative runtime validator; CMake can use a bounded, reviewed subset for build registration.

How the CMake integration can work

Engineering algorithm — preserve existing CMake and comments
# ILLUSTRATIVE PSEUDOCODE — not a drop-in replacement.
# 1. Discover applications/*/application.umicom.yaml.
# 2. Accept only approved, registered Git submodules.
# 3. Validate each manifest and its CMakeLists.txt.
# 4. Derive a unique option such as UMICOM_APPLICATIONS_BUILD_NOTES.
# 5. When ALL_MODULES is ON, include each approved module.
# 6. Call the existing umicom_add_optional_application(...).
# 7. Record module in the existing installer and test catalogue.
# 8. Fail with a clear message on duplicates or invalid metadata.
Automatic registration is not permission to execute arbitrary code

CMake runs build instructions from registered module repositories. A folder appearing on disk must not be treated as automatically trusted. The resolver should accept registered submodules, validate their paths and manifests, check for duplicate identities and target names, honour an allowlist or explicit approval policy, and fail closed on invalid input. It must not auto-fetch unknown remote code or silently publish it.

Part B · Lesson 10

Future one-command project creation

Extend the existing native C23 command, instead of implementing the workflow with Python, PowerShell scripts or another scripting language.

For a novice, the best final experience is a single preview followed by one confirmed creation command. Internally, the Framework creates a standalone parent and one thin application module, records both Git repositories, links Framework once in the standalone project and registers the module in the suite.

Why this design is reusable

The Framework provides native project creation and registration APIs. PowerShell is only a command line where the contributor types instructions. It is not used to implement project functionality. Studio IDE can eventually present the same workflow as a guided graphical wizard.

Part B · Lesson 11

Safe implementation plan and acceptance tests

Improve the existing software incrementally, without removing features, comments, test coverage or registered applications.

Milestone 1 — Automatic build registration

  1. Add a manifest/submodule discovery function to the suite’s existing CMake integration.
  2. Derive unique UMICOM_APPLICATIONS_BUILD_* switches and retain current options for compatibility.
  3. Ensure UMICOM_APPLICATIONS_BUILD_ALL_MODULES includes the discovered module.
  4. Continue calling existing umicom_add_optional_application() so installer, targets and tests keep their current contract.
  5. Track .gitmodules and manifest changes so CMake notices added or removed modules.

Milestone 2 — Native two-repository project creator

  1. Extend existing C23 scaffold and repository services; preserve their current standalone mode.
  2. Create a module repository plus a parent product with framework/ and application/ links.
  3. Add an optional registration operation against an existing Umicom Applications workspace.
  4. Show a dry-run plan and leave existing files untouched when a conflict is detected.
  5. Make repository publication and GitHub remote creation separate, explicit actions.

Milestone 3 — Umicom Studio integration

  1. Add “New Umicom Application” to the existing Framework-backed project creation UI.
  2. Ask only for name, location, frontends, standalone/suite choice and visibility.
  3. Show generated folder paths and module ownership before confirmation.
  4. Display configure, build and test results without hiding errors.

Source-preservation rule

Retain current CMake registrations and explanatory comments during the transition. Introduce the discovery path additively, test it against the existing suite, and only remove redundant code with explicit project-owner approval. Native functionality belongs in C23 or Assembly, using the Framework as its single source of truth.
