# Episode 42 — How does a kernel find a storage device?

**Duration:** approximately 12–15 minutes  
**Related chapters:** [127. Read a device tree](../../lessons/05-engineering/127-inspect-device-tree-in-c23.md) and [128. Memory-mapped I/O](../../lessons/05-engineering/128-mmio-and-transport-negotiation.md)

## 00:00–01:15 — The problem

**On screen:** Umicom Notes → Save → storage service → question mark beside a disk icon.

**Narration:**

“When we press Save in a note-taking application, we rarely think about the hardware underneath. A few words on the screen eventually become bytes that a storage service has to handle. But how does the operating system know what storage hardware is available? It cannot safely guess that every device lives at the same address on every computer.

“In this lesson we will follow one part of the discovery process. We will read a device-tree description, understand the difference between discovering a device and controlling one, and write a small C23 program that inspects a synthetic example. No physical disk will be accessed, and no hardware registers will be modified.”

## 01:15–03:00 — What a device tree describes

**On screen:** [Device discovery diagram](../../assets/diagrams/device-discovery-to-driver.svg).

**Narration:**

“A device tree is a hierarchical description of hardware. Imagine a family tree: a parent node may represent a bus and its child nodes represent devices attached to that bus. Each node has properties. A storage device might advertise a compatibility string and a register range.

“Advertised is an important word. The tree is information supplied by firmware. It does not by itself grant permission for a driver to start touching the device. The kernel needs to validate the description, interpret the address in the context of its bus, identify a supported transport and claim the resource safely.

“In our diagram there are five stages: firmware describes a resource; a parser validates the bytes; a bus translator interprets the address; a driver qualifies the transport; and only then does it acquire permission to use the device. Confusing these stages would be like reading the address of a bank vault on a form and assuming you now have authority to open it. A description is not permission.”

## 03:00–05:30 — Look inside the binary header

**On screen:** `labs/native/device-tree-inspector/fixture.c`, then `fdt.c`. Highlight the magic bytes `d0 0d fe ed`.

**Narration:**

“The device tree is not stored as an ordinary text file in the boot interface we are studying. It uses a binary format called the Flattened Device Tree, or FDT. Its header begins with a magic number. Our program expects the four bytes d0, 0d, fe, ed.

“Those bytes encode a 32-bit number in big-endian order. Big-endian means the most significant byte comes first. We cannot read those bytes by blindly casting the pointer to a 32-bit integer because the machine reading them may use a different byte order, and the pointer might not have suitable alignment.

“Open the `Read32` function. Each byte is explicitly widened to `uint32_t` and shifted into place. The result has the same meaning regardless of the host machine's usual byte order.

“Next, examine the FDT header's total size and the offsets of the structure and strings blocks. A malicious or corrupted file could claim that a block begins near the end of memory and extends well beyond it. Our `Span` function checks the offset and then compares the requested length with the remaining capacity. This avoids overflowing an unchecked addition.”

**Demonstration:** Show the `Span` function and explain `bytes <= total - offset` only after `offset <= total`.

**Narration:**

“We are asking CMake to configure a small C project and Ninja to compile it. CTest then runs two checks: the parser tests and a demonstration program.

“The demonstration reports one VirtIO MMIO candidate. It shows an address and a length, but these values were generated by our own fixture, not read from a real device. The program never dereferences the address; it only explains what the bytes say.

“Go back to the source and identify the two integer-cell properties, `#address-cells` and `#size-cells`. Our fixture uses two 32-bit cells for the address and two for the length. This represents a 64-bit value without depending on the host processor's byte order.”

## 08:30–10:30 — Refusal is useful behaviour

**On screen:** `test_fdt.c`, assertions for truncated input and header mutations.

**Narration:**

“A good parser is not simply one that accepts a valid file. It is also one that refuses an invalid file without modifying an unrelated object.

“Watch what happens when the tests replace the magic number or shorten the supplied buffer. The code must return an error instead of reading past the end. It builds a summary locally and gives it to the caller only after the complete parse succeeds. This is called failure-atomic output publication.

“The test also mutates 10,000 byte positions, using a deterministic sequence. That means repeated test runs examine the same changes. It is useful for reproducing failures, although it does not prove the parser is immune to every possible input.”

## 10:30–12:45 — What happens after discovery?

**On screen:** `kernel/hardware_catalogue.c`, `kernel/virtio_block.c`, and [Kernel hardware discovery guide](https://github.com/umicom-foundation/umicom-kernel/blob/main/docs/HARDWARE_DISCOVERY.md).

**Narration:**

“The next step is memory-mapped I/O. Some devices expose registers at addresses in a memory map. We must not try to read one of those addresses from an ordinary Windows teaching program. Hardware access belongs in an approved, privileged platform adapter with correctly established permissions, memory ordering and device lifetime.

“The real Umicom Kernel has an independent hardware catalogue. It can interpret bus ranges that our classroom example deliberately omits. Its VirtIO block driver then performs device and feature checks, and it owns the resources involved in request handling.

“As you read the Kernel code, ask three questions. Where did this address come from? What establishes that it describes a supported device? And who owns the resource once the driver starts using it?”
