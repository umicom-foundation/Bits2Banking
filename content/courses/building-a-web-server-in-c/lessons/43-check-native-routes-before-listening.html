Check native routes before listening

A route connects a request path to a response handler. In a live server a listener accepts connections. An in-memory check supplies a request directly to the same parser and service without opening that listener.

Run one local check

  1. Use a built Umicom Framework local service example with --check-routes in its help. On Windows, use the full path to its executable if the command is unavailable from your terminal.
  2. Run the command below. The port supplies the values expected by the local browser admission policy. The check does not use the port to listen.
  3. Expect Local route and browser admission checks passed in memory. A failure prints the case name and expected and observed HTTP status. Compare the named contract before retrying.
umicom-web-local-service-example --port 8080 --check-routes

Follow the evidence in C

  1. Open Framework’s examples/web/local_service.c. Follow UmiWebRequestParseStrict, then UmiWebServiceHandleBody. Identify where the check compares machine status, HTTP status and response bytes separately.
  2. Write a table of expected results. The home and health routes should return HTTP 200 under the configured policy. The controlled unrelated Host and Origin checks should each receive 403. Describe why the two refusals need separate cases.
  3. In a branded build, identify how the held response body is compared to the expected SVG or ICO asset. Locate the release call and explain why the comparison needs to happen while the body is still owned.

Predict what each method should do

The method says what the sender wants. A response header describes the reply, while its body holds the returned data. Find these cases in the C example. Cover the last column, predict each outcome, then compare your answers with the table and with the source.

RequestExpected HTTP statusWhat the in-memory check compares
HEAD /api/health200The selected representation has the JSON type. The service result still carries its data at this stage.
POST /api/echo with message=ready+check200The reply has a plain-text type and includes every original byte in order.
POST /favicon.ico with branding enabled405The Allow header names GET and HEAD. A successful favicon request uses an icon type.

Imagine the echo handler sends HTTP 200 and returns only message=ready. Explain which check fails. Then explain why a live HEAD response should keep its selected representation's headers while sending no body bytes. The in-memory test checks the route choice and representation. The later network test checks the response sent to the client.

Propose a separate loopback test that would verify listening, forwarding, finishing the response, and shutdown. Describe each observation you would keep. An installed SDK test adds package identity and linking evidence before testing in-memory behavior.
