Reject an invalid port before starting a server

Before a server opens a socket, it needs a valid port number. The Framework example parses a chosen port without trusting the input text. We will trace its arithmetic and publish-on-success behaviour.

Source to open: Umicom-Applications/framework/examples/web/local_service.c.

Setup recap

Use a text editor, this course and a checkout of the named source. A checkout is a folder containing a repository's files. This is a source-reading and reasoning lab; it needs no running service or account. Choose your own practice folder and keep the original example unchanged. The commands below display source rather than compile or execute it. Replace the example directory with your checkout location. The detailed terminal and editor guide explains how to obtain a checkout, open a terminal and prepare later executable exercises.

A terminal accepts commands. Set-Location (PowerShell) and cd (Bash) choose the folder in which subsequent commands work. Get-Content and sed display text. If a path is missing, locate the repository first instead of creating an empty replacement file.

PowerShell

Set-Location 'C:\umicom\Umicom-Bits2Banking'
Get-Content -LiteralPath '..\Umicom-Applications\framework\examples\web\local_service.c'

Bash

cd /path/to/umicom/Umicom-Bits2Banking
sed -n '1,200p' '../Umicom-Applications/framework/examples/web/local_service.c'

Understand the idea

A decimal parser builds a number one digit at a time: multiply the previous value by ten, then add the new digit. Doing that before checking bounds can overflow. ParsePort instead tests whether port is greater than (65535 - digit) / 10 before multiplication. The accepted policy range is 1024 through 65535.

port text → digit check → checked decimal accumulation → policy range → publish port

Work through the lab

  1. Read ParsePort. Mark the checks for missing text, nondigits, upper bound and lower bound. Find the only assignment through out.
  2. Trace 8765 on paper: 8, 87, 876, 8765. Then trace 65536 and identify the digit that makes the guard reject.
  3. Trace 80, an empty string, 87x5 and -1. Give each a refusal reason. Notice that a sign is not part of this parser's accepted grammar.
  4. Follow main's failed-parse branch. It prints guidance and returns before creating the service. Write a test plan that checks no server is started on invalid input.

Expected result

8765 and the boundary 65535 are accepted. 80, 65536, empty text, signs and nondigits are rejected. On refusal, the parser does not assign the output.

If the result differs

If a rejected input still starts a server, inspect the caller's handling of ParsePort's result. If an accepted port cannot bind, that is a later socket/environment failure; a valid number does not guarantee availability.

Explain it yourself

Why is checking port <= 65535 only after multiplication weaker?

Worked explanation

The intermediate arithmetic may already have overflowed before the comparison. The precondition guard proves that the next multiply-and-add fits, preserving the intended number.

Use the idea in Umicom

Record inputs, expected outputs and refusal cases before extending the example. Reusable production behaviour belongs in Umicom Framework; applications translate user actions and show the service result. A traced example explains a contract. It does not establish that every application using a similar idea has been integrated or tested.
