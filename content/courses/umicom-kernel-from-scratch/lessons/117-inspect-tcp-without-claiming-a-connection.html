Inspect TCP without claiming a connection

Course contents · Previous lesson · Next lesson

Goal and prerequisites

Read a fixed-header TCP segment from caller-owned memory and explain what the result proves. You will trace byte order, length bounds, a mandatory checksum and copied metadata. Complete the earlier IPv4, UDP and ICMP capture lessons first. You need the Kernel sources, CMake, Ninja and a C23 compiler for the host exercise. The optional guest exercise also needs the documented RISC-V toolchain and QEMU. No administrator access or network adapter is needed.

This reader is a narrow capture inspection profile. It does not establish a connection, acknowledge a segment, retransmit data, negotiate options or deliver bytes to an application. A checksum-valid SYN is an observation, not evidence that a handshake succeeded. The full TCP endpoint remains separate development.

Start with lengths, not C structure casts

Open include/umicom/kernel/network_tcp.h and kernel/network_packet.c. The API reuses the existing Ethernet-II and IPv4 reader. An admitted capture has a fixed 14-byte Ethernet header and a fixed 20-byte IPv4 header. The IP protocol must be 6; fragments, IPv4 options, VLAN tags and IPv6 remain outside this profile. TCP then needs at least 20 bytes inside the admitted IPv4 payload.

The TCP data-offset field counts 32-bit words. Five words means the supported 20-byte header. Values below five are malformed. A declared header beyond the IP payload is truncated. A complete longer header has options, so this profile returns unsupported rather than guessing where application data begins. A general TCP receiver must implement more than this restricted reader.

The function reads network-order fields bytewise. Casting an unaligned capture to a native C structure could violate alignment requirements and would also assume the host byte order and padding match the wire format. The public view contains host-order copied values and payload coordinates. It contains no pointer that extends the input lifetime.

Trace one independent vector

  1. Open tests/network_packet/tcp_tests.c and locate the literal golden capture. It contains 59 accessible bytes: 14 Ethernet bytes, 20 IPv4 bytes and 25 TCP bytes.
  2. Read source port 12345, destination port 80, sequence number 0x12345678 and acknowledgment number 0x90abcdef. The fixture has flags 0x18, window 0x1000 and a zero urgent pointer.
  3. Find the five bytes spelling hello at capture offset 54. The IP total length is 45, not 59. The TCP segment length is 25, including its header.
  4. Compare the literal IPv4 checksum 0x3c60 and TCP checksum 0x77ed with the independent test helper. The expected bytes are not generated by the production parser.
  5. Append unrelated Ethernet padding to a scratch copy. The returned payload remains five bytes, because the IP length, not the end of accessible storage, bounds the TCP segment.

Verify the pseudo-header boundary

TCP checksum verification includes the IPv4 source and destination addresses, a zero byte, protocol number and TCP segment length as a conceptual pseudo-header. It also includes the TCP header and data. An odd final byte occupies the high half of a conceptual zero-padded word. These extra bytes are arithmetic inputs, not extra bytes read beyond the capture.

The production function adds bounded 16-bit words, folds carries and requires the complete folded sum, including the stored checksum, to equal 0xffff. A zero checksum field never disables checking. It can be valid when the remaining words already produce the required sum. The checksum_zero case tests both a rejected zero field and a deliberately valid zero-field fixture.

This differs from the optional-checksum policy of IPv4 UDP and from ICMP echo, whose checksum does not include IP addresses. Read source_address and destination_address: each changes an address and repairs the IPv4 header checksum while leaving the TCP checksum stale. The TCP reader must still refuse the capture. A checksum detects some corruption; it does not authenticate a sender or prevent a deliberate forgery.

Keep observations separate from connection state

The view copies all eight flag bits, four reserved bits, the advertised window and the urgent pointer. The reader does not infer whether a flag combination is legal for a particular connection. It has no connection state. Reserved bits are retained as observations rather than used to reject unfamiliar received features. Flags, reserved bits and sequence numbers need a separate endpoint policy if the Kernel later implements one.

#include "umicom/kernel/network_tcp.h"

/* capture points to stable readable storage owned by this caller. */
UmicomEthernetIpv4TcpView tcp;
UmicomNetworkPacketStatus status =
    UmicomKernelEthernetIpv4TcpRead(capture, capture_bytes, &tcp);
if (status == UMICOM_NETWORK_PACKET_OK) {
    /* Consume capture + tcp.payloadOffset for tcp.payloadBytes bytes
     * only while the capture remains owned and unchanged.
     * tcp.sequenceNumber is an observation, not an accepted stream offset. */
}

This is an integration fragment, not a standalone program: the caller supplies capture and capture_bytes. On refusal, the output object remains byte-for-byte unchanged. Successful admission stages a complete result before copying it. The output must be aligned, and it must not overlap any accessible capture byte, including Ethernet padding. Integer address checks prevent wraparound; they cannot prove that a fabricated address is mapped.

Run the host exercise

From the Kernel repository in PowerShell, run each command separately and stop if it fails. The build directory below belongs to this isolated host exercise. It does not configure or boot the operating system. On Linux, omit the Windows compiler argument and use an available C23 compiler.

$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S tests/network_packet -B build/host-network-packet -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DBUILD_TESTING=ON
cmake --build build/host-network-packet --parallel 2
ctest --test-dir build/host-network-packet -R "^kernel[.]network_tcp[.]" --output-on-failure --no-tests=error

Expect 30 TCP cases. The complete isolated suite currently contains 100 cases: 19 IPv4, 27 UDP, 24 ICMP and 30 TCP. These are expected results to check on your own build, not a guarantee for an untested compiler. Golden, empty, even and maximum exercise payload sizes. Truncation and data-offset cases exercise header bounds. Corruption, address changes and zero-field cases exercise checksum boundaries. Lifetime, overlap and output-alignment cases exercise ownership.

Relate the host result to the diagnostic guest

After configuring the documented RISC-V build, use its existing evidence target and test wrapper. Replace the build directory if your configured directory differs. The current-image fixture may add another test to the selection.

cmake --build build/riscv64-clang-debug --target umicom-kernel-evidence umicom-boot-memory-contracts --parallel 2
ctest --test-dir build/riscv64-clang-debug -R "^kernel[.](qualification[.]identity|riscv64[.]packet_admission)$" --output-on-failure --no-tests=error

The guest retains the previous fifteen packet groups and appends tcp-golden, tcp-refusals, tcp-zero-checksum and tcp-padding-lifetime. The required final marker is packet-admission.cases=19, followed by the readiness marker and normal diagnostic completion. The wrapper supplies -nic none. It exercises synthetic RAM captures without sending or receiving network traffic. O0/O2 no-libc links separately check that the production parser does not acquire a hidden hosted runtime dependency.

Exercise, diagnosis and next boundary

  1. Change a payload bit in a scratch fixture without repairing the TCP checksum. Predict a checksum refusal and unchanged output, then run the focused case.
  2. Change only an IP address and repair the IPv4 checksum. Explain why TCP still refuses while the earlier ICMP echo message can remain checksum-valid.
  3. Set the data offset to six in the five-byte-payload fixture. Explain why a fully present 24-byte header is unsupported rather than interpreted as a 20-byte header.
  4. If a golden case fails, inspect literal bytes, byte order and admitted lengths before changing expected values. If a guest marker is missing, inspect the current-image fixture and selected ELF identity first.
  5. Design the next ownership boundary on paper: a future NIC driver must establish DMA completion, capture lifetime, queue limits and shutdown before calling this reader. Do not treat capture admission as a socket or a TCP connection.
