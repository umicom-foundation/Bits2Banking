Read versioned interpreter reports

A person can read the interpreter's normal trace. An editor or test runner needs a predictable format so it can find the same fields on every run. JSON Lines gives it one structured object per line.

Read a successful run

  1. Save this C program as charge.c with its first source line on line 1.
  2. Use an Umicom C executable that lists --jsonl in its help. If PowerShell cannot find umicom-c, use the full path to the executable you built.
  3. Run the PowerShell commands below. Expect a step for the declaration, a step for the return, and a result with the value 42.
int main(void) {
    int amount = 40;
    return amount + 2;
}
$events = @(umicom-c interpret charge.c --jsonl | ConvertFrom-Json)
$runExit = $LASTEXITCODE
$events | Format-Table event, stepKind, firstLine, ok, value
$runExit

Each record contains schema with the value 1. The schema is the agreed layout of a record. A consumer can check the version before reading fields such as firstLine or value. In this run firstLine is 2 for the declaration and 3 for the return. An exit code of 0 means the tool finished successfully. The program returns 42 in the final event.

See what a failed run keeps

Change return amount + 2; to return amount / 0; and save the file. Run the same PowerShell block. The declaration still produces a successful step. The return step has ok set to False. The interpreter prints a separate diagnostic about division by zero. Expect exit code 1 and no result event.

Restore the addition and run it again. An editor could use firstLine to highlight a step and display diagnostics beside the source. Explain why it should check both the exit code and the final result event before displaying a returned value. Keep prompts and diagnostics separate from the JSON objects when collecting the report.
