Preserve progress when a slice fails

Course contents · Previous lesson · Next lesson

A runtime error can happen after earlier instructions have succeeded. The slice API preserves that successful prefix. A prefix means the beginning of a sequence. It does not roll back the whole call, and it does not partially execute the failing instruction. Understanding these two boundaries prevents a debugger from displaying a result that never completed.

1. Follow division by zero

PUSH 1     # succeeds: stack contains 1
PUSH 0     # succeeds: stack contains 1, 0
DIVIDE     # refused: division by zero
RETURN     # never reached

With a slice budget of four, two instructions succeed before DIVIDE is refused. The report contains instructions_executed equal to two and finished equal to zero. The program counter still identifies DIVIDE. Calling the machine again without changing the program encounters the same refusal and reports zero new successful instructions. Do not retry forever; the host should show the error or start a different program.

2. Distinguish admission from execution

Admission checks whether the input is structurally acceptable before work starts. A zero slice budget, a null machine or malformed bytecode is refused without publishing a new slice report. An execution fault occurs after admission and may leave earlier successful instructions committed. These contracts differ deliberately. Read the status before interpreting the report; an old report is not a new observation.

invalid budget: machine unchanged, report unchanged
runtime fault: successful prefix retained, report counts that prefix
completed machine: valid report with zero new work and finished = 1

3. Inspect the meaningful regression

Open tests/test_machine_slices.c and find faults. It checks division by zero, signed addition overflow and the exceptional signed remainder pair. It verifies the program counter, trace status, diagnostic offset and the unchanged machine on a second refusal. Those checks establish observable behavior; merely calling the same function twice would not prove it.

The fuel test sets the lifetime allowance to zero, one, two and three for a four-instruction program. The machine stops at the budget boundary without publishing a result. This catches accidental fuel renewal between calls. A scheduler may choose a larger slice later, but it must not silently increase the admitted lifetime allowance.

4. Run the source-facing demonstration

Set-Location C:/umicom/Umicom-Applications/framework
cmake -S examples/cvm_preview -B build/cvm-preview-debug -G Ninja -DCMAKE_C_COMPILER=gcc -DUMICOM_C_PREVIEW_SOURCE=C:/umicom/umicom-c -DBUILD_TESTING=ON
cmake --build build/cvm-preview-debug --parallel 2
& ./build/cvm-preview-debug/umicom-cvm-preview.exe --slice 4 'int main(void){return 1/0;}'

Run each command separately and stop on build errors. The final invocation is deliberately invalid at runtime and should exit unsuccessfully with a diagnostic. It should not print a successful value. This demonstration is a bounded integer preview, not permission to execute arbitrary native C code.

5. Avoid a misleading repair

Do not replace a refused result with zero. Zero is a valid answer to many programs, so it would hide failure. Framework instead records FAILED and keeps source coordinates. A fresh start clears the old result before admitting new source. The difference between a value and an error belongs in the state model, not in a special integer chosen by the UI.

Exercise: suppose a slice succeeds on three instructions and fails on the fourth. Which amount belongs in instructions_executed? Three. Which instruction should the trace describe? The fourth, because it was the last attempted instruction. Why is finished still zero? RETURN did not complete.
