Separate firmware inventory from hart entry

A RISC-V hart is one hardware thread. Firmware can describe several harts in a data structure called a device tree. The Kernel records a separate event when a hart reaches its C startup code. These facts answer different questions about the same identifier.

Read two independent facts

QuestionExample observation for hart 1What to record
Did a checked firmware description mark it enabled?One-hart QEMU profileThe checked tree did not describe ID 1.
Did a checked firmware description mark it enabled?Two-hart QEMU profileThe checked tree described ID 1 as enabled.
Did it reach the Kernel’s C entry?Both profilesThere is no C entry record for ID 1. Hart 0 has an observed entry.

Trace the native reading

  1. In Umicom Kernel, open include/umicom/kernel/hardware_catalogue.h and locate UmicomKernelHardwareHartRead. Name the two fields that let the caller keep firmware state and entry evidence separate.
  2. Open kernel/hardware_validation.c. Find the query for hart 1 and the hardware.hart-evidence record emitted by the fixture. Predict the value of other-firmware-enabled for one and two harts. Then predict other-c-entry for each run.
  3. Keep these values in separate columns. When a checked tree is unavailable, report that state. When the tree is available and lacks the ID, report that it was not described. Those cases do not establish that a hart entered the Kernel.
  4. Try a paper example with ID 4096 and only two entries. Find the record by its full firmware ID. The identifier is a label, so its value cannot be used as a position in a table of two entries.

Define the next observable event

Write an acceptance check for independently starting a secondary hart. Ask it to report its own identifier and its current startup attempt. A later test can verify that it owns an independent stack and can receive a bounded message. Keep those checks separate from the firmware inventory and from per-hart memory locality.

Use the Kernel’s hardware discovery guide to identify the test images and QEMU commands. When comparing two runs, retain the same image digest, tool version and boot settings apart from the requested hart count. Umicom Kernel hardware discovery
