Bits2Banking

Drive a clocked circuit from a testbench

What you will learn

A testbench is a program for the simulator. It supplies inputs at known times and checks outputs after the circuit has reacted. You will learn the role of signals, a clock generator, a process and a procedure.

Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

git --version
cmake --version
ninja --version
ghdl --version

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.

Read the clock generator

clock <= not clock after 5 ns;

clock starts at '0'. Five nanoseconds later it becomes '1', then alternates every five nanoseconds. A full cycle lasts ten nanoseconds. The model executes on rising edges only.

Read the step procedure

procedure step(value : std_logic_vector(7 downto 0)) is
begin
  instruction <= value;
  wait until rising_edge(clock); wait for 1 ns;
end procedure;

A procedure groups repeated operations under a name. value is its input parameter. The procedure drives the instruction, waits for the CPU's active edge, then allows time for scheduled signal updates to become visible.

The final one-nanosecond wait is a deliberate testbench observation delay. It is not a proposed physical propagation-delay specification. In a more detailed model, timing checks would use the actual interface contract.

Trace one call

  1. The stimulus process calls step(x"13").
  2. The instruction signal is scheduled to receive LOAD 3.
  3. The procedure suspends until a rising edge.
  4. The CPU process schedules new register values.
  5. The procedure waits one more nanosecond.
  6. The assertion reads the updated outputs.

If an assertion reads immediately at the rising edge, it may see the old state because signal assignments are scheduled rather than instantly applied.

Practice

Draw a timeline with clock edges at 5, 15 and 25 ns. Mark when the instruction is driven and when the assertion reads. Then inspect the simulator waveform generated by the simulate target.

Troubleshoot

A process with no wait statement can repeatedly execute without advancing simulated time. The supplied stimulus uses waits inside step; its deadline process also waits explicitly. Keep those timing points when extending the test.

Check your understanding

Why does the testbench use a procedure instead of copying the same wait sequence after every instruction? It keeps the timing rule consistent while each test still supplies its own instruction and expected result.
