Bits2Banking

Make invalid instructions visible

What you will learn

An invalid instruction is an encoding for which the CPU has no defined operation. A fault output gives the surrounding system a visible reason for stopping. You will inspect that boundary and distinguish an intentional halt from a decoding fault.

Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

git --version
cmake --version
ninja --version
ghdl --version

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.

Read the default decoder branch

when x"F" => stopped <= '1';
when others => stopped <= '1'; invalid <= '1';

The others branch covers operation codes not listed earlier. Both branches stop execution, but only the invalid branch sets invalid. The output fault follows invalid.

Follow the test

  1. Locate the reset before step(x"60").
  2. Confirm that reset cleared halted and fault.
  3. Split x"60" into opcode 6 and operand 0.
  4. Verify that 6 has no instruction definition.
  5. Predict halted = '1', fault = '1' and address = 0.
  6. Compare that prediction with the assertion.

The address stays at the offending instruction. That makes it possible for a monitor to identify where execution stopped.

Add a diagnostic check

In a practice copy, add another enabled step after the invalid instruction. Present LOAD 4. Check that fault remains set and the accumulator stays zero. Then assert reset and verify that fault clears.

Use a separate assertion message such as "faulted CPU executed another instruction". A message should state the broken rule, not simply say "failed".

Keep the contract precise

The current fault flag reports an unrecognised opcode. It does not report every possible hardware problem, memory error or undefined input signal. Additional fault sources need distinct definitions and tests so that users can interpret them.

In Umicom Kernel, traps and exception records similarly need a reason and location. The teaching CPU is a way to understand that design principle before reading an architecture-specific trap handler.

Check your understanding

Should a monitoring program treat every halt as an error? No. HALT may be the program's intended end. The separate fault signal distinguishes this decoder error from normal completion.
