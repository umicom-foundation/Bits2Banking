Bits2Banking

Explain wraparound in fixed-width arithmetic

What you will learn

A register has a fixed number of bits. An eight-bit unsigned register has 256 possible states. This CPU deliberately keeps the low eight bits after arithmetic, which is arithmetic modulo 256.

Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

git --version
cmake --version
ninja --version
ghdl --version

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.

Calculate before simulating

For addition, 255 + 2 = 257. Dividing 257 by 256 leaves a remainder of 1, so the stored result is 1. For subtraction, 0 - 1 wraps to 255.

This rule is part of this CPU's instruction contract. A banking amount should usually reject an out-of-range result instead of wrapping; the application domain determines the correct policy.

Follow the implementation

when x"2" => acc <= acc + operand; pc <= pc + 1;
when x"3" => acc <= acc - operand; pc <= pc + 1;

numeric_std defines operations on unsigned vectors. The result here has the width of the accumulator and operand, both eight bits. The program counter also has a fixed width: four bits, giving addresses 0 through 15.

Inspect the boundary checks

  1. Open the testbench and locate the subtraction wrap assertion.
  2. Trace the earlier instructions that set the accumulator to zero.
  3. Execute SUB 1 on paper and predict 255.
  4. Execute ADD 2 and predict 1.
  5. Locate JUMP F followed by NOP.
  6. Predict the program counter after the NOP: zero.

The counter wraps because 15 + 1 cannot be represented in four bits. The test covers this separately from accumulator arithmetic.

Extend the exercise

In a practice copy, add a LOAD 15 followed by ADD 15 case. Expect 30. Then add repeated ADD operations until the result crosses 255. Write each expected value before running the simulation.

Keep the original wrap checks. A new ordinary example does not replace a boundary case.

Troubleshoot

If a wider accumulator changes the result, examine every resize and declared vector range. Increasing a register's width changes the model's arithmetic contract. Update the instruction description and independent expected values together.

Check your understanding

Would saturation produce the same result as wrapping? No. Saturating addition would hold the maximum value, 255, rather than returning to 1. Both are possible designs; this model explicitly chooses wrapping.
