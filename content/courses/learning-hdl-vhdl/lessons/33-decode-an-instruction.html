Bits2Banking

Decode operation codes and operands

What you will learn

An encoding is a rule that maps a meaning to bits. This CPU uses the upper four bits for an operation code, usually shortened to opcode, and the lower four bits for an operand. An operand supplies the value or address used by the operation.

Set up this exercise

A terminal is a window in which you type commands. A folder holds the files of a project. Install Git, CMake 3.26 or later, Ninja and GHDL with VHDL-2008 support; make their executable folders available on PATH. PATH is the list of folders the terminal searches for programs. Open a fresh PowerShell or Bash terminal and check:

git --version
cmake --version
ninja --version
ghdl --version

Each command should print a version. If a command is not found, correct its installation or PATH before continuing. Download the Bits2Banking repository with Git if you do not already have it:

git clone https://github.com/umicom-foundation/Bits2Banking.git
cd Bits2Banking/labs/hardware/vhdl-cpu

If you already have the repository, open its labs/hardware/vhdl-cpu folder instead of cloning again. Work in your own practice copy. The following commands are identical in PowerShell and Bash:

cmake --preset simulation
cmake --build --preset simulation
ctest --preset simulation

Configure finds GHDL and writes build instructions. Build analyses the VHDL files. Test runs the simulated circuit and checks its results. Expected: the cpu.instructions test passes. This is a learner check to perform on your computer, not a claim about a supplied binary. To select a GHDL installation outside PATH, configure with a quoted absolute path:

cmake --preset simulation "-DGHDL_EXECUTABLE=C:/tools/ghdl/bin/ghdl.exe"

A simulation predicts the behaviour described by a model. It does not program a physical chip. No hardware board is required for this module.

Read hexadecimal notation

One hexadecimal digit represents four bits. Digits 0 through 9 have their usual values; A through F mean 10 through 15. Thus x"13" contains the bits 0001 0011. Its opcode is 1 and its operand is 3.

OpcodeOperationEffect
0NOPAdvance the program counter.
1LOADReplace the accumulator with the operand.
2ADDAdd the operand, wrapping at 256.
3SUBSubtract the operand, wrapping at 256.
4JUMPSet the program counter to the operand.
5JZJump if the accumulator is zero; otherwise advance.
FHALTStop executing until reset.
6 through EInvalidSet fault and stop.

Follow the decoder

case instruction(7 downto 4) is
  when x"1" => acc <= operand; pc <= pc + 1;

Bits are numbered from zero. The slice 7 downto 4 selects the upper four bits. The case statement chooses the matching operation. The operand is converted to unsigned and resized to the accumulator's width. Resizing a four-bit unsigned value to eight bits adds zero bits at the front.

Work an example

  1. Write x"19" as opcode 1 and operand 9.
  2. Predict the accumulator after an enabled clock edge: 9.
  3. Predict the new program counter: its old value plus 1.
  4. Find the LOAD example x"13" in the testbench.
  5. In a separate practice copy, change both the instruction and its expected accumulator to 9.
  6. Rebuild and run the test.

Changing only the input should fail an assertion. That is useful feedback: a test compares behaviour with an explicit expectation.

Understand the boundary

The supplied examples drive defined binary instructions. This teaching model does not validate every unknown or high-impedance input bit. A physical interface needs an input-validity and timing contract before those signals are trusted.

Check your understanding

Why is the largest LOAD immediate 15 even though the accumulator holds 255? The instruction reserves only four bits for the operand. Wider results can arise through arithmetic.
