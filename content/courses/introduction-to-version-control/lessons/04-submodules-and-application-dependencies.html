Submodules and application dependencies

Umicom Applications uses separate repositories for shared Framework and application modules. The parent records which child commits belong together.

Previous lesson · Course contents

Read the real registration

Open Umicom-Applications/.gitmodules. The Framework entry includes:

[submodule "framework"]
    path = framework
    url = https://github.com/umicom-foundation/umicom-framework.git
    branch = main

The path is relative to the parent repository. The URL says where the child history comes from. The branch setting is a preference for branch-aware operations; it does not automatically keep every checkout on main or at the latest commit.

A gitlink is the parent tree entry that records a child commit identifier. The child has its own files, staging area and commits. Recording the parent does not record uncommitted child edits.

Inspect the relationship

Set-Location "C:\umicom\Umicom-Applications"
git ls-tree HEAD framework
git -C framework status --short --branch
git -C framework rev-parse HEAD
git diff --submodule=log

The first command shows the published-in-that-parent pin. The third shows the child currently checked out. Different identifiers need explanation: the child may be intentionally newer, older, or independently edited. A parent status can also report modified child content without a changed child commit.

Follow the Framework implementation

Read umicom-framework/src/repository/control/lock_plan.c. umi_repository_lock_plan_build receives an inventory, observed child heads and policy, then produces proposed steps. Its action names include no-change, stage-gitlink and missing-head. This separates deciding what to record from actually changing the parent index.

for each registered child:
    read its checked-out commit
    if the commit is missing:
        report the missing input
    otherwise:
        compare it with the parent's recorded commit
        propose no change or a gitlink update

This is explanatory pseudocode, not an executable script. Locking records checked-out revisions; it does not download new source or prove that every child commit is published.

A safe publication order

  1. Review and publish the edited Framework repository once.
  2. Fast-forward other clean main-branch Framework copies to the published revision. Preserve unique edits separately.
  3. Review the parent gitlinks and its own changes.
  4. Record and publish the parent after its children. A parent push using --recurse-submodules=check checks referenced submodule commits are available on a remote.

That availability check is not proof that every remote is the intended one or that tests passed. Do not update third-party dependency pins merely because another dependency changed.

Exercise

Framework contains an uncommitted edit, while its HEAD identifier still equals the parent pin. Will committing the parent include that edit?

Answer

No. The edit belongs to the child working tree. First review and record the child, publish it, then record the new child identifier in the parent.

Choose one editing copy explicitly

A remote repository can appear in several local directories. An OS checkout may contain Framework for dependency builds, while Applications contains the shared authoring copy. These directories are not interchangeable.

This preview fetches metadata without staging or publishing:

umicom repo publish-all "C:\umicom" --primary-directory Umicom-Applications

The primary directory is relative to the workspace argument. The service groups checkouts by remote identity, selects the unique matching copy there, then orders groups by child relationships. Registered Applications modules, including Healthcare, follow that choice. A repository such as Kernel keeps ordinary selection if no copy is inside that directory.

Read the primary-selection source. It does not copy files. An edited outside copy, a different unpublished history or a misspelled directory stops publication.

Work through two copies

Applications/Framework is clean at commit A. OS/Framework has an uncommitted fix based on A. Which copy should the explicit policy publish?

Worked answer

Neither is ready. Preserve and compare the outside fix, then deliberately reconcile it into the authoring copy. The service must not silently promote the dependency or erase edits. Publish shared source once, update clean copies and then record parent pins. The regression framework.repository.publication.primary.edited-copy covers refusal, separately from evidence of a real remote push.

Observe every recursive child revision

Use the native observation command when you need the recursive listing, including unchanged entries. It invokes the existing Framework Git-capture service and validates the complete result before publishing counts.

umicom repo submodules "C:\work\application"
# Direct Git alternative, from that same repository:
git submodule status --recursive
  1. Run the command from a known repository or supply its path. No initialization, fetch, checkout or publication occurs.
  2. Read each commit and its leading marker. A space means initialized at the indexed revision; - means uninitialized; + means a different checked-out revision; U means an unresolved submodule merge conflict.
  3. Use umicom repo review --root PATH inside an initialized child to inspect its working-file changes. A matching revision alone does not prove that its files are unchanged.
  4. Retain the listing alongside the parent's commit record and qualification evidence. It describes local state, not the remote server.

A successful observation exits with zero even when it reports a missing or mismatched child. Read the result before proceeding. Bad arguments exit with two; failed capture, timeout, malformed output or display failure exit with one. The capture limit is 4 MiB and the command timeout is ten seconds. An unavailable Git executable, truncation or unexpected diagnostic line is an incomplete observation, never an empty healthy inventory. Partial or rejected output is displayed without publishing counts.

The tail of each Git line is human-readable evidence, not a machine-readable path. Control and non-ASCII bytes are displayed with escapes. Unusual names may be rejected by the record validator. Do not paste an escaped display label into a command. In the legacy C summary, dirty counts merge-conflicted entries reported by this probe; it does not count all edited child files. The parser's output stays unchanged on refusal; the older probe API retains its zero-on-read-failure contract.

Exercise: mismatched but clean

A child has marker +, and its own working-tree review shows no changed files. Did either command repair the parent pin?

Answer: No. The child is clean at a revision different from the parent's index. Review that revision, its publication state and its qualification before deliberately recording a new parent pin. Observation does not select the correct revision.

See the Git submodule manual for the underlying status convention.

Follow submodule_probe.c: capture bounded bytes, validate every record, then assign counts. A diagnostic after a valid line must refuse the whole summary. The regression framework.repository_inspection.submodules.warning checks this ordering; the oversized-line case checks that a long valid record is not silently skipped. Executing these contracts and exercising real Git are separate qualification steps.
