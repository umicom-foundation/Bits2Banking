LESSON 76 · NATIVE C23 · BENCHMARK EVIDENCE

Qualify Timing Evidence and Protect Native Checkpoints

Reject numerical mismatches, preserve model and output integrity, and interpret benchmark clocks without overstating performance.

Learning objectives

Learn to decide whether a performance comparison deserves to be published. Inspect a native C23 report, distinguish available measurements from missing data, protect caller-owned outputs and checkpoint bytes, and record enough experimental context that another developer can reproduce the result.

1. A benchmark report is a claim that needs evidence

It is tempting to run a small test once and announce a speedup. That practice is particularly misleading for native inference, where CPU frequency scaling, cache warming, work scheduling, system load, compiler optimisation level and memory allocation costs affect the result. The Umicom approach is stricter: the service can report timing evidence only after proving that it is comparing equivalent computations.

The new UmiAiTrainingPrefixBenchmarkResult is not a trained model or a production performance certificate. It is a bounded, in-memory report from one execution. The result describes the workload that was actually qualified, the number of parity-checked pairs, a non-cryptographic token fingerprint, the number of checkpoint bytes verified and whether each clock produced usable readings.

2. Mandatory gates before publishing the report

GateMeaningOn failure
Input validationNonempty bounded prefix, valid decoder shape, valid temperature/top-K/top-p, bounded planInvalid arguments rejected, report untouched
Canonical parityEvery generated token from both paths is identical for the same seedNo successful report
RepeatabilityThe full sampled sequence agrees across independent benchmark pairsNo successful report
Cache accountingReported rows, retained tokens and rebuilds match the Framework plannerNo successful report
Model immutabilityOriginal and final portable decoder checkpoint bytes agree exactlyNo successful report
Clock integrityDurations positive, finite, consistent and supported by the selected clockTiming marked unavailable; parity evidence can remain valid

The crucial distinction in the final row is deliberate. A clock with insufficient resolution is not evidence of a numerical defect. Equally, a correct numerical result must not be used to invent a zero-duration or high-performance result when timing is unavailable.

3. Wall clock, CPU time and timer quality

Wall-clock duration records how much real time passed between the start and end of one complete generation call. For interactive users, this is closer to perceived latency. The Framework uses native monotonic timing facilities when present: QueryPerformanceCounter on Windows and CLOCK_MONOTONIC on POSIX. If neither is available, it falls back to C23 timespec_get; the report flags that fallback as not guaranteed monotonic.

Process CPU time, read through C clock(), measures CPU time consumed by the process. It is not necessarily the CPU time of only one thread. Parallel activity may contribute to that number. If the clock is unavailable or too coarse to register a positive interval, the report explicitly sets cpuClockAvailable to zero and leaves the CPU timing value at zero without interpreting that as free computation.

Because the experiment alternates path ordering, both timing sets include complete repeated calls with equivalent inputs, but they do not eliminate all host-level variation. Report the full min/median/max wall distribution and compiler settings rather than choosing whichever single run looks best.

4. Inspecting an evidence report in C23

#include "umicom/ai/training/prefix_benchmark.h"
#include <inttypes.h>
#include <stdio.h>

/* This function receives a successfully published result. */
static void PrintEvidence(const UmiAiTrainingPrefixBenchmarkResult *report)
{
    printf("Parity-checked pairs: %zu\n", report->verifiedPairs);
    printf("Tokens compared: %zu\n", report->comparedTokens);
    printf("Reference rows: %" PRIu64 "\n",
           report->estimate.canonicalComputedRows);
    printf("Observed KV rows: %" PRIu64 "\n",
           report->observedCache.computedRows);
    printf("Checkpoint integrity: %s\n",
           report->checkpointUnchanged ? "preserved" : "NOT verified");

    if (report->wallClockAvailable) {
        printf("Reference median wall: %.6f s\n",
               report->canonical.medianWallSeconds);
        printf("KV median wall: %.6f s\n",
               report->incremental.medianWallSeconds);
        printf("Monotonic timer: %s\n",
               report->wallClockMonotonic ? "yes" : "no");
    } else {
        puts("Wall timing unavailable: no latency conclusion.");
    }
    if (!report->cpuClockAvailable)
        puts("Process CPU timing unavailable: no CPU-speed conclusion.");
}

checkpointUnchanged is one only when the successful benchmark compared complete original and final portable checkpoint bytes and found them identical. The fingerprint is intended for quick reproducibility checks of generated IDs; it uses FNV-1a, not SHA-256 or a digital signature, and does not authenticate a checkpoint.

5. Rejected operations must not corrupt the caller's report

Umicom Framework contracts require failure-atomic output publication. A caller can reuse its report object after a rejected plan without finding half-filled timings or leftover token counts from a failed comparison. The implementation calculates everything into a local candidate and publishes only after every gate passes.

UmiAiTrainingPrefixBenchmarkResult report;
unsigned char saved[sizeof report];
memset(&report, 0xA5, sizeof report);
memcpy(saved, &report, sizeof report);

UmiAiTrainingPrefixBenchmarkPlan invalid = {
    12U, 0U, 0U, UINT64_C(99) /* no measured pairs */
};
UmiStatus result = UmiAiTrainingPrefixBenchmarkRun(
    model, prompt, promptCount, &policy, &invalid, &report);
if (result != UMI_STATUS_INVALID_ARGUMENT ||
    memcmp(saved, &report, sizeof report) != 0) {
    /* Reject the implementation: output was changed on failure. */
}

The excerpt assumes a caller-owned decoder, prompt and policy, plus <string.h> and <stdint.h> headers. Complete executable regression coverage is in tests/ai_training/test_training_prefix_benchmark_rejections.c. The report has the same byte sequence before and after the rejected call.

6. Reproduce the experiment on Windows

The opt-in native LLM prefix laboratory composes the same Framework-owned decoder, KV cache and sampler that applications consume. Open PowerShell and use your current C:\umicom\Umicom-Applications tree after reviewing and merging the files with Beyond Compare.

Set-Location 'C:\umicom\Umicom-Applications'
$env:Path = 'C:\msys64\ucrt64\bin;' + $env:Path
cmake -S '.\framework\learning\native-llm\prefix-work' `
    -B '.\build\windows-ucrt64-native-llm-prefix-debug' `
    -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw 'Configure failed.' }
cmake --build '.\build\windows-ucrt64-native-llm-prefix-debug' `
    --target umicom-native-llm-prefix-benchmark `
             umicom-ai-training-prefix-benchmark-parity-test `
             umicom-ai-training-prefix-benchmark-rejections-test --parallel 2
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }
ctest --test-dir '.\build\windows-ucrt64-native-llm-prefix-debug' `
    -R '^framework\.ai\.training\.prefix_benchmark_' --output-on-failure
if ($LASTEXITCODE -ne 0) { throw 'Benchmark qualification failed.' }

Run the same focused tests in an independent Release build. Do not confuse a Release timing with a Debug timing. Also retain the complete command line, operating-system build, CPU model, compiler and compiler version, number of warm-up pairs, number of measured pairs, sampling seed, decoder configuration and prompt. The benchmark executable prints both parity and timing evidence; attach its console output to a development log if you need to compare later.

7. Worked decision: what can the team reasonably claim?

Suppose the eight-token experiment produces 96 canonical rows and 56 cached rows. If all pairs match, the team may say: the opt-in KV path computes 40 fewer token rows for this specific input while producing the same sampled token IDs and preserving the checkpoint. That result is grounded in measured counters.

Suppose the wall-time medians are 4.2 ms for reference and 4.7 ms for KV. The cached path is slower in this observation, despite its lower row count. It would be wrong to call this a 41.67% speed improvement. If the readings are unavailable, the team can discuss only parity and workload, not measured latency.

As the context rolls, learned absolute positions force every retained token into a new positional embedding. A cache cannot simply keep prior keys and values unchanged. A future positional model such as RoPE would have different semantics, and old model checkpoints cannot silently be reinterpreted as the new architecture. New mathematical tests and an explicit checkpoint version policy must precede such a migration.

8. Practical exercises

  1. Describe three reasons for repeating measurements instead of choosing one run.
  2. Explain the difference between CPU time and wall-clock latency during a multithreaded workload.
  3. Which result field proves that the model's binary checkpoint was preserved? Is the token fingerprint a cryptographic signature?
  4. When a measured run returns a different sampled token, should the benchmark still publish its timing statistics? Explain why not.
  5. Compare Debug and Release results and prepare an evidence record containing the complete environment and workload description.

Engineering conclusion: A trustworthy benchmark makes incorrect results impossible to present as successful measurements. Treat performance as observed evidence, not as an inherent property of the words “KV cache”.
