LESSON 70 · NATIVE C23 · TESTING

Test Prefix Reuse Against Real Decoder Logits

Qualify a measured reduction in computed token rows without confusing it with changed generation semantics or a benchmark speed guarantee.

Learning objectives

Run an independent native CMake/CTest project, compare every vocabulary logit for every prefix, verify actual cache-row counters, test input rejection, and interpret CPU-time measurements conservatively.

1. Define the proof you need

Work reduction is useful only if it preserves the numerical result. Our comparison creates one decoder, then two separate caches of its unchanged parameters. The reference cache runs Prefill independently for each prefix length, with positions restarting at zero. The incremental cache runs Prefill once for the first token, then Append for each new token. These procedures must calculate the same values because their positions, weights and attention masking remain identical.

UmiAiTrainingKvPrefixPerformanceCompare checks every logit at each prefix against an absolute difference limit of 0.00004, aligned with the existing KV-cache context regression. It also rejects a report unless both caches' real work counters agree with the expected row totals and there are no rolling-window rebuilds.

Independent-reference qualification follows in Lesson 71. The two methods in this lesson both invoke the existing KV-cache kernel. Their agreement checks scheduling and reuse, not an independent calculation by UmiAiTrainingDecoderLogits. Lesson 71 adds that separate canonical-decoder comparison before the first rollover.

2. Build the native laboratory in Windows PowerShell

First merge the new files into Umicom-Framework, preserving their repository-relative directories. Configure this opt-in CMake laboratory separately so it does not unexpectedly change the existing native generator or the consolidated applications build.

Set-Location 'C:\umicom\Umicom-Applications'
$env:Path = 'C:\msys64\ucrt64\bin;' + $env:Path

cmake -S .\framework\learning\native-llm\prefix-work `
  -B .\build\windows-ucrt64-native-llm-prefix-debug -G Ninja `
  -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw 'Configure failed.' }

cmake --build .\build\windows-ucrt64-native-llm-prefix-debug `
  --target umicom-native-llm-prefix-work `
           umicom-ai-training-kv-prefix-reuse-test `
           umicom-ai-training-kv-prefix-rejections-test --parallel 2
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }

ctest --test-dir .\build\windows-ucrt64-native-llm-prefix-debug `
  -R '^framework\.ai\.training\.kv_prefix_' `
  --output-on-failure --no-tests=error
if ($LASTEXITCODE -ne 0) { throw 'Regression failed.' }

Three CTests are expected: one compares real decoder prefix logits and checkpoint bytes, one checks invalid inputs and failure-atomic reporting, and the last executes the teaching CLI. These are expected checks on your machine, not a claim that your Windows build has already passed.

3. Read the complete result

#include "umicom/ai/training/kv_prefix_reuse.h"
#include <inttypes.h>
#include <stdio.h>

/* model and tokenIds belong to the caller. */
UmiAiTrainingKvPrefixPerformance report = {0};
UmiStatus status = UmiAiTrainingKvPrefixPerformanceCompare(
    model, tokenIds, 6U, &report);
if (status == UMI_STATUS_OK) {
    printf("Prefixes compared: %zu\n", report.matchingPrefixes);
    printf("Reference rows: %" PRIu64 "\n", report.observedReferenceRows);
    printf("Incremental rows: %" PRIu64 "\n", report.observedIncrementalRows);
}

The six-prefix fixture should report 21 independently rebuilt rows, six retained-cache rows and zero context rebuilds. It should report six matched prefix-logit comparisons. The test's decoder and cache both use the original Framework implementation, not a teaching replacement for the attention mathematics.

4. What CPU time does and does not show

Repeated Prefill and incremental Prefill/Append are measured separately using the process CPU clock. Cache construction is excluded from both timings; per-prefix cache inspection is included in both; the final logit comparisons are excluded. These details matter when interpreting a small measurement.

If the clock is unavailable or too coarse, an apparently zero reading is not evidence of free inference. If a single run appears faster, do not generalise. To evaluate throughput, repeat the experiment many times, warm up the execution environment, document compiler options, inspect distribution and variance, and compare wall-clock latency under realistic load. Fewer computed rows is a verified unit-of-work saving; it is not the same as faster text generation.

5. Where the cache stops helping

The moment an append must evict position zero, learned absolute positions are reassigned to the retained tokens. The existing Framework cache correctly rebuilds the rolling context. Making the original text-generation workload faster could require different positional-encoding rules, checkpoint semantics and re-training, or an altogether different mathematically qualified optimisation. Such a change deserves its own design and compatibility tests.

Exercises and review questions

  1. Why do we compare all vocabulary logits instead of merely the highest-scoring token?
  2. For context length eight, what happens when you append the ninth token? Why is the original six-prefix experiment not a benchmark of this situation?
  3. Which errors must leave the result structure untouched? Give two invalid-input examples.
  4. What could cause two implementations to have equal token-row counts but different CPU times?
  5. Plan a reproducible benchmark report that includes machine, compiler, repetitions, variance and numerical parity.

Key lesson: A useful optimisation is a specific and falsifiable claim: identical inputs and positions, bounded numerical difference, measured work savings, and clearly declared limits.
