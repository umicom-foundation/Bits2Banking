LESSON 80 · NATIVE C23 · GENERATION CONTROL

Qualify Policy-Bound Generation and Benchmarks

Bind native token generation and performance evidence to approved positional semantics.

Learning objectives

Apply the checkpoint declaration to real token generation and benchmarking, distinguish the historical BOS-left-padded policy from the newer unpadded-prefix policy, understand why a generated sequence must be staged, and inspect measured KV-cache work without inventing performance improvements.

1. One decoder, two explicitly different generation policies

After a checkpoint has been admitted, the application still has a crucial decision: what does token position zero mean? The original generator left-pads short prompts to the model's full context length using the Beginning-of-Sequence (BOS) token. The opt-in prefix generator begins directly at position zero with the first real prompt token. Because the existing model has learned absolute positional embeddings, the two policies need not produce the same tokens even when all model weights, nucleus settings and seeds are identical.

This is not a defect in either generator. They implement different input conventions, just as a treasury application must distinguish an amount denominated in GBP from the same numeric amount denominated in USD. The mistake would be to conceal the distinction from the caller. The new C23 admission layer makes that choice explicit and checks it against the previously approved position sidecar.

2. Generate with a bound model identity

The new UmiAiTrainingPositionBoundGenerate method first checks the model's complete checkpoint SHA-256 and declared context. It then calls exactly one existing Framework generator: either UmiAiTrainingDecoderGenerateNucleus for the historical left-padded policy, or UmiAiTrainingDecoderGeneratePrefixNucleus for the unpadded prefix. Finally, it verifies checkpoint identity again before publishing tokens and evidence.

#include "umicom/ai/training/position_admission.h"

/* model and approved were obtained using reviewed checkpoint bytes. */
const size_t prompt[] = {109U, 114U, 120U};  /* byte IDs: i n t */
const UmiAiTrainingNucleusOptions policy = {1.0F, 1U, 1.0F};
size_t generated[6] = {0};
size_t written = 0U;
UmiAiTrainingPositionGenerationEvidence evidence = {0};

UmiStatus status = UmiAiTrainingPositionBoundGenerate(
    model, &approved,
    UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED,
    prompt, 3U, &policy, 6U, UINT64_C(80),
    generated, 6U, &written, &evidence);

if (status == UMI_STATUS_OK) {
    /* All six IDs have been published; the checkpoint still matches. */
    /* evidence.cache is actual KV-cache work for the unpadded mode. */
}

There is no replacement neural network in this wrapper. Sampling still belongs to the Framework's original nucleus sampler, and the unpadded KV session still uses the established native cache. Keeping mathematical ownership in one place prevents subtle differences between a UI, a benchmark and a production API consumer.

3. Failure atomicity applies to completed generation, not just file loading

A request for six tokens can fail after several internal operations. For example, a model may be modified by another caller in violation of the documented serialisation requirement, or sampling may encounter an invalid numerical state. If the service published tokens one by one, an application might treat a partial answer as complete.

The bound generator therefore stages the returned token IDs in a private bounded array and stages its evidence separately. The approved checkpoint is verified both before and after generation. Only after all six requested tokens are available and the final verification succeeds are the caller's output array, count and evidence updated. A rejected call cannot silently overwrite those outputs.

This does not make concurrent decoder access safe. The application must still serialise all training, inference and destruction of a shared decoder. It does prevent the wrapper from falsely reporting successful generation when an observed identity mismatch occurs.

4. Evidence availability must be represented accurately

The unpadded-prefix generator already exposes actual KV-cache statistics. The historical canonical generator does not return the same statistics. The new evidence type therefore includes cacheWorkAvailable. For the original policy it is zero, and the cache counters are set to zero rather than being presented as measured results. For growing-unpadded generation it is one and the existing KV statistics are copied.

PolicyGeneration ownerPosition behaviourKV work evidence
BOS-left-paddedOriginal canonical nucleus generatorShort prompts padded on the left to full contextUnavailable from this API; explicitly flagged
Growing-unpaddedExisting prefix KV generatorReal prompt begins at token position zeroActual computed rows, rebuilds, retained tokens

Consider an eight-token context, a three-token prompt and twelve generated samples. The full-context independent reference calculates 96 decoder token rows. The current growing-prefix cache calculates 56 rows, avoiding 40 row computations (about 41.7%). That calculation describes the inspected workload, not a guarantee that elapsed time will improve by 41.7%. Cache allocation, memory access, matrix kernels and clock resolution also affect observed runtime.

5. Benchmark the same declared context

The existing paired benchmark uses a right-BOS-padded canonical reference and compares logits from the last real prefix token. This is appropriate for the growing-unpadded semantics. It would not be a fair comparison for the historical left-BOS-padded mode. UmiAiTrainingPositionBoundBenchmark therefore refuses all contexts except UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED.

const UmiAiTrainingPrefixBenchmarkPlan plan = {
    6U,    /* generatedTokens */
    1U,    /* warmupPairs */
    3U,    /* measuredPairs */
    UINT64_C(80)  /* seeded sampling */
};
UmiAiTrainingPrefixBenchmarkResult report = {0};
UmiStatus status = UmiAiTrainingPositionBoundBenchmark(
    model, &approved,
    UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED,
    prompt, 3U, &policy, &plan, &report);

if (status == UMI_STATUS_OK && report.checkpointUnchanged) {
    /* Report contains established parity, measured rows, and optional clocks. */
}

The bound API checks approved model identity at both ends. It delegates token parity, measured workloads, alternating execution order, checkpoint preservation and all CPU/wall-clock calculations to the existing Framework benchmark. This avoids creating a competing performance implementation.

6. A future position strategy needs more than a new enum

It may be tempting to add a new position-policy identifier and stop rebuilding old keys/values after context eviction. That would be mathematically incorrect for the current learned-absolute-position decoder. Retained tokens move to different absolute positions, so their key/value projections generally change. Even when future architectures adopt relative or rotary positional information, retained hidden states in a multi-layer network may depend on tokens that have left a finite attention window. The attention-window definition and layer-history dependencies must also be qualified.

A genuinely new positional architecture therefore requires separate training or an explicit weight migration, its own checkpoint compatibility identifier, a qualified independent reference, parity tests around eviction, and repeated benchmark evidence. This batch provides a safer admission boundary before that research begins; it does not pretend the optimization is already implemented.

7. Regression testing and engineering exercise

Compile and execute the tests using the commands from Lesson 79 or the private merge guide. The focused native tests cover approved checkpoint round trips, direct-generator parity for both policies, invalid input and output preservation, shape-identical foreign checkpoint rejection, an unsupported positional strategy and the benchmark context gate. The full Windows UCRT64 execution is the definitive integration check.

  1. Why is it unsafe to compare a left-padded generator with a right-padded canonical prefix benchmark?
  2. What does cacheWorkAvailable == 0 communicate to the application?
  3. Explain why a checkpoint is checked again after the generation call, even though it was checked before the call.
  4. Given context length eight, prompt length three and twelve samples, reproduce the 96 and 56 computed-row totals using the Framework's pending-final-token convention.
  5. Use Beyond Compare to verify that the new module did not replace or remove any pre-existing generator, checkpoint or KV-cache implementation.

Key lesson: a fast inference path is only useful if the application can prove which model and context convention produced its output. Enforce that identity at the execution boundary, preserve failure-atomic results, and measure computation separately from timing.
