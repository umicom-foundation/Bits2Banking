LESSON 78 · NATIVE C23 · CHECKPOINT IDENTITY

Encode and Verify Portable Position Sidecars

Protect checkpoint compatibility through a strict 128-byte record, independent SHA-256 checks and explicit policy admission.

Learning objectives

Write and validate the native positional-compatibility sidecar, understand how portable binary schemas are defined without relying on the C compiler's structure layout, and distinguish a content digest from authentication. Use the existing decoder and prefix benchmark to qualify an inference experiment while preserving the original checkpoint and every caller-owned output on failure.

1. An explicit sidecar—not a modified checkpoint

The original Umicom native checkpoint format stores a specific decoder architecture and trainable parameters. It is a separate, existing Framework contract. Adding an unrecognised position field into that binary format would risk breaking older readers and generating misleading compatibility claims. For this stage, the more conservative engineering decision is a new 128-byte unsigned sidecar that describes how an approved checkpoint may be used.

A sidecar is a small companion record stored separately from the model file. Think of the signed deployment manifest that identifies an executable without inserting new bytes into the executable itself. Here the record stores a model digest, shape, seed, completed optimiser steps, positional strategy, context policy and rollover rule. It is deliberately not part of the trained model.

2. Portable binary layout from first principles

A public C23 struct is not automatically a portable file format. Compilers may insert padding between members; machines can differ in endianness; size_t can be 32 or 64 bits. Therefore we must define the byte offsets explicitly and write multibyte integer fields in a chosen order. The new contract uses unsigned little-endian integers, an exact record length and SHA-256 digests.

Offset (bytes)LengthContent
0–78Magic UMIPOS01
8–2316Format, positional encoding, context mode and rollover rule
24–4320Five decoder dimensions
44–474Canonical checkpoint size in bytes
48–6316Initial seed and completed optimiser steps
64–9532Checkpoint SHA-256 digest
96–12732SHA-256 digest of sidecar bytes 0–95

The decoder dimensions are validated using the existing Framework KV-cache allocation planner. That allows the same shape validator to protect both live cache sizing and parsed sidecar metadata. A parser must reject unsupported versions, bad lengths, invalid channel/head combinations, corrupt record digests and unknown position strategies. It must not try to guess a compatible replacement.

3. Encode and decode with the actual Framework API

#include "umicom/ai/training/position_contract.h"

UmiAiTrainingPositionContract record = {0};
UmiAiTrainingPositionContract parsed = {0};
uint8_t bytes[UMI_AI_POSITION_CONTRACT_RECORD_BYTES] = {0};
size_t written = 0U;

UmiStatus status = UmiAiTrainingPositionContractBuild(
    model, UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED, &record);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPositionContractEncode(
        &record, bytes, sizeof(bytes), &written);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPositionContractDecode(
        bytes, written, &parsed);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPositionContractVerify(
        model, &parsed, UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED);

This example assumes that model has already been created from an approved checkpoint. The buffer is caller-owned. The functions neither choose a filename nor write to disk. Umicom Studio, Umicom Trader and future consumers must use their own approved Framework storage and security policies when persisting the record.

Notice that the output record is assigned only after every validation step succeeds. A malformed record does not partially replace the caller's structure. An undersized destination does not modify its bytes or length counter. These are examples of failure-atomic APIs: callers either receive one complete valid result or retain their original data.

4. A digest is not a signature

SHA-256 produces a 256-bit digest that will ordinarily change if the input bytes change. This is useful for detecting accidental corruption and making exact content comparisons. But a digest does not tell us who supplied the input. Anyone able to replace a sidecar can calculate another unkeyed digest for the replacement. Therefore the new sidecar is explicitly unsigned.

To trust an external model, Umicom must separately verify its source and any signed release approval using the Framework's established security and publication services. Only then should the ordinary checkpoint codec accept the file. Decoding the positional sidecar is not a shortcut around that trust boundary. The demonstration creates its own local educational decoder rather than loading an unknown model from the network.

5. Pair positional admission with inference evidence

The Batch 75 benchmark compared the canonical decoder and growing-prefix session with identical inputs. It checked token parity and checkpoint byte preservation. The new position declaration adds a complementary control: the comparison must be attached to the model and context policy it actually used.

/* Preconditions: approved model, prompt, policy and benchmark plan. */
UmiAiTrainingPositionContract approval = {0};
UmiAiTrainingPrefixBenchmarkResult evidence = {0};

UmiStatus status = UmiAiTrainingPositionContractBuild(
    model, UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED, &approval);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPositionContractVerify(model, &approval,
        UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPrefixBenchmarkRun(model,
        promptIds, promptCount, &sampling, &plan, &evidence);
if (status == UMI_STATUS_OK)
    status = UmiAiTrainingPositionContractVerify(model, &approval,
        UMI_AI_POSITION_CONTEXT_GROWING_UNPADDED);

Include umicom/ai/training/prefix_benchmark.h to use the benchmark plan and evidence types. A production application should record the approved sidecar, benchmark build identity, compiler and hardware environment, elapsed wall-clock distributions, token fingerprints, row counts and any independently signed approval as separate evidence. A token-row reduction is not itself a guaranteed timing improvement.

6. Execute the experiment on Windows

After selectively merging the complete Framework files with Beyond Compare, configure the existing isolated native prefix laboratory. This uses the same Framework decoder and SHA-256 owner; no PowerShell script becomes part of the delivered application.

Set-Location 'C:\umicom\Umicom-Applications'
$env:Path = 'C:\msys64\ucrt64\bin;' + $env:Path
cmake -S '.\framework\learning\native-llm\prefix-work' `
  -B '.\build\windows-ucrt64-native-llm-prefix-debug' `
  -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw 'Configuration failed.' }
cmake --build '.\build\windows-ucrt64-native-llm-prefix-debug' `
  --target umicom-native-llm-position-contract `
           umicom-ai-training-position-contract-roundtrip-test `
           umicom-ai-training-position-contract-rejections-test `
           umicom-ai-training-position-contract-benchmark-test --parallel 2
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }
ctest --test-dir '.\build\windows-ucrt64-native-llm-prefix-debug' `
  -R '^framework\.ai\.training\.position_contract_' `
  --output-on-failure --no-tests=error

The complete test project also includes earlier prefix-reuse, canonical-decoder parity and benchmarking regressions. Those older cases must continue to pass. Run the Release configuration and the full consolidated Framework tests separately before claiming platform-level integration. This book cannot assume your local Windows results.

7. A compatibility decision table

Observed inputResponsible resultReason
Same checkpoint and declared context, authentic approved source.Admit for the supported decoder.Identity, policy and provenance align.
Record length is 127 or 129 bytes.Reject.The portable format has exactly 128 bytes.
Checksum changed or field rehashed with unsupported encoding.Reject.Unknown strategy cannot be interpreted safely.
Model weights changed while declaration remained unchanged.Reject.Canonical checkpoint SHA-256 no longer matches.
Valid unsigned record from an unknown publisher.Do not treat it as trusted.Hash agreement does not establish source authenticity.

8. Practical exercises

  1. Write out the first 24 bytes of a valid position record. What happens if a future record uses a new positional-encoding value?
  2. Why must a parser compare decoded fields rather than cast raw bytes to a C structure?
  3. Change one digest byte in a copy of the sidecar. Confirm that Decode rejects the record and preserves the output object.
  4. Change the checkpoint's approved generation policy while keeping its SHA-256. Why does Verify reject the request?
  5. Explain to an Umicom Studio contributor the difference between source authentication, checkpoint integrity, numerical parity and benchmark timing evidence.

Key lesson: optimisation needs an explicit compatibility boundary. The model's positional mathematics, the caller's context convention and the bytes of the approved checkpoint must remain individually identifiable and independently verifiable.
