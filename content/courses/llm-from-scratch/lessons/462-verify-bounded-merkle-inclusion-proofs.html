What you will learn

Explain verify a bounded merkle inclusion proof in native c23 with explicit assumptions, an independently checkable worked example and the limits of the evidence.

Concept and mechanism

A proof is a path: leaf index, total leaf count, one sibling digest for every level, and a separately trusted root. Verification must reject impossible indices, missing siblings, surplus noncanonical data and wrong duplicated-last siblings. It then reconstructs parents in the exact left/right order dictated by each index bit. The result is compared with the anchored root only after the count-binding step.

Worked example

For 1,024 leaves, the height is 10 and an ordinary sibling array occupies 10×32=320 bytes. For five leaves the height is 3 and the sibling payload occupies 96 bytes, excluding metadata and the trusted root.

Try it yourself

Test valid membership, wrong leaf index, one-bit changes, wrong root, wrong sibling count and changed unused proof bytes.

Reveal the fully worked answer

Valid evidence returns OK; malformed evidence returns INVALID_ARGUMENT and an otherwise well-shaped but nonmatching path returns INVALID_STATE.

Where the proof stops

The API proves inclusion of a *hash*; the application must verify the corresponding signed receipt, data rights and independent root authority.

A native test can verify byte-level membership but cannot by itself authenticate a participant, authorise financial transactions, establish consensus or prove neural model improvement. Record the independent root, protocol and unperformed tests.

Native implementation boundary

Use the existing Umicom Framework C23 SHA-256 and ordered record chain. The opt-in Merkle service consumes validated digests and exposes bounded membership checks. Existing Python and PowerShell teaching tools remain alternatives, not the implementation.
