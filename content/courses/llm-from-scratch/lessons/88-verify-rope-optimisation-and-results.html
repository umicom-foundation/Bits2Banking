LESSON 88 · NATIVE C23 · ROTARY TRAINING

Verify Rotary Training Results Without Overstating Them

Read the evidence for every update and recognise what has not been proven.

What this lesson will help you prove

When a training application prints a smaller number, we must still ask: Is it the right number? Was the measurement taken before or after the update? Did an error change the caller's data? Could the same inputs reproduce the result? Does a smaller teaching loss demonstrate a better language model? This lesson turns these questions into explicit native C23 test requirements.

Mathematics support: Maths Unit 12 explains approximate equality, numerical tolerance and independent gradient checks. Unit 10 shows why a learning rate does not guarantee improvement.

1. Inspect the baseline and every subsequent result

The new UmiAiTrainingRotaryOptimisationRun API returns initialLoss, lossAfterStep[] and finalLoss. The initial value comes from a forward pass with untouched input weights. Each subsequent value is from a new forward pass after an SGD step. The final value is not the loss from a stale graph built before the final update.

observedLossChange = finalLoss − initialLoss

Initial and final mean the values measured before and after the declared training steps. A negative difference means loss went down on this one particular training problem. It does not say anything by itself about generalisation to new examples.

For an accessible example, suppose a model starts at MSE 0.025 and finishes at 0.020. The change is 0.020−0.025 = −0.005. A reduction of 0.005 is measurable improvement on that defined objective, but not evidence that every generated answer will be more accurate.

2. Why test reproducibility?

In this exercise the input features, training targets, weight matrices, positions and learning rate are fixed. There is no random initialisation during the run, so repeating the same call with unchanged inputs should produce identical numerical results on the same configuration. The regression calls the API twice and compares its complete result. This catches unexpected hidden state and accidental retention of data between runs.

Cross-machine floating-point calculations may differ slightly. For separate compiler families, compare declared outputs with justified tolerances instead of demanding universal byte-for-byte equality. A change in compiler or CPU may change rounding, which is not a reason to hide a real numerical mismatch.

3. Understand the two gradient sizes

The result records the first gradient magnitude for the query and key weight matrices. A gradient is a list of numbers with one entry per trainable weight; its Euclidean length describes how large those numbers are collectively.

gradientL2 = √(g₁² + g₂² + ... + g₁₆²)

g₁ through g₁₆ are the sixteen gradient values for one 4×4 matrix. The symbol √ means square root, and ... means the omitted intermediate entries follow the same pattern. The result is a magnitude, not a direction or a direct loss prediction.

For a simpler two-value example, g=[3,4] gives √(3²+4²)=√25=5. Learn the full calculation using Maths Unit 3 and Unit 6.

4. Why do we keep inputs unchanged on failure?

A caller could have a trainable experiment open in Umicom Studio while another module reads its configuration. Unexpected partial mutation would make it difficult to know which parameters produced a result. The new API copies input values into a private Framework tape and publishes its output structure only if every operation succeeds. If a parameter is invalid or an internal call fails, the caller's result buffer remains byte-for-byte unchanged.

5. Run the actual native regression suite

Set-Location 'C:\umicom\Umicom-Applications'
$env:Path = 'C:\msys64\ucrt64\bin;' + $env:Path

cmake -S '.\framework\learning\native-llm\prefix-work' `
  -B '.\build\windows-ucrt64-native-llm-prefix-debug' `
  -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
if ($LASTEXITCODE -ne 0) { throw 'Configuration failed.' }

cmake --build '.\build\windows-ucrt64-native-llm-prefix-debug' `
  --target umicom-native-llm-rotary-optimisation `
           umicom-ai-training-rotary-optimisation-convergence-test `
           umicom-ai-training-rotary-optimisation-rejections-test `
  --parallel 2
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }

ctest --test-dir '.\build\windows-ucrt64-native-llm-prefix-debug' `
  -R '^framework\.ai\.training\.rotary_optimisation_' `
  --output-on-failure --no-tests=error

The C23 library does the training. PowerShell here is only an interactive way to run CMake, Ninja and CTest; it is not a substitute for native functionality.

6. What is not complete?

The optimiser exercise uses only three token rows, two attention heads and two 4×4 trainable projection matrices. It does not contain an autoregressive output head, token-level cross-entropy, a general decoder checkpoint codec, inference sampling or a production memory-optimised RoPE tape operation. The earlier learned-absolute-position decoder and its checkpoints are preserved. A future RoPE decoder will require an explicitly different checkpoint family and new independent integration tests.

7. Exercises and worked answers

  1. Compute the difference when initial loss is 0.03 and final loss is 0.02. What exactly does this show?
  2. Why is the last forward evaluation important?
  3. Give one example of a claim the demo cannot support.
Reveal the instructor's explanation

The observed loss change is 0.02−0.03 = −0.01. It shows a lower value for the declared loss and data. The last forward evaluation uses the updated parameters; a previous graph would be stale. The example cannot prove a production-grade LLM, a numerical advantage over all other systems or an improvement in GPU throughput.
