LESSON 74 · NATIVE C23 · INDEPENDENT QUALIFICATION

Test Prefix-Generation Parity and Observed Workload

Use the original decoder and seeded sampler as the independent reference for streaming, one-shot and rollover behaviour.

Learning objectives

Build an independent reference for the new prefix-streaming policy using the original decoder, reproduce sampling with the same random seed, check prediction parity before and after the first rollover, and understand why a workload estimate must be checked against actual cache counters before publication.

1. What does an independent reference actually mean?

Lesson 69 measured two schedules inside the same KV-cache implementation. That was useful evidence about cache reuse, but two executions of the same kernel can share the same mathematical mistake. Lesson 71 therefore introduced an independent comparator using UmiAiTrainingDecoderLogits, the existing training-tape decoder. This lesson extends that approach from a single fixed context into a complete autoregressive token stream.

We have to compare like with like. The new prefix-session puts the first prompt token at learned absolute position zero. The historical generator places a short prompt on the right side of a BOS-filled context. Those are different models of the request, so comparing their generated text directly would be an invalid parity test. Instead, the canonical reference must preserve the new prefix session's actual positions while still obeying the canonical decoder's fixed-context input size.

2. Right padding and causal attention

Suppose the decoder expects eight input positions, but the growing prefix contains three real tokens. Place those three tokens at positions 0, 1 and 2, followed by five BOS tokens at positions 3 through 7. Call UmiAiTrainingDecoderLogits with the full eight positions, then read the vocabulary-logit row at index 2. The model is causal: the third real token cannot attend to the five later positions. This is a canonical reference for the growing-prefix policy because it preserves the learned positions of every real token.

Original prefix:  [ A B C ]
Right-padded:     [ A B C BOS BOS BOS BOS BOS ]
Reference logits:          ^ read row at index 2
Legacy left pad:  [ BOS BOS BOS BOS BOS A B C ]
Legacy logits:                            ^ index 7

Do not read the final BOS logit from the right-padded reference. That would answer a different question. Also do not left-pad the new reference: changing positions changes the learned position embeddings that the decoder receives.

3. The native parity regression

The new test_training_prefix_generation_parity.c compares real outputs from three paths: a streaming growing-prefix session, a canonical full-context decoder with right padding and the same Framework sampler, and the one-shot wrapper around the new session. It covers short prefixes, prefixes filling the context, greedy and seeded sampling, and sequences long enough to cause repeated rollovers.

#include "umicom/ai/training/prefix_generation.h"
#include "umicom/ai/training/byte_tokenizer.h"

/* Setup has created a decoder, canonical context, and an RNG. */
for (size_t step = 0U; step < requestedTokens; ++step) {
    for (size_t position = 0U; position < contextLength; ++position)
        canonicalContext[position] = position < retained ?
            history[position] : UMI_AI_BYTE_BOS;

    UmiStatus status = UmiAiTrainingDecoderLogits(
        model, canonicalContext, contextLength,
        canonicalLogits, contextLength * vocabularySize);
    if (status != UMI_STATUS_OK) break;

    const float *lastRealRow =
        &canonicalLogits[(retained - 1U) * vocabularySize];
    /* Pass lastRealRow to the original Framework nucleus sampler,
       then compare its selected ID against PrefixGenerationSessionNext. */
}

This is a focused excerpt, not a stand-alone program: model, retained, history, canonicalContext, canonicalLogits and vocabularySize belong to the surrounding test. The complete regression source in the development package includes the RNG setup, sampling call, result checks and history updates. Both paths use the same seed and sampler rather than creating an alternative pseudorandom algorithm for the test.

4. Workload accounting: forecast versus observation

A performance report should not be accepted merely because it contains plausible numbers. The predictor determines how many rows must be computed if the session follows its declared policy. The KV cache reports what it actually computed. The one-shot API refuses to publish the generated token array if those numbers disagree.

For C = 8, P = 3 and G = 12, the required observed values are 56 computed rows, six window rebuilds, eight retained tokens and twelve generated tokens. A mismatch is a correctness problem, not an optimisation opportunity. These counters are exact for the educational single-block decoder contract but are not a complete measure of FLOPs, memory bandwidth, latency or throughput.

5. Checkpoint and failure safety

The regression captures the decoder's portable checkpoint bytes before and after the test. They must be unchanged: inference is not a training step. The rejection regression verifies that invalid prompt lengths, invalid token IDs, malformed nucleus policies and insufficient output capacity do not change caller-owned outputs.

Both streaming and one-shot APIs enforce a maximum of 256 output tokens. One-shot generation stages tokens privately and commits the final array, count and optional cache statistics only after successful generation and counter checks. A streaming session intentionally publishes one token at a time; if sampling fails after the cache advanced, the session becomes terminal and must be destroyed rather than blindly retried.

7. Practical exercises

  1. With context C = 4 and prompt P = 2, calculate the cache rows for G = 1, G = 3 and G = 8. Which sample first requires a complete rebuild?
  2. Why is the right-padded reference logit taken from retained - 1 rather than C - 1?
  3. Explain why exact generated-token parity can be a weaker test than comparing every vocabulary logit. Which earlier test checks all logits before and after rollover?
  4. Design an Umicom Studio diagnostics panel that displays computed rows, rebuilds, context occupancy, model identity and the selected positional policy. Which values must be supplied by Framework services?
  5. Propose a controlled experiment comparing observed CPU time and wall-clock throughput under 100 repeated, warmed runs. What configuration and checkpoint evidence should accompany the result?

Qualification boundary: this batch offers a real new prefix-generation mode and a strict correctness target, but no claim that it accelerates the historical BOS-left-padded generator or that it replaces learned absolute positional embeddings. Preserve both facts in all documentation and user interfaces.
