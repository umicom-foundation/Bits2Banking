Inspect application services

What you will learn

In the previous lesson, a service registry connected a name with a shared object. This lesson asks a different question: how can a screen display information about those services without keeping their memory alive or accidentally reading old storage? You will follow the real Framework service registry and Studio's native state tool. You can read the code and draw the memory relationships on paper before installing any development tools.

1. Separate an object from information about it

A service object does work. For example, a document store holds editable documents, and a task queue schedules background jobs. Information about an object is called metadata. A service's identifier, provider, version and policy flags are metadata. They help us describe an object but do not perform its work.

Think about an application service named example.counter in Framework's examples/service_composition directory. Its object holds a number. Its provider identifier tells us which module supplied it. A diagnostic view can display the provider's name without holding the counter itself.

2. Understand a borrowed pointer

A pointer is a value that identifies a location in memory. When umi_service_registry_find returns a descriptor pointer, the caller borrows a location owned by the registry. Borrowing does not allocate another descriptor and does not transfer responsibility for freeing it.

The registry stores entries in an array: a sequence of positions. Removing an entry can move later entries forward to fill the gap. Replacing an entry can change its contents. Releasing the registry frees its storage. A borrowed pointer must not be kept and used across those changes. Even a pointer that still points inside allocated memory might now describe another entry.

Writing UmiServiceDescriptor saved = *found; copies the descriptor structure, but its string and service pointers still refer to other storage. The star reads the object at found; it does not recursively copy all the objects reached through that structure. This is why copying a pointer and copying the characters it points to are different operations.

3. Read Framework's metadata type

Open include/umicom/runtime/service_registry.h in the Framework checkout. Find UmiServiceSnapshot. Its service and provider names are character arrays inside the structure. The version consists of three numbers. Flags are an integer containing policy bits. There are no object pointers or destructor callbacks in this type.

The word snapshot means a recorded observation. It does not mean that the whole application stopped changing. Once Framework returns the copy, the registry may change later while your copied characters stay the same. This is useful for rendering a report, but you must make a fresh request before relying on current service availability.

4. Follow a checked copy

UmiServiceSnapshot description;
UmiStatus status = UmiServiceRegistryCopySnapshot(
    registry, "example.counter", "example.counter.provider", &description);
if (status == UMI_STATUS_OK) {
    printf("%s comes from %s\n",
        description.service_id, description.provider_module_id);
}

description is local storage for the result. The ampersand in &description gives Framework its address so the function can fill it. status receives the outcome of the request. The two equals signs compare that outcome with the success value; they do not assign a new value.

Only the success branch prints the names. A missing record returns UMI_STATUS_NOT_FOUND and leaves the output unchanged. Because this local variable was not initialised earlier, reading its fields after failure would be wrong. Error handling controls which values are valid to use.

The example supplies a provider explicitly. Passing NULL instead means no specific provider was requested: the first matching registration is chosen. It does not ask Framework to find the newest or healthiest provider.

5. Capacity is not the same as the total

A list needs an array and a limit. If your array has eight positions, you can store at most eight snapshots. The registry may contain eleven. Framework's list copy can fill the first eight, return UMI_STATUS_CAPACITY_EXCEEDED and tell you that the total is eleven. Those eight rows remain useful, provided the view clearly says the list is incomplete.

UmiServiceSnapshot rows[8];
size_t total = 0U;
UmiStatus status = UmiServiceRegistryCopySnapshots(registry, rows, 8U, &total);
if (status == UMI_STATUS_OK || status == UMI_STATUS_CAPACITY_EXCEEDED) {
    size_t visible = total < 8U ? total : 8U;
    for (size_t index = 0U; index < visible; ++index)
        printf("%s\n", rows[index].service_id);
}

size_t is the C type used for object sizes and array counts. The suffix U marks an unsigned integer literal. The expression condition ? first : second chooses one of two values: here it chooses the smaller of the reported total and the array capacity. The loop starts at position zero, checks the limit before each read and adds one to the index after each iteration.

Using index < total would read beyond this array when eleven services exist. That is a memory-safety defect, even if the first eight rows were copied correctly. Always keep the storage capacity alongside the returned count.

A count-only request uses NULL, 0U, &total. Allocating an array after that request does not freeze the registry. A second request can observe a larger count. Handle that possibility rather than assuming two calls saw the same moment.

6. Know what a mutex protects

A mutex coordinates access to shared state so cooperating operations do not change it simultaneously. The copied list and its total are read under the same registry mutex. Registration and removal use that mutex too. The result therefore describes one consistent registry observation.

The mutex does not extend the lifetime of the registry object itself. The owner must keep the registry alive while the call runs and exclude other operations before releasing it. It also does not make every registered service thread-safe. A service's own operations need their own contract.

7. Trace Studio's real reporting path

  1. Open Studio's include/umicom/studio/state.h and find UmiStudioStateCopyServices.
  2. Read its implementation in src/app/state.c. It obtains the registry from Studio's bootstrap and delegates copying to Framework.
  3. Read PrintServices in src/tools/state_main.c. It owns the output array, prints metadata and frees the array when finished.
  4. Find the --services command-line branch. Follow the checked bootstrap release at the end: printing a report does not remove the need to stop workers and close session state.

After building the updated state tool, run umicom-studio-state --services from an intended working directory. Use the full executable path when it is not on your process search path. The tool starts its own Studio composition and may create its normal local session files. It is not a remote inspector for an already open IDE.

Each row prints an identifier, provider, version and hexadecimal flags. Flags describe policies such as ownership and singleton registration; they are not a health score. The tool writes control characters in identifiers as visible escape sequences so records do not unexpectedly split across console lines.

8. Read the regression checks

Framework's tests/test_service_snapshots.c checks copies before and after removal, replacement and release. It also checks short output buffers and read-only inspection from a service destructor. Studio's tests/test_service_discovery.c checks the application wrapper, while tests/check_service_inventory.cmake checks the native console's exit status and row count.

Study why the C tests keep assertions enabled even in release builds. An assertion is a check which stops the test when a condition is false. If a build removes assertion expressions that also perform setup, the intended experiment does not run at all. The installed module composition example uses explicit status checks instead. Both approaches require actual execution before you can report a pass.

Count without copying every name

A status bar may need only the number of services, not a full list. Framework provides UmiServiceRegistryCopySummary for that case. It fills a small structure with the total and four policy counts under one lock. The runtime inventory uses this operation, so its service total and service flag counts describe the same observation without allocating a large array.

A prefix is the beginning of a name. UmiServiceRegistryCountPrefix can count names beginning with example.. An empty prefix matches all rows. If two providers publish the same service identifier, they are two registrations and count twice. Counting unique names would be a different question.

These service operations do not freeze other registries. An application report may also read commands and capabilities; its owner must follow those registry access rules. Be precise about what one observation covers before describing a report as consistent.
