Store checkpoints on a worker

What you will learn

Saving a small record can take longer than drawing a window. A disk may be busy, a network drive may be unavailable, or a database may be locked. This lesson explains how Umicom Framework lets a reader continue to exist while a background worker stores one explicit learning checkpoint. You will trace the real service used by Studio's learning catalogue.

You can follow the diagrams without installing anything. For the code sections, you need the ideas of a function, a structure and a pointer. The Learning C course introduces them. The previous chapters explain verified readers and revision-bound checkpoints. Here we concentrate on who owns each object and when a request becomes a result.

1. Separate the request from the result

A request describes what the user has asked the application to do. A result reports what actually happened. Clicking Record can produce an accepted request before the database operation has even started. Treating acceptance as success would give the user misleading information.

The request in learning_progress_local.h contains an action, a database path, a learner ID, a checkpoint and an evidence reference. The receipt contains those captured fields, the verified lesson selection, storage flags, a journal snapshot and the final status. A snapshot is a copy of some state at a particular point; it is not a live connection to later changes.

A thread is one sequence of instructions running in a process. The main GTK thread owns the widgets. A worker performs the storage operation. They belong to the same application, but that does not make every object safe to use from both threads at the same time.

2. Capture the user's choice

Imagine that you choose database A, click Record, then change the path field to database B. The accepted action must still refer to A. Otherwise the program would write to a destination you had not chosen when accepting that action.

In learning_catalogue_progress.c, the native adapter copies the fixed-size request structure into a job. It also clones the current reader. Cloning creates an independently owned reader with the already verified selection. It does not reopen the source file and it does not silently adopt a newer lesson.

job->progress_receipt.request = *request;
job->progress_receipt.selection = owner->state.reader;
status = UmiLearningReaderClone(
    owner->reader, &job->progress_reader);

*request means the structure at the supplied pointer. Structure assignment copies its fixed-size arrays as well as its numeric fields. That works here because the request contains values, not borrowed pointers to entry-field text. The reader still needs a clone because it owns allocated objects; assigning a reader pointer would only make another name for the same object.

Before accepting the job, the adapter validates the action, the path and the identifier fields. Only a displayed guide or lesson can receive progress. A source example is refused. This admission stage performs no database operation. If cloning fails, it releases the unsubmitted job and leaves the reader unchanged.

3. Give one worker the whole connection lifetime

A database connection is an object used to communicate with a database. Some libraries restrict how connections may be shared between threads. Even where sharing is possible, mixed ownership makes it harder to reason about transactions and shutdown. The local checkpoint service avoids that problem: the same worker opens, uses and closes one connection.

Read UmiLearningProgressLocalExecute in src/teacher/learning_progress_local.c. Its ownership sequence is:

  1. Validate the copied request and read the verified selection.
  2. Open the chosen SQLite database. Inspect opens an existing database read-only; Record may create the selected database.
  3. Open a journal for the chosen learner. The journal borrows the connection.
  4. Inspect the current checkpoint, or record an explicit event.
  5. Copy the final journal state into the receipt, including an uncertainty flag if a storage operation failed.
  6. Close the journal, then destroy the connection.
  7. Publish the receipt to the caller.

Borrowing means using an object whose lifetime someone else controls. The journal must close before its connection is destroyed. The source makes that order visible:

receipt.status = status;
UmiLearningProgressClose(progress);
umi_data_server_destroy(server);
*out = receipt;
return status;

The receipt contains copied values. It does not expose the closed connection or a pointer into the destroyed journal. A frontend can therefore display it later without retaining either storage owner.

4. Keep the visible lesson independent

The worker's purpose is to record something about the selected lesson. It is not a navigation operation. It must not advance reading history, replace the text or change which lesson the user is viewing.

In learning_catalogue_jobs.c, checkpoint jobs have their own action. Their independent reader is stored in progress_reader. Completion publishes a progress receipt, not a replacement reading session. Search and navigation can later change the display without changing the identity inside that earlier receipt.

This separation is useful beyond learning software. A media export receipt must keep the export's accepted destination even if another playlist is selected. A project-build receipt must keep the source configuration that was actually used. Each application has different domain rules, but captured inputs and explicit ownership are reusable Framework ideas.

5. Understand why retrying can be dangerous

A transaction groups storage changes into one operation. A commit asks the database to make those changes durable. Sometimes the database commits but the caller receives an error before it can know that reliably. “An error was returned” does not always mean “nothing was written”.

The progress journal exposes recovery_required after an uncertain commit or rollback. The native panel then blocks further records. The learner must inspect the same database and learner through a fresh connection. Inspecting a different database does not answer whether the first operation succeeded.

ObservationAppropriate response
Request acceptedWait for completion. Do not yet claim storage succeeded.
Successful new eventDisplay its captured identity and sequence.
Identical event already existsExplain that no additional event was appended.
Valid journal, no exact matchExplain that this revision and hash have no matching checkpoint.
Uncertain writeInspect the original database and learner before deciding whether to retry.
Damaged journalPreserve it for investigation; do not replace it with an empty history.

These are local, plaintext learning records. They do not authenticate the learner, prove that evidence exists or establish mastery. A hash identifies the lesson bytes; it does not turn a self-recorded action into an assessment.

6. Close the window without losing ownership

Closing a panel prevents new requests. It does not undo a write already accepted by its worker. The job holds its own copied fields and reader, so it does not need to access a destroyed widget to finish.

The job keeps a weak reference to its presentation root. A weak reference lets completion ask whether that object still exists without keeping the window alive. If the panel has retired or disappeared, completion discards the presentation result. The job still releases its reader and other allocations.

For a GtkApplication host, accepted jobs also hold the application while work is pending. A hold keeps orderly exit from ending the event loop too early. An explicit forced quit can bypass this contract. Closing a window is therefore not proof that its accepted database write was cancelled; inspect saved state when you return.

7. Follow the real regression source

Open tests/learning_pack/test_catalogue_progress_gtk4.c. The tests exercise public requests with real local database operations. One narrow substitution reports uncertainty after a real write; that lets the test check recovery without depending on a disk randomly failing.

  1. Find no-automatic-write. Explain why opening and reloading a lesson must leave the checkpoint database absent.
  2. Find captured-request. The caller changes its request after dispatch. Explain why the saved receipt must retain the original values.
  3. Find revision-binding. An older event must not satisfy the query for a newly opened pack revision.
  4. Find other-database-recovery. Explain why a valid inspection of another database must leave the record block in place.
  5. Find destroy-pending. Explain why the durable event can exist after the presentation has disappeared.

These cases are authored checks. Their presence in a source repository is not evidence that a particular binary passed them. A missing GTK display or SQLite backend is reported as skipped coverage. A skip is not a successful storage or window test.

8. Try the user workflow

After building a version that includes the feature, use Studio's local learning catalogue and follow Framework's docs/learning/record-private-checkpoints.html. Choose your own private database, open a lesson, inspect, then record one deliberate checkpoint. Reopen the database and inspect again. Repeat the identical record and check that the event count does not grow.

Do not intentionally damage your real records for this exercise. For source-level experiments, use a separate test directory and the supplied regression fixtures. Keep learner history outside public repositories.

Check your understanding

Why is a copied path not enough? The request also needs the learner, checkpoint and verified document identity. Copying only the path would still allow later selections to change what the record describes.

Why close the journal first? It borrows the database connection. Destroying the connection first would leave the journal holding a pointer to an object that no longer exists.

Does a successful Record prove understanding? No. It proves that this local operation stored the requested event according to its contract. Assessment needs separate evidence and authority.
