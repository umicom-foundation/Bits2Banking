Follow protocol message boundaries

Read the accompanying Umicom source example. Match its revision to your checkout before comparing behavior.

What you will learn

When Umicom Studio asks a language server for suggestions, the answer arrives as bytes through a connection between programs. A byte is a small unit of stored information. A stream is a sequence of bytes arriving over time. The operating system can deliver part of a message, one complete message, or several messages in one read. A program must identify the message boundaries itself. In this lesson you will follow that job through the real Framework framer used by language services and the debugger.

You can begin with paper and the diagrams. The practical example needs an installed Umicom Framework SDK and the C tools from the Windows development guide. SDK means software development kit: the headers, libraries and build information needed to use Framework from another project. No account, network server or live project data is needed for this example.

1. Separate a message from a read

A read operation asks a connection for bytes that are available now. It does not promise a whole answer. Imagine the sender writes this small frame:

Content-Length: 2\r\n\r\n{}

The characters \r\n in this illustration stand for two actual control bytes: carriage return and line feed. They mark the end of a header line. A second pair creates the blank line between the header and the body. The body is {}, an empty JSON object. JSON is a text format for values and named fields. This body is two bytes long because each brace uses one byte in UTF-8.

2. Understand the three stages

The transport moves bytes. The framer finds a header and the announced number of body bytes. The message parser understands the JSON fields, such as the request number and result. These are different jobs. A complete zero-byte frame is possible at the framing layer, but an empty body is not a valid JSON response. Separating the jobs lets several applications reuse the same byte-handling code.

  1. umi_language_runtime_framer_feed adds a fragment to owned storage. An OK result means the fragment was accepted; it does not mean a whole message has arrived.
  2. umi_language_runtime_framer_status reports OK for a complete frame, NOT_FOUND when more bytes are needed, or an error when the buffered header is malformed.
  3. umi_language_runtime_framer_pop copies one complete body into caller-owned storage and removes that frame from the queue.

A queue is an ordered collection: the first complete message is delivered first. After popping a message, inspect the framer again before waiting for more input. Another complete message, or a malformed next header, may already be buffered.

3. Count bytes, not visible letters

UTF-8 represents text using one or more bytes for each character. The letter é uses two bytes. Therefore the JSON text {"text":"é"} occupies 13 bytes, even though it has fewer visible characters. Content-Length describes those bytes. It does not count the header or a C string's final zero byte.

A C string usually ends with a zero byte, written '\0'. Framework reserves room for that marker when it returns text. If a body has two bytes, the output array needs at least three slots. A literal zero byte is refused inside incoming JSON text. The six characters \u0000 are different: they are a JSON escape which the JSON layer interprets.

4. Check room before touching input

size_t is C's unsigned type for storage sizes. It has a largest representable value. Adding two large sizes can wrap around to a small value. For a ten-slot buffer with six occupied slots and one reserved ending slot, there are only three free slots. Ask whether the incoming count fits those three slots before reading or copying the input.

if (count > capacity - 1U - used)
    return UMI_STATUS_CAPACITY_EXCEEDED;

This calculation assumes that used < capacity was already checked. The order matters. Framework validates its stored state first, then checks the remaining capacity. A transport callback has a related obligation: if it receives an 8,192-byte destination, it cannot claim to have filled 8,193 bytes. The caller checks that report before inspecting the data.

Ownership means responsibility for keeping memory alive and using only the part that belongs to an operation. The framer owns its buffered bytes. The caller owns the output body. Output storage must not overlap the framer itself. Those separate lifetimes make it possible to retain a partial message without borrowing a temporary read buffer.

5. Keep a good result when the next message is bad

Suppose a read contains a valid response followed by a header with Content-Length: -1. A negative byte count is not valid here. Framework delivers the first response successfully. The next status check reports the malformed header without asking the transport for more bytes.

This detail matters in an IDE. If a valid completion response were consumed and then reported as failed because of a later frame, the editor could lose an answer it had already received. The receive service also decodes into a temporary candidate. Only a complete, valid decoded message replaces the caller's previous result. A failed debugger response does not silently consume its pending request.

A malformed complete header remains an error. An application should close and reconnect the affected protocol connection rather than repeatedly reading and hoping the byte boundary repairs itself. The low-level initializer resets a framer for a new stream; it discards its buffered state, so use it deliberately.

6. Build the small SDK example

Open examples/protocol_frames/main.c in the Framework repository. It uses the actual public API. It allocates a framer, encodes a JSON response, feeds it in two fragments and checks the recovered body. It then feeds a valid frame and a malformed successor together. Its checks remain active in optimized builds because they are ordinary control flow.

  1. Install a matching Framework SDK first. The following commands assume its folder is C:\umicom\installed\framework. Replace that path if your SDK is elsewhere.
  2. Open PowerShell and configure this small example. The explicit SDK prefix prevents accidental selection of a different installation.
  3. Build the example, run its focused check, then run the executable to read its output. Stop if any command fails.
Set-Location "C:\umicom\Umicom-Applications\framework"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake -S examples/protocol_frames -B build/examples/protocol-frames -G Ninja -DCMAKE_C_COMPILER=C:/msys64/ucrt64/bin/gcc.exe -DUMICOM_EXPECTED_SDK_PREFIX=C:/umicom/installed/framework -DBUILD_TESTING=ON
cmake --build build/examples/protocol-frames --parallel 2
ctest --test-dir build/examples/protocol-frames --output-on-failure --no-tests=error
& ".\build\examples\protocol-frames\umicom-protocol-frames.exe"

The expected successful output contains these lines:

First fragment: more bytes are needed.
Complete body: {"jsonrpc":"2.0","id":1,"result":null}
Coalesced input: the valid first body was delivered.
Next header: malformed; no extra read is needed.

This is expected output, not a claim that your machine has run the example. Record the actual command result and SDK revision. A missing umi_language_runtime_framer_status declaration or linker symbol means the example and SDK are from different revisions; update the SDK before retrying. A toolchain metadata error means the SDK was built for a different environment. Do not hide either mismatch by copying headers into the example.

7. Follow the production paths

  • include/umicom/language_runtime/framing.h defines the public contract.
  • src/language_runtime/framing.c owns buffered bytes and parses headers.
  • src/language_runtime/server.c receives and correlates language responses.
  • src/debug_runtime/adapter.c uses the same framing for debugger messages.
  • tests/language_runtime/test_framing_boundaries.c covers fragmentation, refused counts, character encoding and queued messages.
  • tests/debug_runtime/test_receive_boundaries.c checks output and pending-request ownership when a transport or message fails.

Run the full integration checks when changing protocol services. Passing the small console example alone does not establish that a native process launches, that a GUI remains responsive, or that every language server works.

Practice and review

  1. Draw three different ways to split the same encoded frame. Explain why each must produce the same body.
  2. Change the first fragment size in a practice copy from seven bytes to one. Predict the output before rebuilding.
  3. Explain why an OK feed result and an OK pop result establish different facts.
  4. For an output array of eight bytes, what is the largest NUL-terminated body it can hold? Answer: seven bytes.
  5. Why must a custom transport's reported count be checked? Because a count does not enlarge the destination memory it was given.
  6. Why inspect status after popping? The next result may already be buffered, so another blocking read could be unnecessary or wrong.

Apply the idea

A frame arrives in three reads

The first read ends halfway through Content-Length, the second completes the header and begins the body, and the third completes the body. How many messages should the application receive?

Explanation: Exactly one complete message. A read is a transport operation, not a message boundary. Retain incomplete bytes, validate the declared length, and publish only the complete body. No partial read should be presented as a separate response.
