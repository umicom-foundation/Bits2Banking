Copy examples without overwriting your work

What you will learn

Practice should help you experiment without damaging the reference material or your earlier work. This chapter follows the real examples/learning_pack_inspector/practice.c application in Umicom Framework. It previews an example, checks the source bytes and creates a new file only when you explicitly request a copy.

You will meet four useful ideas: selecting a file through a catalogue, checking the bytes before using them, refusing to overwrite an existing file, and reporting a failure accurately. These ideas also apply to Studio saving an export, Media creating a new output file and Bank exporting a statement. Each application decides what the user is allowed to do; Framework provides the reusable storage behaviour.

Read the previous chapter on offline learning readers first. If a term such as file, directory, function or pointer is unfamiliar, return to the Introduction to Computers and Learning C courses. You can draw the steps in this chapter before installing development tools.

1. Separate the reference from your experiment

A directory groups files. A learning pack directory contains a manifest, reading material and examples. Your practice directory holds files that you intend to edit. A copied file initially contains the same bytes as its source, but it is a different file. Changing the copy should leave the reference unchanged.

A byte is a small unit of stored data. Text, images and compiled programs are all stored as sequences of bytes, even though applications interpret them differently. A copy operation must preserve every byte. It must not stop at a zero byte or quietly convert line endings. This matters for both source code and binary files.

learning pack/
    learning-pack.json
    guide.html
    main.c

my practice/
    my-inspector.c

The names above illustrate two separate directories. The lesson's manifest links guide to the example identifier inspector. That identifier refers to main.c. The user chooses the destination name my-inspector.c. The file's visible title, stable identifier and storage path serve different purposes.

2. Preview an operation before changing storage

Open the complete Framework file examples/learning_pack_inspector/practice.c. Start at main, the function called when this console application starts. The argc parameter counts its command-line arguments. argv provides the text of those arguments.

The program first loads a pack with UmiLearningPackLoad. It then calls UmiLearningPracticeResolveExample. This second operation returns a copied description of the example; it does not read the example file. A lesson without an example link returns NOT_FOUND, which means that no example is supplied for that selection.

Next, the program checks the destination's path syntax. A path is a name that locates a file or directory. An absolute root identifies the chosen directory without depending on where the application was started. A relative filename is interpreted beneath that root.

PartExampleMeaning
Absolute rootC:\umicom\practice\learning-packsThe directory the learner chose.
Relative namemy-inspector.cA new file inside that directory.
Nested nameexamples/my-inspector.cA file under an existing examples directory.

Preview displays the selected example and destination. It does not create the destination, reserve its name, verify its permissions or establish that the source bytes are still correct. These conditions can change before the user requests copying, so the later operation must check them again.

3. Verify the source before creating the destination

The copy service begins by reading the entire selected example under a size limit. A size limit prevents an unexpectedly large file from consuming unbounded memory. The example application permits up to four mebibytes: 4 × 1024 × 1024 bytes. The service itself accepts a chosen limit between one byte and sixteen mebibytes.

Framework compares the read bytes with the SHA-256 digest recorded in the manifest. A digest is a fixed-length result calculated from bytes. If the bytes change, the digest is expected to change too. A match checks consistency with that manifest. It does not identify a trustworthy author or establish that the code is safe to run.

If reading or verification fails, destination creation is not attempted. If it succeeds, the service gives the exact verified memory buffer to the writer. It does not reopen the source path and read it a second time. Otherwise another process could change the file between verification and copying.

4. Why an existence check is not enough

Imagine two application workers exporting to the same new filename. Worker A checks and sees no file. Before A opens it, worker B creates a file with that name. If A now opens the name for replacement, it may erase B's work even though A's earlier check was correct.

This is a race: the outcome depends on how operations from different workers overlap. A preview cannot prevent it. The Framework writer asks the operating system to create the file only if no leaf already exists. Creation and refusal are one native operation rather than two separate decisions.

In the source, Windows uses CREATE_NEW; the POSIX implementation uses O_CREAT | O_EXCL. The vertical bar combines flags, which are named options passed to the operating system. Both implementations also use the Framework's checked parent-directory handling. The caller does not build a shell command from the selected filename.

Read tests/platform/test_rooted_create_race.c. Eight workers try to create the same file with different byte patterns. The test expects exactly one successful writer and checks that every byte in the result belongs to that winner. This is different from simply running the writer eight times in sequence. The test is one focused check; it cannot prove protection against every privileged system change or storage fault.

5. Read a result instead of guessing from a file

A new file can exist even though copying failed. For example, the writer may create the file and accept some bytes before storage becomes unavailable. Deleting that partial file automatically can also be unsafe: another process might have changed the pathname since the failure. The service therefore retains the new file and reports what happened.

UmiLearningPracticeResult result;
UmiStatus status = UmiLearningPracticeCopy(
    pack, "guide", selected_root, "my-inspector.c",
    4U * 1024U * 1024U, &result);

if (status == UMI_STATUS_OK) {
    /* Report successful copying; do not start a compiler here. */
} else if (result.destination_attempted && result.destination.created) {
    /* Explain that a partial new file remains for inspection. */
} else {
    /* Explain the refusal without claiming that a copy was created. */
}

This fragment belongs inside an application that already owns a valid pack and selected directory. Read the complete practice.c example for argument checks and cleanup. UmiStatus is a named result value. UMI_STATUS_OK means the operation succeeded. The address operator & lets the function fill the caller's result structure. && means both conditions must be true.

FieldQuestion it answers
source_verifiedWere the source bytes read and matched against the manifest?
destination_attemptedWas the rooted creation operation called?
destination.createdDid the native exclusive creation succeed?
destination.bytes_writtenHow many bytes were accepted by native writes?
destination.completeDid all writing, flushing and closing succeed?

Flushing asks the operating system to commit buffered output. Closing releases the file handle. Neither a successful close nor a complete flag guarantees that a future power failure or external edit cannot affect the file. Applications should describe what they verified, not promise more.

6. Try the complete example

  1. Follow the previous chapter's installed-SDK configuration and build instructions for examples/learning_pack_inspector.
  2. From that example's build directory, create a separate practice directory and run the preview below.
  3. Read the printed destination. Run the second command only when it is the new file you intend to create.
  4. Open the copy in an editor. Add a comment and save it.
  5. Repeat the copy command. It should refuse the existing destination and preserve your comment. Compare the source pack's file as well.
New-Item -ItemType Directory -Force "C:\umicom\practice\learning-packs"
& ".\umicom-learning-pack-practice.exe" "$PWD\pack" learning-pack.json guide "C:\umicom\practice\learning-packs" my-inspector.c

& ".\umicom-learning-pack-practice.exe" "$PWD\pack" learning-pack.json guide "C:\umicom\practice\learning-packs" my-inspector.c --copy

Stop and read any error. A missing parent requires you to create the intended directory. A hash mismatch requires investigation of the source pack. An existing destination requires another new filename if you want another copy. Do not disable checks or remove earlier work merely to make the command succeed.

Copying this one C source file does not supply its include directories, libraries or CMake project. Continue using the complete SDK example when you want to compile it. A future application practice workflow can use the existing Framework project generators for multi-file projects and a separate trust decision before executing project commands.

Check your understanding

  1. Why does preview not guarantee the destination is still free later?
  2. Why should the writer receive the verified bytes instead of reopening the source filename?
  3. Can a failed copy leave a new file?
  4. Does an existing destination authorize replacing it?
  5. What extra decision is needed before running a copied example?
Compare your answers

Another writer can create the destination after preview. Reopening a source could read changed bytes that were not verified. A failure after exclusive creation can leave a partial new file; the result records that state. An existing destination must be refused, preserving the learner's work. Running code requires the application's separate execution-trust workflow and an explicit action; reading and copying are not that permission.

For a paper exercise, draw two writers checking one filename at overlapping times. First draw a separate existence check followed by replacement. Mark where work could be lost. Then replace those steps with exclusive creation and explain which writer can succeed. Finally draw a storage failure after three bytes and show the result fields the interface should display.
