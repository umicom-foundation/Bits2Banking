Build an offline learning reader

What you will learn

A useful application should help people learn without requiring a permanent internet connection. This chapter follows a real Umicom Framework example that opens an offline guide, checks its contents and keeps a reading history. You will learn how a catalogue differs from a file, why a failed operation must preserve the current screen, and how a program transfers responsibility for memory.

You can trace this example on paper first. If pointers and functions are new, return to Learning C before compiling it. The complete source is in Framework's examples/learning_pack_inspector directory. The same reusable service can support guides inside Studio, Trader, education tools and other applications; each application still needs its own presentation and interaction tests.

1. Put a catalogue beside the material

A learning pack is a directory containing a manifest and its resources. A manifest is a small document describing the other files. It is written in JSON, a text format that groups names with values. Braces surround an object, square brackets surround a list, and quotation marks surround text. A comma separates one item from the next.

{
  "id": "guide",
  "title": "Use offline learning packs",
  "topic": "learning-packs",
  "kind": "guide",
  "path": "guide.html",
  "sha256": "a complete 64-character digest belongs here",
  "example": "inspector"
}

This is an explanatory resource entry, not a complete valid manifest: the digest line needs a real digest. The example's CMake configuration copies the actual files and calculates their digests. The generated pack/learning-pack.json is the complete document you can load.

id is a stable name used by application code. title is text shown to a person. path identifies the file relative to the pack directory. They are separate because a title may be translated or a file may be reorganised while the stable identity continues to mean the same lesson. The example field links this guide to another declared resource.

The surrounding manifest also declares the product, language or locale, content revision and compatible application versions. A locale such as en-GB identifies a language and regional convention. A revision is a content edition number. Compatibility bounds tell the loader which host versions the author intended to support; they do not prove that every instruction has been tested on every machine.

2. Understand a content digest

Files are sequences of bytes. A SHA-256 digest is a fixed-size result computed from those bytes. The reader computes a digest for the file it has just read and compares it with the value in the manifest. An ordinary edit changes the digest, so a guide and an outdated catalogue are not silently treated as one matching edition.

A digest does not identify a trustworthy author. Someone who controls both a malicious file and its manifest can calculate a matching digest. You still need a trusted source for the pack. Reading an example also does not give permission to compile or run it. Content consistency, publisher trust and execution permission answer different questions.

Line endings matter because they are bytes too. A text file copied with different line endings can have different content bytes even when it looks the same in an editor. The supplied example hashes the staged files that the reader will actually receive, rather than assuming that another checkout's digest still applies.

3. Keep paths inside a chosen library

An absolute directory identifies the pack's location. A relative resource path identifies a file beneath that directory. The current working directory is where a process happens to be operating; it may change when an IDE opens a project. Framework does not use that changing location to guess where your learning material lives.

UmiLearningPackLoad reads a bounded manifest below the chosen root. The shared rooted-file service rejects parent traversal, reserved names and links or reparse points beneath that root. Ancestors above the selected root must be trusted. These checks are boundaries around this file operation, not an operating-system sandbox against an administrator or every concurrent edit.

The loader copies accepted metadata into an immutable pack. Immutable means its public API does not change the catalogue after creation. The JSON input buffer can be released once loading succeeds. You do not need to retain the original text just to keep the lesson titles alive.

4. Give a reading session one owner

UmiLearningPack *pack = NULL;
UmiLearningReader *reader = NULL;

UmiStatus status = UmiLearningPackLoad(
    directory, "learning-pack.json", host_version, &pack);
if (status == UMI_STATUS_OK) {
    status = UmiLearningReaderCreate(
        &pack, 4U * 1024U * 1024U, &reader);
}
if (status == UMI_STATUS_OK) {
    status = UmiLearningReaderOpen(reader, "guide");
}

/* Use reader here before releasing it. */
UmiLearningReaderDestroy(reader);
UmiLearningPackDestroy(pack);

NULL means the pointer does not currently identify an object. The loader receives &pack, the address of your pointer variable, so it can store the newly created pack there. The reader creation function also receives that address. On success it takes ownership of the pack and sets your pointer to NULL.

Ownership means responsibility for keeping an object alive and eventually releasing it. Once the reader adopts the pack, the reader destroys it during its own cleanup. If adoption fails, the pack remains yours. That is why both cleanup calls are correct: each destroy function accepts NULL, and only one variable owns the pack at a time.

The limit 4U * 1024U * 1024U permits at most four mebibytes in one resource read. A mebibyte is 1,024 × 1,024 bytes. The U suffix marks an unsigned integer literal. A size limit prevents an unexpected resource from demanding unbounded memory.

5. Prepare a page before changing the screen

Suppose a learner is reading A and clicks B. If the program changes its title to B before reading the file, a failure could leave A's text beneath B's title. Framework avoids that inconsistency by resolving and verifying the candidate before committing a new selection. Commit here means accepting an in-memory state change; it is unrelated to creating a Git commit.

A missing file, changed hash or invalid link leaves the current content and navigation history unchanged. The UI can show an error beside the existing lesson. The application should report that error and keep the learner's place, rather than blanking the page or pretending the requested lesson opened.

6. Follow a real local link

status = UmiLearningReaderFollow(reader, "main.c");
if (status == UMI_STATUS_OK) {
    UmiLearningReaderSnapshot page;
    status = UmiLearningReaderCopySnapshot(reader, &page);
    if (status == UMI_STATUS_OK) {
        printf("Selected %s\n", page.selection.resource.id);
    }
}

From this example's guide.html, main.c resolves to the resource named inspector. The file must be declared in the manifest. The first offline link profile accepts local forward-slash paths and anchors. It refuses parent traversal, absolute addresses, queries, percent escapes and unapproved schemes. A refused link must not be retried through a shell or external browser as an automatic fallback.

An anchor such as #navigation names a place within a document. Framework retains the requested name; the renderer must still locate the heading. The resolver does not claim that the anchor exists or that a graphical page has scrolled successfully.

7. Trace Back and Forward

  1. Open guide A. History contains A.
  2. Follow example B. History contains A, B, with B selected.
  3. Go Back. A is selected, and B is still available through Forward.
  4. Open C from A. History now follows A, C. B is no longer in that forward branch.
  5. Try an invalid link from A instead. The request fails; A and the existing forward branch remain unchanged.

The reader keeps at most 64 entries. When another distinct entry would exceed that limit, it discards the oldest one. This bounds memory use. Back and Forward verify the requested file again, so a file changed since your earlier visit is not silently accepted. Reload rechecks the current resource without duplicating its history entry.

8. Copy bytes for a display

A worker is a part of the application that can perform slower work without blocking the UI's event handling. Disk reads belong on an application-owned worker. Serialize reader operations: finish one before starting another or destroying the reader. This service does not create a background thread for you.

First ask UmiLearningReaderCopyContent for the byte count using NULL and capacity zero. Allocate that count plus one. Then copy the content into the allocation. The extra byte is a terminating zero, but the byte count remains authoritative because images and examples can contain binary zero bytes within their contents.

This independent copy can be transferred to your UI using its existing event mechanism. It remains valid after the reader closes. The frontend owns rendering, text-encoding checks and image decoding. It must not execute source code or embedded scripts simply because their bytes passed a hash check.

9. Study and run the supplied example

  1. Open examples/learning_pack_inspector/history.c in your Framework checkout.
  2. Find each status check. Mark the operations that must not run after an earlier failure.
  3. Find the point where the reader adopts the pack. Draw which variable owns it before and after that line.
  4. Follow the example's guide.html for exact installed-SDK configuration and build commands. Its CMake project builds the inspector and the history example without including Framework source.
  5. From that example's build folder, run the command below after the build succeeds.
& ".\umicom-learning-pack-history.exe" "$PWD\pack" learning-pack.json guide main.c

Expected output describes Open on guide, Follow on inspector, Back on guide and Forward on inspector. The final line reports the independently copied byte count. The count depends on the exact file contents. This is a console demonstration of the shared service, not a screenshot or qualification of Studio's document UI.

If the executable is missing, finish the example build. If the pack is incompatible, check the installed SDK and the manifest's version range. If a resource hash differs, inspect why the file changed and rebuild the example's staged pack from the intended sources. Do not suppress verification just to make the command return success.

Check your understanding

  1. Does a matching hash establish a trustworthy publisher?
  2. After reader creation succeeds, which object owns the pack?
  3. If opening another lesson fails, what should happen to the current page?
  4. Why might Back fail even though a lesson opened earlier?
  5. Does opening a C example give permission to compile or execute it?
