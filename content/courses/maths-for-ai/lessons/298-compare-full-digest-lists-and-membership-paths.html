298 — Compare bandwidth for full lists and inclusion proofs

Research-grounded native computing, verifiable evidence and distributed-systems boundaries.

What you will learn

Explain compare bandwidth for full lists and inclusion proofs with explicit assumptions, an independently checkable worked example and the limits of the evidence.

Concept and mechanism

Sending all digest values costs 32n bytes. A compact binary proof needs 32 ceil(log2(n)) sibling bytes, excluding index, count, leaf digest, root and security envelope. The reduction is attractive when a recipient already has an authenticated root and checks only a small number of leaves.

Worked example

For 1024 digests, complete list=1024×32=32768 bytes. A single membership path=10×32=320 bytes, exactly 1/102.4 the bytes of that list; the ratio is not a full protocol speed ratio.

Try it yourself

Estimate two hundred distinct proof sibling payloads without sharing nodes.

Reveal the fully worked answer

200×320=64000 bytes, now exceeding the complete 32768-byte digest list; batching proofs could change the comparison.

Where the proof stops

Do not assume all users request one inclusion proof or that transport cost is the only cost.

A native test can verify byte-level membership but cannot by itself authenticate a participant, authorise financial transactions, establish consensus or prove neural model improvement. Record the independent root, protocol and unperformed tests.

Native implementation boundary

Use the existing Umicom Framework C23 SHA-256 and ordered record chain. The opt-in Merkle service consumes validated digests and exposes bounded membership checks. Existing Python and PowerShell teaching tools remain alternatives, not the implementation.
