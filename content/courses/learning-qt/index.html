Learning Qt

Qt is a library for building applications. A widget is a visible control, such as a text box or button. This course builds a small desktop interface that calls a C function in Umicom Framework. The interface uses C++ because Qt Widgets exposes a C++ API; the reusable validation policy stays in Framework C.

Start with the window and build process, then trace a click into Framework, inspect byte boundaries and test the displayed result. Each lesson includes an experiment and a way to recover from common mistakes. The final lesson explains what still needs qualification on a real desktop.

  1. A window, a program and an event loop
  2. Build a small Qt consumer of the Framework SDK
  3. Controls, layouts and ownership
  4. Connect clicks and keyboard actions to Framework
  5. Pass text safely from Qt to a C function
  6. Test the real widget event path
  7. Troubleshoot a desktop adapter with evidence
  8. Extend the view while keeping Framework authoritative

Continue to web and mobile

Reuse the same form and shared C naming policy with a target-specific toolchain. Lessons 9–12 cover portable composition, browser builds, local delivery and trust boundaries. Lessons 13–16 cover Android, iOS, lifecycle observations and evidence review. Reading needs no account; practical target setup may require platform tooling and signing.

  1. Share one C policy across target toolchains
  2. Build the Qt form for a browser
  3. Serve and observe the generated web application
  4. Separate browser validation from server authority
  5. Package the same Qt lab for Android
  6. Build and observe the lab on iOS
  7. Observe mobile input and application lifetime
  8. Compare desktop, web and mobile release evidence

Each target remains unverified until its build and interaction steps are executed. The existing desktop laboratory has no account creation or persistent draft store.

Build a Qt model over Framework components

Lessons 17–24 use a native Qt Core adapter over the shared C component registry. Follow copied ownership, UTF-8 byte limits, staged insertion and refused edits, then inspect the model and its signal tests without creating a window. This extends the course with a separate installed-SDK lab.

  1. Use the C registry directly from a Qt adapter
  2. Map registry records to rows and roles
  3. Keep text ownership and byte boundaries explicit
  4. Prepare an edit before publishing a Qt row
  5. Test that refused edits preserve the model
  6. Keep model mutation on its owner thread
  7. Check model consistency without launching a GUI
  8. Qualify the model lab and record its limits

The source is in labs/framework/qt-component-model. Compilation, tests and the demonstration require owner execution; authored lessons are not qualification evidence.

Further reading
