Learning Umicom Framework: Markdown manuscripts

This companion keeps the editable lesson manuscripts in a bounded native catalogue. The lesson files and their resource identifiers are preserved. The HTML course remains available through its original manifest.

  1. Use the complete Bits2Banking checkout as the library folder.
  2. Enter learning-packs/umicom-development-manuscripts.json as the manifest path and load it.
  3. Open a manuscript from the list below. Reading source examples does not execute them.
  4. For the HTML lessons, select the separate learning-packs/umicom-development.json pack. Links outside the currently selected pack can be refused by the native reader.

A checkpoint includes its pack identity, revision and resource identity. Existing checkpoints are retained; moving a manuscript to this companion does not automatically migrate its earlier progress record. Review that earlier record separately rather than marking the new entry completed without evidence.

The shared stylesheet, SVG wordmark, SVG icon and ICO are declared resources in both packs. Browser presentation and the native structured reader still require separate qualification.

Project recipe workflow

Eight paired lessons connect the installed Framework API to memory previews and explicit native CLI creation.

  • Select a project recipe by its stable identity
  • Separate borrowed recipes from owned variable values
  • Keep display names, targets and application identities distinct
  • Preview generated files in an owned plan
  • Preserve a reviewed preview when the next recipe fails
  • Choose a destination without confusing it with write authority
  • Move from a native CLI preview to explicit project creation
  • Qualify generated application branding and the installed SDK boundary

Build checked filesystem and project clients

Use shared portable paths, native directory/file ownership, explicit progress and success-only model publication through an installed SDK.

  • Admit portable paths before touching the filesystem
  • Prepare directories below an explicit existing parent
  • Distinguish ensuring a directory from creating a new name
  • Create a file without replacing an existing leaf
  • Read empty and binary files with explicit ownership
  • Report refusal and partial progress without inventing rollback
  • Publish project state only after successful file creation
  • Qualify storage clients across source, SDK and native boundaries

Own native project creation and host lifetime

Trace copied worker requests, GTK task admission, success-only publication, hidden results and safe normal shutdown through shared Framework forms.

  • Copy a project request before starting background work
  • Admit a GTK task before transferring lifetime ownership
  • Publish created source and adoption state in separate steps
  • Distinguish a hidden form from a retired host
  • Keep a host alive until its shared source writer completes
  • Qualify a native workflow without confusing authored tests with results

Observe build failures and own operation history

Use a real installed Framework client to distinguish admission, preparation, copied results, bounded retention and qualification layers.

  • Record an admitted failure before a child starts
  • Keep retained build evidence independent of caller storage
  • Retry with new identities and bounded retained history
  • Qualify the runner, installed client and native presentation separately

Publish owned UI values and reactive observations

Use the installed Framework SDK to handle aliased strings, refused edits, copied properties, revision boundaries and archive admission.

  • Read a UI value as a kind and an owned payload
  • Stage aliased text before replacing a display value
  • Publish a copied property without sharing caller storage
  • Keep reactive observations readable when revisions are exhausted
  • Validate every encoded field without confusing data with authority
  • Qualify a branded installed client and report its limits

Own compiler records, catalogues and argument plans

Build an installed Framework metadata client with bounded records, refused edits, complete plan publication and borrowed-pointer lifetimes.

  • Construct compiler metadata without losing the previous value
  • Check catalogue storage before selecting a compiler
  • Compose a bounded compiler request and preserve refused edits
  • Publish a compiler plan only after every argument is accepted
  • Rebase borrowed argument views after copying a plan
  • Qualify the installed compiler client and report what it proves

Inspect native compiler plans as structured evidence

Use an installed C client and native CLI metadata to distinguish action mappings, complete driver identities, JSON argument boundaries and qualification layers.

  • Choose a compiler action before planning its arguments
  • Keep the complete compiler driver identity
  • Present compiler arguments as structured JSON
  • Qualify preview behavior without claiming a build

Keep compiler metadata and published commands coherent

Explore request identity, staged centre publication, explicit command replacement and unsupported policy intent with an installed C23 client.

  • Distinguish request identity from artifact freshness
  • Preserve both owners when compiler planning is refused
  • Refresh a stored command without losing its ownership
  • Report unsupported compiler policy without weakening it
