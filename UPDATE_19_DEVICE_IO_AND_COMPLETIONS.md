# Device I/O, request lifetimes and bounded completions

A device request crosses multiple ownership boundaries. The caller supplies a request; a driver admits it and retains the information the device may still need; a completion records the observed terminal outcome; a consumer collects the completion; finally the request record can be released.

In this batch, `umicom-education device-io-trace --file PATH` is a Framework-owned **read-only** inspector of a *fictional* binary trace, `UMIDIO1`. It does not access block hardware or use privileged RISC-V instructions. The format is defined in `include/umicom/education/device_io_trace.h`: a 24-byte header and 40-byte records. At most 4,096 events, eight device slots and eight outstanding requests can be represented, with no more than four completed-but-uncollected results. The parser validates owner and generation identities, monotonic record order, request sizes, cancellation intent, terminal outcomes, FIFO completion collection and quiescent detach. Error results leave the caller's output report untouched.

Two separate C23 learning laboratories build these concepts from first principles. `completion-queue` implements a four-slot copied-result ring. `io-request-lifecycle` composes the queue through CMake's `add_subdirectory`, rather than copying its implementation. Both have two CTest cases, including a demonstration executable. No device interrupts, actual DMA or filesystem modifications occur.

Five chapters (122–126), two video scripts (40–41) and three SVG diagrams explain the model and refer readers to Umicom Kernel's authoritative VirtIO block driver and writable-storage guide. Umicom Kernel implements stronger contracts: device-visible queue/bounce-frame ownership, reset acknowledgement, explicit write authority and FLUSH semantics. The classroom state machine should not be substituted for that privileged implementation.
